# Workspaces

Open **Workspace** from the home page and choose a root folder. Enter a workspace name and choose **Save workspace** to create it. Selecting a folder only remembers the location; an existing workspace loads automatically. Names, hierarchy edits, imports, and moves remain in the draft until saved. **Discard changes** restores the last saved state without changing disk contents.

**Remove** schedules deletion when the workspace is saved. Removing a module or project deletes its entire folder, including child definitions, generated data and other files inside it. Removing a run deletes its definition and generated parameter files, then removes project data not used by remaining runs or retained parameter files. Shared setup/results data stays available. Incomplete surviving query spans conservatively retain their output type's data. Cleanup reads data headers rather than decompressing payloads and requires no tracking files. Unlisted folders outside removed components and external import sources remain untouched. Discarding edits before saving cancels deletion. Locked files stop the save; removed contents are staged until definitions commit and restored if the save fails. Any failure during final disposal reports the exact remaining staging path.

Removing a saved item pauses further editing until you choose **Save workspace** or **Discard changes**. You can still select items and copy messages. Saving frees the removed name for reuse, including replacing a project with a module. Removing an item that has never been saved does not need this pause. Workspace error messages can be selected and copied with **Ctrl+C**.

## Persistence boundary

`Sortopia.Workspaces.Persistence` is an F# library that owns workspace filesystem operations and targets plain .NET 10. It references the F# serialization library and uses `Sortopia.FileDb` to identify unshared run data, with no WPF dependency or additional third-party packages. `WorkspaceFileStore` provides the public API for loading definitions and committing saves, removals, copies, and moves. Internally, `WorkspaceDisk` loads and fingerprints the hierarchy, `WorkspaceSavePlan` prepares immutable write plans and remaps IDs, and `WorkspaceCommit` stages and applies transactions with rollback. `WorkspaceDefinitionFiles` locates GUID-named files. The MessagePack schema and folder layout are unchanged by the library extraction and F# conversion.

`WorkspaceImport.PrepareModule` and `PrepareProject` return the loaded definition and a deferred `WorkspaceFolderCopy`. Copies receive new entity IDs, with internal source-project references and run parents remapped together; attaching in place keeps the IDs and returns no copy. Preparation does not write files. Pass the returned copy to `CreateWorkspace` or `SaveWorkspace` to commit it. `PrepareChild` and `WithExclusions` support moving a child out of a pending import while preserving its allocated IDs. Saves return the final definition in `WorkspaceSaveResult`; callers should keep that as the next saved baseline.

WPF owns folder dialogs, remembered folder preferences, draft editing, progress, and error presentation. It calls the persistence library for storage operations. `Sortopia.Workspaces.Serialization` continues to own DTOs and MessagePack encoding, and `Sortopia.FileDb` owns execution data and prepared work items. The independent `Sortopia.Workspaces.Persistence.Tests` project exercises workspace storage without the Windows desktop runtime.

The editor uses `WorkspaceFileStore.LoadDocument`, `CreateDocument`, and `SaveDocument`. `WorkspaceDocument` is an in-memory hierarchy of shallow file DTOs, preserving editable text without parsing it into executable domain values. Each file still stores only its own settings and child references, with captured inherited defaults for module/project portability; no extra draft files are created. Save results provide the document to retain as the next concurrency baseline. Typed `LoadDefinition` and `WorkspaceDocument.toDomain` remain strict and reject invalid configurations and unsealed projects with draft runs. Execution never uses an unvalidated draft.

Run parameter generation validates only the selected saved run, its resolved project settings, and the results contracts of its required source projects. Unfinished sibling runs, unrelated branches, and later changes to module defaults for an already sealed project do not block it. Draft projects still inherit module changes; save relevant changes before generation. `WorkspaceRunDocument.resolve` builds this scope without converting the whole workspace. Source reads need the producer's saved results contract and existing data, not valid producer run inputs or upstream setup settings. Unsaved inputs on the selected run, pending moves of required project folders, and missing required definitions still block generation with a specific explanation. Other workspace issues remain visible and can be saved as drafts.

## Root and branch hierarchies

A workspace can contain both root and branch modules. Each module and all its descendants use one type:

| Container | Allowed children |
| --- | --- |
| Workspace | Root modules and branch modules |
| Root module | Root modules and root projects |
| Branch module | Branch modules and branch projects |
| Root project | Root runs |
| Branch project | Branch runs |
| Run | None |

Root runs execute without a setup step. Branch runs have separate setup and execution settings. Projects contain runs only; use nested modules to organize projects.

Module and project folders sit directly inside their parent folder. Modules may contain both types together, but their folder names must be unique across both collections, ignoring case. For example, results can live at `C:\GuiSpace\SortableTests\Prefix\SmallCC\data\results\SortableTests`. The `runs`, `runParameters`, and `data` directories inside projects are unchanged. Folder names beginning with `.sortopia-` are reserved for transaction staging.

Select the workspace to choose **New root module** or **New branch module**. Inside a module, creation buttons name the matching type, such as **New branch module** and **New branch project**. Inside a project, **New root run** or **New branch run** creates the correct run type automatically. The tree identifies each item's type with text and color; the hint above it explains the selected item's allowed children. Types are fixed when created.

Module and project folders are derived directly from `ModuleName` and `ProjectName`; these entities have no `FolderName` property or constructor argument. Their names must be valid folder names. Save workspace moves the folder and all contents; Discard changes cancels the rename. Nested renames are committed together, occupied destinations are rejected, and failed saves restore the original folders. Sealed projects can be renamed while their IDs, run parents, and execution settings stay fixed. Location displays the resulting full path, which can be selected and copied, with an Open folder button. There is no separate folder-name editor. Workspace display names do not move the selected root folder, and runs remain GUID-named files.

Runs have no folder name. A run is stored directly as `runs/<run-id>.msgpack`. The **Full path** field shows the selected folder or run file and supports text selection/copy. **Open folder** opens that folder, or the containing `runs` directory for a run.

## Module defaults, project defaults, and run inputs

Defaults begin on top-level modules; the workspace itself has no configuration defaults. Root modules supply Description, ResultsFunctionName, ResultsSortopiaDataTypes, and ResultsParameterDefaults. Projects choose query keys separately for each output. Branch modules and projects also share SetupFunctionName, SetupDataTypes, and SetupParameterDefaults. Database names belong only to projects: each root project defines ResultsDatabaseName, and each branch project defines both ResultsDatabaseName and SetupDatabaseName. These are direct fields with initial values `Results` and `Setup`, with no inheritance toggle. Modules have no database properties, and runs display their project’s database names as read-only values with a link to that project. Each resolved setup data-type entry combines its exact type/text pair, SourceProjectId, and its own QueryParameterKeys. Editable overrides contain only source assignments (`setupSources`: exact data type and project ID), descriptions, and parameter defaults; projects also own database names and modules own function selections. Output types are fixed by the function. Projects own editable per-output query selections (resultsQueries and setupQueries), and module/project overrides can exclude inherited defaults by key. The three logical views (setup types, source IDs, and query-key map) are derived from this single list.

Each property follows the nearest ancestor with a local override. The inspector displays its effective value and the name of the ancestor supplying it. Click an **Inherited from [ancestor name]** link to select the module or project defining that property. Check **Override on this module** or **Override on this project** to edit a local value; uncheck it to restore inheritance. Modules and projects inherit shared properties. Function selectors use **Define on this module**; functions are defined only on modules; project and run inspectors show them read-only. Database names remain project-owned. With no ancestor override, descriptions and lists are empty and function names are unset. Organizational modules can leave functions unset; projects need resolved, nonblank database and function names before sealing or generating run parameters. Incomplete settings can be saved as drafts.

Selecting a catalog function fixes its required parameters and saved data types, including each case's string. The inspector displays these contracts read-only. Follow the value-source link to the module defining the function. Projects choose source projects for source-dependent setup outputs and query-key subsets for each output. They cannot change the function's required inputs or output types/strings. Each phase's default and span key dropdowns contain only that function's explicitly declared required parameters. Defaults may supply some of these values at a module or project; runs must supply exactly all required keys through inherited defaults and local spans, with every output query key explicitly present in the spans. An explicitly blank description overrides its parent. Turning a local default override off and back on preserves its draft during the current edit session.

Select a run to edit its description and execution parameters. Branch runs have separate setup parameters. Functions and database names always come from the project. Before sealing, functions follow the draft project’s inherited module selections; after sealing, runs use the project’s fixed snapshot. Only the description has an optional per-run override; an explicitly blank description is allowed.

The run's execution settings and output types are inherited. Query selections belong to the project and can be edited from the project or a draft run until run parameters are generated. **Edit parent defaults** selects the containing project or module, and is available even while a required inherited value is missing. Run type and parent ID come from the containing project. Data types persist as case/text pairs. There is no JSON editor.

Run **Required parameters and spans** editors show a separate coverage checklist for setup and results: supplied by default (with its value and source link), supplied by an explicit span, or still needing span input. Empty or invalid spans and default/span conflicts stay visible as issues. The same editor displays **output query projections** read-only, labeled as inherited from the named project, with a link to edit the matching results or setup projections on that project. Only explicit span keys shared by the project's runs can be selected there; defaults never become query keys. Saving leaves the project editable.

For example, a prefix-tests root run can inherit `SortableDataFormat = Bools` and enter `PrefixLibId` values for 16 and 18 channels in a results span. Select only `PrefixLibId` for the `SortableTests` result projection on its project. The two prefix IDs then identify two result files. Selecting no query keys intentionally makes both parameter sets share one output (for the same project and input data); the editor highlights this consequence. Setup projections follow the same rule independently for each setup output.

For branch results that consume setup data, the results query editor also displays **Query keys inherited from setup**, grouped by the exact setup datatype consumed by that output. These are read-only, with a link to the project's setup projections. They distinguish results through the identities of the consumed setup files; they are not copied into the saved results query projection and do not require duplicate results spans. Additional results query keys distinguish results within each setup combination. Different setup files still produce separate results when no additional results keys are selected.


On a module, open **Results parameter defaults** or **Setup parameter defaults** and choose **Add missing required defaults**. The action adds typed entries for the selected function's required keys that have no inherited or local default. Existing entries and their values stay intact, including incomplete edits, and inherited entries remain inherited. New entries use suggested starting values: 8 channels, 1 stage, 100 sorters, replication 0, self-comparisons excluded, test collection off, `Bools`, `Mssi`, `SplitMix64`, and evaluator `V1`. Channel count follows an existing count or library ID in that phase, then the other phase, before falling back to 8. Library IDs prefer available entries at that width, with a one-stage prefix and a two-way merge where available; if that width has no catalog entry, an available 8-channel entry is used. Review the new values using the usual typed editors and validation. Repeating the action does not duplicate entries; it is disabled when all required keys already have entries or no catalog function is selected.

Use **Add default parameter** on a project or module to supply one typed value per key. Once a catalog function is selected, the key picker contains exactly its required parameters and cannot accept other keys. Each descriptor supplies its value type. Choose the function before editing defaults. The function descriptors determine the available keys and their types; arbitrary custom keys are not offered by these editors. Parameter bindings still support text, integer, unsigned 64-bit integer, floating point, Boolean, GUID, sorter library ID, prefix library ID, and merge library ID at the domain level. Defaults use the same key-specific editors and validation as run spans, including catalog value dropdowns and numeric limits. Boolean values use a True/False selector. Numeric and GUID fields retain invalid drafts and show validation errors. Numbers use invariant formatting, floating values must be finite, and integer bounds are checked. Unconstrained text preserves spaces, commas, Unicode, line breaks, and blank values. Changing a default's key preserves its value and revalidates it. Invalid local or inherited defaults appear in the save explanation and block the affected run preview until corrected; **Override here** uses the same editor for local overrides.

`SorterLibId`, `PrefixLibId`, and `MergeLibId` are distinct typed parameter values backed by the existing catalog ID records. Their shared editor is used for module/project defaults, run spans. Choose a catalog entry to populate its fields, or enter channel count and variant directly. Prefix IDs also require a positive stage length; merge IDs require a positive merge dimension that divides the channel count exactly. Merge catalog suggestions update with the channel count. Invalid field drafts and incompatible values retained after a type change remain visible and can be saved; they block parameter generation. A structurally valid ID may have no catalog entry; lookup availability is checked by the function using it.

Parameter defaults inherit **by key**. A child adding `SorterSuccessFraction = 99%` keeps its parent's `ChannelCount = 16`; a child setting `ChannelCount = 8` replaces only that key. Results and setup defaults merge independently. The inspector shows inherited defaults alongside local defaults, with a clickable source for each inherited value. Choose **Override here** to copy just that key into a local editor. Removing a local row restores its inherited value, if any. An empty local list inherits all parent defaults. Only local bindings are saved as overrides, so other inherited values continue to follow ancestor edits until a project is sealed.

Runs receive the resolved default lists from their parent project. Use **Add parameter** to add a span of candidate values, or **Add missing span rows** to create empty rows for missing query spans and required inputs that have neither a default nor a span. Every output query key requires an explicitly entered span, including fixed values. A default alone never satisfies a query key. Results and setup span pickers use their respective functions’ required keys, excluding keys already supplied by defaults. Spans carry their own declared value type, including when no default exists. Values use that type for editing, validation, serialization, and parameter-set generation. Unsupported keys, missing required inputs, and missing query spans block previews and parameter generation, while draft saving remains available. The shared rule is `default keys ∪ span keys = required keys`, with `default keys ∩ span keys = ∅` and `query keys ⊆ explicit span keys`, independently for setup and results.

Selecting a key chooses its editor and validation. Booleans use True/False; data formats, RNG types, sorter success fractions and evaluator types offer value dropdowns using their domain parsers. Numeric fields retain invariant numeric validation; ChannelCount and SorterCount must be at least 1, while StageLength and Repl may be 0 unless the selected function imposes a stricter limit. GUIDs and free-form text retain their respective editors. Library IDs use structured editors as described below. Functions can provide cross-parameter validation: the five `sorter-model-set.prefix.*` functions check prefix availability, algorithm compatibility, unfolding-level counts, and numeric limits in module/project defaults, run previews, saving, and execution. All span values are checked, including those beyond the preview limit. Changing the key preserves entered values and immediately flags incompatible ones. Each span needs at least one value; blank values are valid for unconstrained text or an empty unfolding list at the seed width. Errors identify the key, clear the affected parameter-set preview, and block parameter generation until corrected. Saving the draft remains available. Results and setup span editors use the same rules, with independent inherited defaults. **Discard changes** also clears invalid field edits.

Use **Exclude default here** on a module or project to stop inheriting that key. Exclusions persist separately from local values, so ancestor changes cannot restore an excluded default. The exclusion list lets you restore inheritance. Defaults are never copied or moved into spans. Enter span values separately for required parameters without defaults; adding missing span rows leaves their values empty. Project defaults cannot change after the project is sealed.

Parameter sets contain all combinations of the run's span values, combined with its disjoint fixed defaults. Defaults ChannelCount = 8 and a Repl span of 11, 13 produce {ChannelCount = 8, Repl = 11} and {ChannelCount = 8, Repl = 13}. Putting Repl in both lists is an error. With no spans, one set contains the defaults, provided they satisfy the function's required inputs and there are no selected query keys. Branch setup and results sets are generated independently.

Run editors have one **Run parameter files** section containing the preview, generation controls, and saved-file table. Expand **Preview parameter combinations** for results combinations and, on branch runs, setup combinations. Each preview row is a combination in execution order, using the effective inherited defaults and local spans. Column headers show the key, type, and whether the value comes from a default or a run span. Model-generation previews also show a read-only **Suggested suffix stages** column beside the set number, calculated independently for each setup or results combination using the same helper as execution. It updates with inherited defaults, local spans, the selected function, and success fraction. Fixed prefix stages are additional. This calculated value is display-only: it does not add an editable parameter or query key. Previews update with edits, show the first 50 combinations and total count, and never allocate the full product just to display it. Invalid parameters or missing required query values replace the affected preview with an error. An empty input produces one empty set. Previewing writes no files and executes no functions.

The workspace has three resizable columns: the hierarchy, a compact read-only configuration summary, and the editor for the selected setting. Drag either divider, or focus it and use the arrow keys, to adjust the widths. The summary shows current values, inherited/local/fixed state, validation issues, and run file status. Select a setting’s linked descriptor to open just that setting on the right. Source links select the defining module or project and keep the same setting open. Save-error links open the corresponding setting directly. Each entity remembers its selected setting while navigating the current draft. Parameter lists and setup outputs remain individual items; run previews, generation reports, and saved files share **Run parameter files**. Edits update the summary without discarding drafts. Each column scrolls independently.

Module editing starts with **Choose functions**. A module may define neither function, one function, or both. Organizational modules can be saved without functions; empty local function choices mean no definition here and inherit from the parent when available. Each draft project's module path must contain exactly one results definition and, for branch projects, exactly one setup definition before generating a run. Setup and results may be defined on different modules in either order. Repeating a definition, even with the same function name, is an issue on the affected draft project and runs; clear the extra module definition. Sealed projects keep their recorded functions independently of later module edits.

Root modules choose results functions that work without setup data. Branch modules can choose results before setup; once setup is known, the results picker lists functions whose inputs that setup supplies. Both selectors share one editor, with setup above results. A known phase exposes its defaults and outputs even if the other phase will be defined by a child module. Name, location, and description remain available throughout.

When an ancestor or descendant module already defines a function, **Define on this module** stays visible but is disabled for that function. The **Defined on [module name]** link opens an ancestor definition; descendant definitions appear as individual links with relative module paths so repeated names can be distinguished. Each link opens the defining module at the same function setting. Setup and results are handled independently. Only nonblank local module definitions count; inherited values and functions captured by projects do not add definitions. Links and availability update after edits, renames, removals, and moves. Clearing all conflicting definitions re-enables the local choice. Older drafts with duplicate definitions retain their saved values and offer **Use inherited function** or **Remove local definition**, as appropriate, to remove the extra local definition.

Project and run editors start with **Inherited functions**, showing setup first for branch hierarchies. Function names are read-only, with source links to the defining module or sealed project. Defaults, spans, outputs, and source settings appear only when the inherited functions are available and compatible. Database names, description, and identity remain accessible while functions need attention. Project default pickers and run span pickers list only their phase’s required keys. Output cards show each function’s fixed types and the project’s chosen query projections. Projects choose compatible source projects only for source-dependent setup outputs; runs display those choices read-only. Sealed projects and their runs keep their saved function contracts when an ancestor changes.

Setup and results functions have separate catalogs and hierarchical name selectors on modules only. Open the selector and expand the dot-separated parts, for example `sorter-model-set` → `uniform` → `mssi`. Browsing groups does not change the configured function: choose a complete name with **Choose function**, Enter, or a double-click. Escape or Cancel keeps the previous selection. The full name stays visible; reopening expands its path. Highlighting a complete function shows its description, required parameter names and value types, and exact output SortopiaDataTypes (including their text) beside the hierarchy. The preview reads the catalog contract for that phase and updates before choosing; group nodes clear it. Long parameter lists can be scrolled without changing the selection. Check **Define on this module** to choose a function; inherited and sealed values remain read-only and retain their source links. Results choices come from `ResultsFunctionCatalog.functions`, and setup choices come from `SetupFunctionCatalog.functions`. Changing a function refreshes its output contracts and allowed parameter keys. Changing a module function retains only compatible inherited defaults; competing module definitions must be cleared before preparing runs. Module defaults for other functions are retained only in the editing session: they are hidden, excluded from the effective configuration and saved overrides, and restored if you switch back. Compatible local values and inherited sources stay intact. Draft project defaults and run spans follow the same rule: entries outside the inherited function’s required keys are kept only in the editing session, hidden from the active editor, and excluded from previews and saved inputs. Restoring the function restores those entries. Incomplete or invalid values for allowed keys remain visible, are saved as entered, and block parameter generation. Upstream source query keys must also be within the setup function's required parameters. The inspector reports incompatible setup/results selections: evaluator functions need a branch setup that provides their exact input types.

The catalogs are plain immutable maps in `Sortopia.Functions`, keyed by `string<resultsFunctionName>` and `string<setupFunctionName>`. `ResultsFunctionNames` and `SetupFunctionNames` hold the typed name variables. Each `functionDefinition` declares `RequiredParameters: paramKeyDescriptor list` and `Outputs: functionOutputDefinition list` alongside its independent `Execute` implementation. Each output declaration contains its exact `DataType`, contributing `ParameterKeys`, and input `Dependencies`. `DataTypes` and `OutputDependencies` are derived maps, and `SourceDataTypes` is the sorted union of dependencies; these are not separate stored declarations. Parameter descriptors define the types once. Output parameter keys describe contributions, not fixed project query keys. Each project query projection selects a subset of the phase’s required keys; required parameters need not occur in any query projection. Duplicate required keys, duplicate output keys, and output keys outside the required contract are rejected. Both `setupConfig.DataTypes` and `resultsConfig.DataTypes` expose the corresponding exact type-to-key maps. `SetupSortopiaDataTypes` and `ResultsSortopiaDataTypes` are their keys; `ResultsQueryParameterKeys` remains a convenience union, never a shared projection for all result files. Current function labels are empty strings, fixed by their definitions.

Define a function with `FunctionDefinition.results` or `FunctionDefinition.setup`, passing its semantic version, parameter requirements, output declarations, parameter support, and executor. Results takes declared typed descriptors via `ParamKey.describe`. Setup takes `setupParameterRequirements.Declared descriptors` or `FromSources`; the latter resolves requirements from source-query keys and requires source inputs. Copied outputs declare empty parameter-key lists and their source types as dependencies; the selected sources still determine required inputs and permitted project query projections. Both builders use the same field and combination validation from parameter support. Add the name/definition pair to `ResultsFunctionCatalog.fs` or `SetupFunctionCatalog.fs`, respectively, and attach a description with `FunctionDefinition.describe`. Descriptions do not change saved identities or require a version change. Both catalogs remain independent name-to-function maps; dot-separated groups are built by the UI.

`OutputPlan.create` receives `definition.Outputs` and the project's saved query projections (`config.DataTypes`). It reads each output's type and dependencies directly from its declaration. Projections must cover exactly the declared types, including labels; an explicit empty projection is valid, and a missing projection is rejected. Catalog `ParameterKeys` never replace the project's choice, including for copied outputs with source-derived keys. Planning requires exactly one reference per declared input type and binds only each output's own dependencies. Canonical query and identity bytes, phase-scoped access, and the storage layout are unchanged.

Every output explicitly declares its dependency list; `Dependencies = []` means that output is independent. There is no parallel table to keep aligned with output parameter keys. Builders require at least one output, unique output types and data kinds, unique parameter keys, and unique dependencies per output. Setup source types must also be exact declared output types, including their labels. For example, evaluation depends on both tests and models, while copied setup tests depend on source tests and generated models have no dependencies. Dependencies are resolved before invoking the executor. Preparation, output checks and `Save` share `OutputPlan` and stable keys; saving a different dependency list is rejected. The derived maps preserve their existing ordering and contents, so consolidating declarations does not change function versions, stored identities, or storage layout. Change the version whenever computation, query projection or dependency contracts change. The builders enforce the correct host phase and cancellation before validating inputs, reject missing, incorrectly typed, and unexpected parameters, and require every output in the invocation plan. Setup additionally requires exactly its declared source-project assignments, with nonempty IDs. Execute validates both phases' contracts and generated sets before work or cache reuse. Unknown names may be retained in drafts, but Execute rejects them.

The initial functions adapt GeneSort's standalone computation to Sortopia's current types. Both function signatures return `unit`: `resultsFunction = runHost -> unit` and `setupFunction = runHost -> sourceProjects -> unit`. `sourceProjects` maps each required source `sortopiaDataType` to its project ID. The host holds the invocation's typed `Parameters`, cancellation token, one phase-scoped `IRunDatabase`, and a read-only `RunOutputs` view. `host.Outputs.Planned` contains the declared output descriptors, and `host.Outputs.Stored` returns a snapshot of successful saves and cache reuses. Both setup and results functions save through `host.Database`. `sortopiaStorageData` is the typed database payload. Its `SortableTests` case contains only `sortableTests`; tests do not track the CEs used to construct or filter them. Exceptions are caught at the execution boundary and reported with the function and parameter-set number.

`IRunDatabase` exposes only `Find`, `Load`, and `Save`. Each write takes a `runDataOutput`: its data type, exact query parameters, and input references. Multiple outputs can share a type while differing in query values, such as generation. `Save(output, factory)` generates data only on a cache miss. `Save(output, value)` accepts an already computed payload and verifies it against any saved value, rejecting mismatches without overwriting files. Both overloads validate the output plan, payload, and cached data. Repeated saves reuse the output and count it once; every supplied value is still checked, and the first save's `Reused` flag is retained. Reads use one lookup/load pair: `Find` returns a reference and `Load(reference)` reads the authorized payload. `Find(dataType)` requires exactly one match among frozen inputs and planned outputs, whether or not the output has been saved yet. An input/output collision or multiple output queries is ambiguous; use `Find(outputDescriptor)` for an exact output or the configured source-query overload for a source. A known input reference is also available in the output descriptor's `Dependencies`. Lookup never generates output payloads or counts them as saved. `host.Outputs.Output(dataType)` requires exactly one planned output; its dependency-list overload also checks the consumed references. The database independently rejects descriptors outside its bound plan. Execution compares `host.Outputs.Planned` against `host.Outputs.Stored` and requires every planned output to be saved or reused. Finding or loading an existing file does not satisfy this check, and failed validation or replay never records a successful write.

`EvolutionSampling` builds snapshot and summary descriptors and batches observations without filesystem access. Its `EvolutionSampler` saves through `host.Database`; the host carries only the optional reporting configuration. `RunOutputFiles` supplies the combined output plan for execution, inspection, cleanup, and report loading. Final populations, intermediate snapshots, and summaries use the same database validation and output tracking.

Settings store results outputs only in `resultsDataTypes`, pairing each exact data type/label with its query keys. Output-type lists and combined query-key lists are derived from those entries and are not serialized separately. Source selection uses the same entries for both output availability and query matching; a missing output never inherits keys from another output or a project-wide projection. Missing canonical output collections are rejected when settings are decoded.

Functions expose read-only `ParameterSupport` providers for suggested defaults, editor rules, guidance, and calculated previews. Defaults receive the current bindings, related phase's bindings, and missing parameter descriptors; existing values are retained. `EditorRules` supplies choices, hints, and single-value validation by parameter key. Guidance receives partial defaults and spans. Previews return named, typed values with labels and hints, which the workspace displays without identifying a model family or interpreting a function name. Functions without suggestions use empty providers. These providers belong only to the runtime catalog and do not contribute to cache identities. Saved run-file suffix sizing reads the `SuffixStages` preview value supplied by the selected function.

The workspace default editor uses function suggestions and only primitive type fallbacks; it has no table of model defaults or library-selection policy. `ParameterDefaults.fs` supplies shared input suggestions and selects libraries using the current or related phase's width. Generation registrations retain their compatible-width, weight, and activator policies. The `sorter-eval.source` copy provider combines common suggestions with `ModelGenerators.sourceDefaults`, which asks algorithm and constructor registrations only for the source-query keys they own. This works with source-derived descriptors without guessing a model family, invoking generation validation, or adding unrelated keys. Existing local and inherited values, including unfinished edits, are retained. Standalone test, evaluation, and SGD functions also supply their defaults through providers; SGD supplies its evaluation measure, mutator variant, and a valid sorted-fraction target.

Saved model and generator records must include their prefix array explicitly; an empty array means no prefix. Missing prefix fields are rejected. The run-file table displays the stage lengths recorded at generation and does not reconstruct missing values from function parameters. A recorded absent length remains valid when the invocation has no single applicable suffix length.

`ModelGenerationDefinitions.fs` builds model-generation contracts for both phases from the registrations in `ModelGenerators.fs`. Each algorithm registration contains its stable name, parameter keys, generator, version, description, input validator, parameter-support provider, and suffix-sizing callback. Defaults, guidance, and previews come from that registered provider. Algorithm-specific rules, such as MSUF4 rate validation and MSUF6 unfolding weights and initial width, live beside their generators. `ModelGenerationSupport.fs` offers reusable builders for common validation and presentation, with no branches selecting algorithms or their parameter keys; registrations can use those builders or provide their own callbacks. Adding a catalog algorithm does not require editing shared helpers or the UI. The internal contracts are defined in `ModelGenerationTypes.fs`; builders and execution do not read a model-type field. A shared generation path supplies the RNG, width, prefix, and registered stage budget to the generator. Concrete Simple-model constructors are registered alongside their stable catalog tokens, required parameters, descriptions, and guidance. There is no separate model-family DU or family-based dispatch: adding a `sorterModel` case does not require updating these registrations unless a corresponding generation function is being offered. The setup and results adapters retain their phase validation wrappers and use the same host database API. Combined generators save models before tests and keep each output factory inside `Save`, so either output can be reused independently. Callers resolve model-generation functions through `SetupFunctionCatalog` or `ResultsFunctionCatalog` using the existing names in `FunctionNames.fs`; `SetupFunctions` and `ResultsFunctions` contain only the distinct copy, evaluation, and test-generation implementations.

Constructor registrations also own `ValidateCombinations`, `Defaults`, and `EditorRules`. SimpleR defines its nonnegative bound as a field rule and the relationship between `AInitial` and `AMax` as a combination check. SimpleS defines its probability range as a field rule and has no combination check. Algorithms similarly provide field rules and a `CombinationError` callback for relationships such as unfolding lengths or all-zero rate combinations. The shared definition builder combines their default suggestions and editor rules. Default suggestions return only requested missing keys in descriptor order. Constructor policies take precedence for their keys. Shared helpers and the UI do not select constructors or contain their generation rules; adding a constructor requires only its registration and the underlying model implementation.

Function builders receive parameter support at construction and compose `InputError` from the shared `FunctionParameterSupport.valueError` check followed by `ParameterSupport.CombinationError`. `FunctionParameterSupport.empty` supplies an empty combination check, so functions with and without custom constraints use the same builders. The same field rule validates editor text, typed defaults, and every distinct span candidate; malformed values stop validation before combination checks run. Missing keys remain valid for partial defaults. Direct execution uses this composed validator before calling the function or reusing cached outputs, as do configuration checks and run preparation. Rules are supplied once, instead of attaching editor support after an execution validator has already been captured. Copy functions apply their source-key field rules through this same path, while retaining their independent copy contract rather than applying generator combination checks.

`WorkspaceParameterRules` only adapts the selected function's editor rules and the generic value-type contracts. Boolean, library, weight, and success-fraction editors remain selected by type; typed parsing runs before provider validation. Model-specific hints and limits live in constructor and algorithm registrations, and SGD owns its selection and mutation policies. Copy functions reuse registered model rules through `ModelGenerators.sourceRules` by the source-query keys' owners, without requiring source function names or applying generation-wide validation to copied inputs. Local defaults, inherited default checks, required-input status, and run spans all consult the active phase's provider, including after a function change. Inputs without a provider retain typed parsing and editors without assuming model policy.

`ModelGenerationCatalog.fs` expands the registered algorithms and constructors through those shared builders. Existing identifiers are constructed from explicit, stable group tokens and the algorithm and constructor registration tokens; the catalog keeps no separate algorithm-name mapping. Setup registers uniform models and standard evaluation inputs; results also registers models with catalog prefixes. The public constants in `FunctionNames.fs` remain unchanged, and tests check that the catalogs contain exactly those names and retain their published versions. Copy, evaluation, and test-only functions remain explicit entries in their phase's catalog.

Catalog definitions expose the composed `InputError` for partial defaults and spans, permitting module/project edits before all required inputs are supplied. `FunctionValidation` combines it with required-key and type checks at run validation and execution boundaries, including output planning before reuse. There are only two phase builders; validation and dependencies do not select a separate builder variant.

`FileRunHost` implements `IRunHostFactory`, creating a separate `runHost` with one `Database` for each invocation. Its output plan permits writes only to that phase's project-local outputs: setup writes to `data/setup`, results to `data/results`. Inputs are read-only and never counted in `host.Outputs.Stored`. During results execution, input access is limited to the exact batch's declared setup references. The host retains output references between invocations, rather than payload lists.

Select each declared output with `host.Outputs.Output(dataType, dependencyReferences)`, then call `host.Database.Save(output, factory)`. Output selection checks the dependencies; the database checks the bound descriptor and stable ID, calling the factory only on a miss. Pure generators pass an empty dependency list. For source-dependent setup, call `host.Database.Find(sourceProjects[dataType], dataType, host.Parameters)` and `host.Database.Load(reference)` to read the source project's results. Lookup resolves the project through the run's workspace scope and applies the producer's result query keys. Source access is read-only and restricted to the configured project/type pairs. Resolved sources do not count in `host.Outputs.Stored`; include every consumed source reference in the saved output's dependencies. Results functions use `host.Database.Find(dataType)` for dependencies and `host.Database.Load(reference)` inside their missing-output factory. During results execution, source lookup is unavailable and setup reads are limited to the frozen input references.

For example, a source-dependent setup saves an output using this pattern (with `dataType` declared in both `DataTypes` and `SourceDataTypes`):

```fsharp
let execute (host: runHost) (sourceProjects: sourceProjects) : unit =
    let source = host.Database.Find(sourceProjects[dataType], dataType, host.Parameters)
    let output = host.Outputs.Output(dataType, [source])
    host.Database.Save(output, fun () ->
        let input = host.Database.Load source
        makeData host.Parameters input)
```

The wrappers verify that the function saved exactly its declared types and labels. There is no registration lifecycle. Each independent definition owns its version; bump it when its output semantics change. Catalogs remain simple name-to-definition maps. Sealed projects capture the function name, version, and resolved output contract. Source lookups use this saved version, even after the installed definition changes. A run whose saved version differs from the installed version cannot execute; create a new project version to use the changed function. Saved data and project snapshots remain readable. Unknown function names are rejected during configuration validation; organizational modules may leave functions unset.

### Standard SGD branch runs

`sorter-sgd.standard.msuf4.simple` (version 6) evolves copied **Simple MSUF4** models using GeneSort's fixed-pool Standard SGD pipeline. Use `sorter-eval.source` for setup, selecting separate SortableTests and SorterModelSets source projects. Setup query projections, inherited query columns, parameter-file generation, and portable execution work as for evaluation branches. The source query weights select the starting model file; the results-phase weights configure mutation and may differ from the source weights. Channel count comes from the copied tests; each copied model supplies its own prefix. Evaluation executes only the suffix against prepared tests, treating the fixed prefix as already applied during input filtering. Prefix CEs remain in evaluation metrics, selection, snapshots, and summaries with usage markers of `-1`; unused suffix CEs are excluded. Version 6 prevents reuse of earlier results that executed the prefix again.

Starting models are taken in stable model-ID order, split into `SorterPoolCount` pools of `SorterCountPerPool` members. Insufficient seeds, incompatible widths, and other model algorithms/families are rejected. Seed model suffixes are evaluated against the complete supplied test set. Each generation mutates every member, retains the best `SelectedSorterCountPerPool` parents, evaluates the children, periodically adjusts raw CE cutoffs, and prunes each pool. Selection uses `SorterEvalMeasure`; `DistinctSorterHashes` removes repeated networks and `PrioritizeNewMutants` controls mutation-cursor tie breaking. As in GeneSort, if strict sorted/length filtering would empty a pool, selection falls back to improving correctness before size. A pool can contain fewer members after duplicate filtering. Each model's prefix remains fixed during mutation and is skipped during evaluation.

`GenerationCount` counts steps after the initial seed evaluation; zero saves that initial population. Mutation uses `RngType`, `MutatorVariantKey` (V1 or V2), `SeedModificationRate`, `ModificationRate`, and normalized relative `OrthoRate` / `ParaRate` / `SelfSymRate` weights. Mutation indices advance for retained parents so later generations do not repeatedly generate the same child. `AdjustCeLengthFrequency` must be positive; `SortedFraction` is the fraction of successful expanded-pool members used to choose GeneSort's raw CE cutoff. These are separate from the model-generation success target.

SGD prepares Boolean inputs with at least 512 tests as `Bitv512` once per invocation on vector-capable machines. The original test ID, duplicates, order, and saved input format are preserved. Independent mutations, network materialization, and evaluation use the invocation's worker budget in separate phases; generations remain ordered. MSUF4 materialization unfolds only enough stages to satisfy the current suffix CE cutoff. These runtime optimizations preserve the generated models, evaluation counts, history, function versions, and output identities.

Scalar batches evaluate independent networks in parallel. SIMD batches choose network ownership when there are at least as many networks as test blocks, or when one worker is requested; otherwise they retain block parallelism. Network owners use ordinary private counters and one reusable work buffer across their test blocks, with no cross-worker counter merge. The block path retains worker-local counts and merges them after processing. Single-file results execution reuses its fully validated setup snapshot instead of deserializing it twice; batch preflight releases payloads to avoid retaining an entire sweep. See [evaluation benchmarks](../benchmarks/README.md) for measurement instructions and results.

Each completed invocation saves one final output with both setup inputs as dependencies: `SorterPoolSet` contains the generation, test identity, and pools with their models, evaluations, parent IDs, and mutation cursors. It contains no embedded history. SGD does not write separate final `SorterModelSet` or `SorterSetEval` files. CSV reports use the evaluations embedded in the saved pools, retaining one row per distinct network within each results file. Completed pool outputs are reused. Pool payload version 2 stores this same population structure for both final results and snapshots; older payload versions are unsupported. The copied source `SorterModelSet` remains a required setup input.

In a run's **Evolution reporting** section, enable two independent schedules: **Full snapshots** retain each model, evaluation, parent, birthday and mutation cursor; **Pool summaries** retain lightweight population statistics, like GeneSort's `ReportCatalog.evolutionSummary`. Choose **Every N generations**, **Increasing intervals** (first interval and fractional growth), or a custom `IntSampleMethod` expression: `Constant(100)`, `Exponential(0.1, 1)`, `Cyclic(Constant(5), 3)`, or `Prefixed(10, Constant(1), Constant(100))`. The preview shows the first samples. Generation 0 is always included. Every GenerationCount value, including values in a sweep, must fall on both the full snapshot and summary schedules. The UI identifies the offending count and schedule and disables parameter generation otherwise; no extra final snapshot or summary is added. For example, snapshots every 100 and summaries every 60 allow generation count 300, but not 200 or 250. With 100 generations, snapshots every 100 and summaries every 1 produce two snapshots and 101 summary samples per pool.

The sampling schedules are frozen with each generated parameter combination. Intermediate full snapshots are ordinary `SorterPoolSet` database records with the label `snapshot`, stored under `data/results/SorterPoolSet`. The final generation must be a scheduled snapshot point, and its snapshot references the ordinary final result file, preserving that file's query projection and identity. It is saved, checked, and counted only once, including when generation 0 is also the final generation. Execution verifies that the observed final snapshot matches the saved final result. `Snapshots.csv` points to that same final file. Summary batches are ordinary `SorterPoolSummarySet` records under `data/results/SorterPoolSummarySet`, the sole source of statistical history and EvolutionSummary.csv. Statistics are computed only at the configured summary generations; disabling evolution reporting creates no historical statistics. Their keys contain the SGD parameter values, exact setup dependencies and generation; summaries also identify their first/last generation and the actual sampled generations. No run or work-item ID participates in these result identities. Equivalent combinations in different runs share the same data, and changing a sampling interval can reuse matching snapshots. Summary batches contain at most 256 sampled generations and are split at snapshot boundaries. Normal database checksums, atomic writes, completion checks and shared-data cleanup apply. There is no evolution subfolder or completion manifest. Removing a run retains samples needed by other generated parameter files. Final-result identities remain unchanged.

This catalog entry implements fixed pools. GeneSort's optional pool expansion/cycling, SOSS, append/condense workflows, and intermediate checkpoint resumption are not included. Cancellation preserves completed files; an unfinished evolution starts again on retry and verifies previously saved samples against the deterministic replay. Snapshots do not currently enable checkpoint resumption. No existing function names, versions, or final-result cache identities change.

### Export sorter evaluation reports

On **Results execution**, choose a run filter, **Select all**, then **Export CSV reports** to aggregate an entire sweep. Selecting individual rows exports just those combinations; **All runs** can combine multiple saved runs in the project. Completed branch parameter files with `SorterSetEval` or `SorterPoolSet` outputs are supported, including `sorter-eval.evaluate` and `sorter-sgd.standard.msuf4.simple`. For SGD, `ResultsDataId` and `ResultsFile` identify the saved pools; `SorterSetEvalId` and `SorterSetId` are blank because no separate evaluation or sorter-set result is created. Re-exporting replaces the previous selected export without creating timestamped or run-specific folders. An export without sampled data removes stale EvolutionSummary/Snapshots CSVs; unrelated files are preserved. The export reads saved invocations, exact setup query headers and validated database results. It never generates models, runs setup, evaluates sorters, changes a cache identity, or reads current draft settings. Copied projects work without the original workspace or source projects.

**Summary.csv** has one row per results file. It includes evaluated and successful sorter counts, `ObservedSuccessFraction` (successful / evaluated), and minimum and median CE/stage lengths among successful sorters. Success means zero unsorted inputs in the associated saved test set. A nonempty evaluation with no successes has fraction zero and blank successful-length statistics. An empty evaluation has count zero and blank fraction, channel count, and length statistics. Observed success is separate from a requested model-generation success target. Evaluated stage/CE lengths describe the saved evaluation's used network; `SetupSuffixStages` and `ResultsSuffixStages` retain the separately recorded generation estimates.

**Details.csv** combines all selected results into one table with one row per network per results file: sorter ID, test subset, actual saved evaluation variant, channel count, success, unsorted count, CE/stage length, sequence hash, last CE index, reflection symmetry, stage crossings, and reflective count. These are the `sorterEval.V1` statistics, also available from saved V2/V3 evaluations; large CE-use arrays and residual test payloads are not expanded into CSV cells. A network appearing in multiple combinations retains one row for each combination. For SGD, these are the final saved networks. Pruning can leave fewer final networks than the requested starting pool size.

For invocations with evolution reporting enabled, the same export also creates **EvolutionSummary.csv** and **Snapshots.csv**. EvolutionSummary has one row per sampled generation and pool: member/success counts and fraction, raw CE limit, minimum/mean/population standard deviation of CE and stage length, mean stage crossings, mean reflective fraction, mean unsorted count, and mean/minimum selection score. These statistics describe the entire pool, matching GeneSort's summary semantics. Reflective fraction is blank if a member has zero CEs. Snapshots has one row per member per full snapshot with its V1 evaluation statistics, generation, pool/member/model IDs, birthday, parent and mutation cursor, plus the full snapshot's path. Both retain the saved mutation parameters and inherited setup query values. Existing runs without sampled reporting still export their final Summary and Details; intermediate statistics cannot be reconstructed from their final evaluations. Reporting-enabled runs with missing or damaged samples must be repaired/rerun before export. All report files are staged before replacing the previous export in the project reports folder.

Both reports repeat the project/run/work-item IDs, exact result and setup data/query IDs, source file paths, saved results parameters, and inherited setup query values. Setup columns use `Setup.<datatype>[<label>].Query.<key>` (the bracketed label is omitted when empty), for example `Setup.SorterModelSet.Query.OrthoRate`. Results parameters use `Results.<key>`. Nonempty labels and key-name segments are percent-escaped, including periods, to prevent column collisions. Keys from different datatypes remain separate. Only saved query projections are reported as setup query values; unrecorded setup defaults are not reconstructed. Set numbers retain their saved zero-based indexing. Columns start with setup query values and results parameters, followed by metrics, then provenance. Each dynamic group has a stable ordinal order. Missing values are blank rather than zero.

The `Sortopia.Reporting` typed report model keeps integers, unsigned integers, floating-point values, booleans, identifiers, text, and missing values distinct until export. It rejects duplicate names, conflicting column types, unknown row columns, and nonfinite numbers. CSV uses comma delimiters, invariant numbers, UTF-8 with BOM, CRLF records, and quoted/escaped text, including embedded commas, tabs, quotes, and newlines. Formula-like text is prefixed with an apostrophe for spreadsheet opening; numeric negatives remain numbers. Use Excel **Data → From Text/CSV**, selecting comma and UTF-8. Keep identifier columns as text, especially when importing large unsigned integers; CSV cannot encode spreadsheet column types or Excel number precision. Fractions are emitted in the range 0–1 and can be formatted as percentages in Excel.

Export revalidates results against their exact planned keys and checks setup query references. Missing/corrupt files, incompatible invocations, and duplicate result selections fail the whole export. CSVs are fully staged before publication. Replacing existing report files uses a publication lock and rolls back on failure, such as a CSV held open in Excel. Unrelated files remain untouched. Evaluation payloads are processed one file at a time, and detail rows are streamed.

Stored setup/results data allows up to 1 GiB uncompressed per payload, supporting larger model sets such as 10,000 MSUF4 models at 895 suffix stages. The compressed file limit remains 256 MiB. Payload bounds and checksums are validated on read; the storage format and cache identities are unchanged.

### File-based data storage

`ISortopiaDb` provides `TryLoad`, `Load`, `FindResults`, and `GetOrCreate`. Each project stores immutable data at `data/{setup|results}/<sortopiaDataType-case>/<data-id>.msgpack`. Database names are logical identity scopes, not filesystem paths. Payloads use explicit versioned DTOs and MessagePack LZ4 block-array compression; envelopes contain full canonical keys and a SHA-256 integrity checksum. This uses existing dependencies, with no SQL database or separate mutable index.

`storedDataReference` carries `ProjectId`, `Id: Guid<sortopiaDataId>`, `QueryId: Guid<sortopiaQueryId>`, `Phase: runExecutionPhase`, and `DataType`. The distinct ID measures prevent mixing query and data identities in F#. The phase selects the `setup` or `results` folder; storage codecs convert it to and from their boolean `IsSetup` field.

Each setup or results output projects its parameter set onto its own entry in `DataTypes`. IDs also include the project ID, database, phase, exact data type/text, function name/version, and declared source-data dependencies. Canonical keys preserve value types, use ordinal key ordering, and are independent of culture and string formatting. Run IDs, execution IDs, and unselected parameters do not participate. Thus setup can reuse the same file when an unrelated span varies, including across runs and app restarts. Results retries also reuse existing outputs, but a single selected results batch must have distinct output owners. Results include only the setup references their function consumes; independent results generators do not duplicate their files when unrelated setup data changes.

**Query keys are a computation contract:** include every parameter that can vary and change that output. A missing selected key is an error; an empty key list intentionally creates one datum per remaining identity scope. The store cannot infer which parameters an arbitrary function uses. This is projection-based reuse, not global deduplication of identical bytes produced by different projects or different keys.

Source lookup uses the source project's fixed results database, function/version, exact data type/text and that output's **results** query keys, projected from the consumer's setup parameters. Execute source runs first. Missing, corrupt, or ambiguous source results stop execution with an error. If multiple upstream setup inputs yielded the same results query projection, lookup refuses to choose arbitrarily; the producer function's contract must distinguish those cases. The current codecs support `SortableTests`, `SorterModelSet`, `SorterSetEval`, `SorterPoolSet`, and `SorterPoolSummarySet`. Catalog declarations describe the primary outputs; configured sampling adds generation-specific outputs to the invocation plan. Other declarations produce a clear unsupported-type error.

Setup writers coordinate through a project-local file lock and check again after acquiring it, so concurrent setup creators invoke a shared factory once. Results writers generate independent outputs without that lock. The empty `.write.lock` file is coordination infrastructure, not a status marker; the active lock is its open file handle. Files are flushed to a temporary sibling and published without overwriting existing data. Readers ignore incomplete temporary files. Source lookup scans headers within the relevant data-type directory without an additional index. Corruption is reported instead of silently regenerating data. Failure, cancellation or a process crash retains already published outputs, which subsequent output checks and retries discover directly. Existing historical receipt files are ignored and left in place; new work never depends on them.

The initial codecs read whole objects and limit both files and uncompressed payloads to 256 MiB. This store is intended for a local workspace filesystem. Moving an existing project preserves its IDs and data. Importing a copy assigns new project IDs, so copied historical data retains its original identity and is not reused by the new project; executing the copy creates data in its new scope.

Select the function on the module and use **Add missing required defaults**. Mode weights start equal and can be edited through the named fields in defaults or spans, using the same typed editors as the prefix functions. MSUF4 normalizes its three floating-point rates once and uses that distribution for its four-channel seed and every unfolding level. The number of levels is derived from the width (`log2(channelCount / 4)`): 4 channels need zero levels, 8 need one, 16 need two, 32 need three, and 64 need four. For prefixed model functions, the width comes from `PrefixLibId`. Rates must be finite and nonnegative, with at least one positive rate in every span combination; defaults are `1, 1, 1`. For example, `2, 1, 1` becomes probabilities `0.5, 0.25, 0.25`. MSUF6 still requires one OPS distribution per width doubling from 6, reused identically in every stage. New UF6 defaults use 12 channels when no compatible width is suggested; other models default to 8. Existing inherited and local values are preserved. Width, stage capacity, replication limits, activators, and every width/weight span combination are validated in both phases before generation or reuse. Defaults and spans remain disjoint; query projections select only explicit spans. Local setup, portable results files, and output reuse work with these functions. Saved-test evaluators execute only each model's suffix against prepared inputs. Model evaluation retains every fixed prefix CE with `UseCount = -1`, plus suffix CEs that made swaps with their real counts. Suffix indices are offset by the prefix length, keeping indices in the complete sorter. Lengths, stage metrics and sequence hashes describe that retained network, counting the prefix once. Merging evaluations preserves `-1` markers and sums only measured suffix counts; serialization retains the markers. `Simple` uses the complete generated suffix. `SimpleR` starts every suffix activator at the integer `AInitial`, within the inclusive bounds `[-AMax, AMax]`; `AMax` must be nonnegative. Only positive activators enable suffix entries. `SimpleS` generates Boolean activators using `ActivationProbability` in [0, 1]. Activators never suppress the fixed prefix. New SimpleR defaults use `AMax = 1` and `AInitial = 0` (suffix initially inactive); SimpleS uses `ActivationProbability = 0.5`. Validation checks every bound/start combination in parameter spans, even beyond the preview limit. Both `AMax` and `AInitial` participate in generator identity and serialize with the generator.

Setup and results default and span editors show only the selected function's inputs: `AMax` and `AInitial` for SimpleR, `ActivationProbability` for SimpleS, and neither for Simple. The function selector chooses the family, so it cannot vary in a parameter span. Changing the selected function updates inherited inputs and projection candidates as well as local editors.

`SorterSuccessFraction` is a typed choice of `pct50`, `pct90`, or `pct99`, displayed as 50%, 90%, or 99% and initially set to 99%. It replaces the editable `StageLength` parameter in all model-generation setup and results functions, including combined evaluation-input generators. The selected algorithm, channel count, and prefix depth determine the random suffix capacity through `SimpleSorterStageLengths`; the fixed prefix is additional. Prefixed model functions use the width and depth in `PrefixLibId`; uniform models use zero prefix stages. Defaults and run spans show the suggested suffix length, or a range across their combinations. These are provisional whole-network success targets assuming uniform, enabled entries; custom weights and SimpleR/SimpleS activation can change the actual success rate. See [stage-length methodology](stage-lengths.md). Each parameter set produces `SorterCount` models of the selected family. `Repl` selects the reproducible model-index batch starting at `Repl * SorterCount`. With all other inputs fixed, rerunning the same batch produces the same models, and increasing `Repl` selects the next batch. `RngType` selects the random generator; only the CE function accepts `ExcludeSelfCe`. Model-generation functions use version 2 or later for this changed parameter contract and call their model-specific initializers. MSUF4 version 3 replaces `Seed4Weights` and `UnfoldingWeights` with the three normalized float rates in both required inputs and model-output query projections, across Simple, SimpleR, and SimpleS. Saved sealed MSUF4 version-2 projects require a new project version for the new contract. The previously unused `SelfSym` parameter name is corrected to `SelfSymRate`. Existing sealed version-1 projects retain their saved data and require a new project version to execute with the new parameter; old stage-length values are not reinterpreted as success fractions.

MSUF4 version 6 uses five times the original calculated suffix budget for every success target, keeping the version-3 parameter contract. For 16 channels with one prefix stage, the 50%/90%/99% budgets are now 435/675/895 stages. Other algorithms are unchanged. The new version prevents reuse of shorter cached models; existing generated files retain their lengths until regenerated using the current function version.

MSRS and MSUF6 weights are typed parameter values with named mode fields in the default and span editors. They must be finite and nonnegative, with at least one positive mode per distribution; zero excludes a mode. Each distribution normalizes independently. MSUF6 starts at width 6. For example, UF6 at width 24 needs two unfolding distributions, for 6 → 12 and 12 → 24. The MSUF6 seed and all per-level weights repeat unchanged in every generated stage. Add/remove MSUF6 unfolding levels in the editor; mismatched prefix widths and level counts block parameter generation and execution, but can be saved in a draft. Newly populated defaults use equal mode weights and enough unfolding levels for the selected prefix; fresh UF6 modules start with a 12-channel prefix. Existing inherited and local values are preserved. Values remain typed in parameter sets and round-trip in portable run-parameter files.

The prefix must exist in the catalog and its channel count must suit the function. `Msce` and `Mssi` support every currently cataloged prefix width; `Msrs` requires an even width; `Msuf4` requires a power of two of at least 4; `Msuf6` requires 6 times a power of two (6, 12, 24, 48, ...). For example, Prefix1 at width 16 works with `Msuf4`, while width 24 works with `Msuf6`. Validation covers inherited defaults and every span value. All prefix/weight combinations in a run's Cartesian product must be compatible. MSUF6 needs separate runs for widths requiring different unfolding-level counts; MSUF4 derives each combination's levels automatically and supports mixed-width spans.

Supply fixed inputs as module/project defaults and varying inputs as explicit run spans. Select the desired query keys from those spans for the `SorterModelSet` output, for example `PrefixLibId`, `Repl`, and (for SimpleR) `AInitial` when they vary and should produce separate files. Defaults remain defaults. The root run needs no setup phase or source project; it supports both direct Execute and generating portable run-parameter files. Results are saved under `data/results/SorterModelSet` and reused using the configured query projection.

## Types and persistence

`Sortopia.Workspaces` defines concrete `rootProject`, `branchProject`, `rootModule`, and `branchModule` types. Their child arrays are strongly typed: for example, `rootProject.Runs` is `rootRun[]`, and `branchModule.Projects` is `branchProject[]`. The `project` and `workspaceModule` discriminated unions provide common views for storage and the editor. Their boundary factories validate type consistency. `workspace.Modules` accepts either `workspaceModule.Root` or `workspaceModule.Branch`. Array properties return copies.

Modules and projects expose their effective shared properties directly and through `Configuration` (`rootProjectConfig` or `branchProjectConfig`). `LocalOverrides` uses `rootDefaultOverrides` or `branchDefaultOverrides`: each property is optional, with `None` meaning inherit and `Some` meaning local, including `Some []` and `Some ""`. `Defaults.resolveRoot` / `resolveBranch` apply local values over the inherited configuration. For parameter defaults, `Defaults.mergeParameterDefaults` replaces matching keys, retains other inherited bindings in order, and appends new local keys. Both `None` and `Some []` inherit all parameter defaults; duplicate keys within a local list are invalid. Other list properties use whole-list replacement. `createInherited` constructs an entity with its parent configuration and local overrides; `rebind` resolves it and its descendants against a new parent. The existing project `create` factory makes every supplied configuration property local; the module `create` factory starts with all properties inherited.

`RootRun.create parent inputs` and `BranchRun.create parent inputs` accept their concrete parent projects through `IRootProject` / `IBranchProject`; the contracts avoid a dependency from runs back to workspaces. Run input records contain Id, RunName, ParentProjectId, DescriptionOverride, and ResultsParameterSpans. Branch inputs also contain SetupParameterSpans. Function overrides are absent from project local overrides and run inputs. Both database names come from the project. The parent must be sealed when constructing a runtime run; `project.seal` creates that immutable parent snapshot and `project.withRuns` attaches the validated runs. `RunDto.toDomain` prepares a sealed snapshot without mutating the draft parent. A run retains its inputs in `Configuration` and fixed settings in `ProjectConfiguration`. Branch runs also retain resolved source project snapshots, so queries need no further workspace lookup.

The four shared names have distinct UMX tags: `resultsDatabaseName`, `resultsFunctionName`, `setupDatabaseName`, and `setupFunctionName`. Shared configuration is factored into `resultsConfig` and `setupConfig`. A `setupDataTypeConfig` contains `DataType: sortopiaDataType`, `SourceProjectId: Guid<projectId>`, and `QueryParameterKeys: string<paramKeyName> list`. `setupConfig.DataTypes` is the ordered list; its `SortopiaDataTypes`, `SourceProjectIds`, and `QueryParameterKeys` views derive from those entries. Results query keys remain one list.

`workspace.ProjectIndex` indexes projects globally by ID, and `FindProject` returns an optional project. Workspace creation/loading validates references and resolves branch source snapshots through `BranchRunSources.resolve`. `QueryParams.forSource` uses the source project's ID, results database, and results query keys. `forSetup` uses the parent project's ID, effective setup database, and the selected entry's query keys; `forResults` uses the parent project's results metadata. Query IDs use the stable project ID, exact type/text pair, and selected parameter strings, rather than the display name.

`sortopiaDataType` is a discriminated union with ten cases: `Workspace`, `Run`, `WorkspaceModule`, `RunParameters`, `SorterPoolSet`, `SorterSet`, `SorterModelSet`, `SortableTests`, `SorterSetEval`, and `TextReport`. Every case carries a free-form `string`; empty strings, whitespace, Unicode, and line breaks are preserved. Execution and setup output lists use this type, as do result and setup queries. Each output row has a case selector and a text field. Lists can contain the same case with different text; an identical case/text pair cannot appear twice. Inherited lists show both values and retain their clickable source. Query matching and query IDs include both the case and the exact text.

`parameterBinding` is the general pairing of a `string<paramKeyName>` with a typed `parameterValue`. It can represent a supplied parameter, a default, or an override; the containing property or operation determines its role. `ParameterBinding.create key value` constructs a binding from a typed key, `fromValue name value` accepts an already typed union value, and `fromText name kind text` validates editor or persisted input. All constructors enforce the known key's type and valid values. `ParameterBinding.validateUnique` validates collections with one binding per key. `parameterBindingDto` and `WorkspaceParameterBinding` provide the corresponding storage and editor representations.

`parameterSet` stores a `Map<string<paramKeyName>, parameterBinding>` exposed by `ParamMap`. `parameterSet.fromBindings bindings` creates a set directly; `parameterSet.create map` accepts a typed map and validates that each key matches its binding. `set.WithBinding(binding)` adds or replaces a binding while preserving the original set. `WithValue` accepts a typed key/value or a key name with a `parameterValue`; `None` removes the key. Binding construction, validation, and set updates retain the typed values without formatting or reparsing them.

`set.TryFind(name)` returns a binding. `set.TryFind(typedKey)` reads the underlying CLR value directly, returning `None` for a missing key or mismatched type; numeric-looking text remains text. String conversion is explicit: `TryFindText(name)` formats one value, and `ToStringMap()` projects the whole set to canonical invariant strings. Queries format only their selected keys; DTO serialization formats bindings at the storage boundary. Library IDs remain typed through bindings, parameter sets, and catalog function calls. File-store identity uses their type tags and stable field bytes, so alternate input formatting produces the same data ID.

`ParameterSets.create bindings spans` expands bindings and spans into `parameterSet[]`. It parses span text using the matching binding's type or the known key's type, and stores each candidate as a typed binding. Matching spans replace bindings and other bindings remain fixed. Combinations exceeding the maximum .NET array length are rejected before allocation.

`ParameterSets.preview maxCount bindings spans` shares the same validation and combination generator, materializing only the requested prefix. All candidate values are validated, including values beyond the visible rows. The editor retains typed parameter sets and formats values only for display.

`RunParameterSets.create run` returns a `runParameterSets` record with `Results: parameterSet array` and `Setup: parameterSet array option`. Root runs return `Setup = None`; branch runs return `Some setupSets`. Results and setup combinations are expanded independently from their respective defaults and spans, retaining typed bindings. No spans is valid only when there are no output query keys and the defaults satisfy the required inputs. The function uses the run's resolved settings and does not need a workspace lookup.

`ResultsParameterDefaults` is a `parameterBinding list` on root/branch modules, projects, and runs. Branch types additionally expose `SetupParameterDefaults`. These properties use bindings as defaults, merging by key through modules and draft projects. Runs receive the sealed project's resolved defaults; their spans replace matching keys. `RootRun.makeResultsParameterSets`, `BranchRun.makeResultsParameterSets`, and `BranchRun.makeSetupParameterSets` use the general binding APIs. `ParamKeys.all` supplies metadata derived from the typed key declarations.

Every entity has a UMX-tagged GUID ID: `workspaceId`, `moduleId`, `projectId`, or `runId`. Its definition filename is `<id>.msgpack`. IDs survive edits, moves, and missing-file restoration. Only the workspace retains a separate root folder name. Modules and projects use their entity names as folder segments. The absolute workspace location stays in application settings, outside the definitions.

Names must be nonblank. Sibling module and project names share one namespace and must be distinct ignoring case; sibling run names must also be distinct. Module, project and run IDs must each be unique within their entity kind throughout the workspace. Rejected edits remain visible for correction while the tree keeps the last accepted value; Save is disabled until corrected. Saved names stay reserved until their removal or rename has been saved.

Workspace, module and project files use schema version **18** through `WorkspaceDefinitionCodec`. Workspace and module child references contain only `{ id, name }`, where `name` is the child entity name and its single relative directory segment directly under the parent. Module/project definitions store their names once, without a separate `folderName`. Separate module/project reference arrays identify the type without extra directories. Project run references are ordered GUID arrays addressing `runs/<id>.msgpack`. When opening or importing modules/projects, their containing folder names must match the entity names. IDs are checked against both the referenced ID and the definition filename; duplicate IDs, duplicate sibling folders, invalid family relationships and escaping paths are rejected. Loading follows references rather than directory enumeration, preserving saved order and keeping removed-but-retained entities out of the loaded tree. Missing children are reported with their ID and location; there is no embedded descendant snapshot to fall back to when reopening.

Modules persist local overrides and **captured parent defaults**, without an additional copy of their own effective configuration. Draft projects likewise persist local overrides and captured parent defaults, including inherited function selections; database names remain project-owned overrides. `inheritedFrom` records the immediate parent module's ID and name for captured context. These defaults are captured *before* local overrides, including values currently hidden by a local override. Removing a local override from a detached entity therefore restores the original parent value. Captures refresh when ancestor defaults change even if the child's effective value is unchanged. Attached entities resolve against the actual parent; `LoadModuleFolder` and `LoadProjectFolder` use the captured context at the detached root and then resolve its descendants normally. Attaching/importing into a workspace resumes normal inheritance from the destination parent. Sealed projects store only their complete fixed configuration and run references, without a redundant inherited-context or local-overrides copy. Captured context makes configuration portable; it does not copy external source-project data or executor code.

Run files use schema version **15**: IDs, optional description override and spans, with no folder or database overrides. `WorkspaceCodec.decodeRunById workspace bytes` resolves a sealed parent and source snapshots; `decodeRun parent bytes` supports an already loaded parent. Run-parameter payloads use schema version **2**; their stage-length display uses only the recorded values. Unsupported run-parameter versions must be regenerated. `WorkspaceDto`, `ModuleDto`, `ProjectDto` and the aggregate methods on `WorkspaceCodec` remain in-memory editing/cloning/comparison representations; persistence does not write them as container files. Older definition formats are rejected without modification; the obsolete layout converter has been removed.

Saving compares the loaded files' content hashes in memory, so edits to any referenced definition—including captured values hidden by live inheritance—cannot be silently overwritten. No tracking file is added. An already-open workspace can explicitly restore missing definitions from its loaded tree; surviving files still must match the loaded baseline. A run-input-only edit writes its run file without rewriting project, module or workspace files. Transactional rollback and folder moves continue to cover the separate definition files.

Definition limits are 64 nesting levels, 50,000 entities, and 16 MB per definition file. Multiple container definitions in one entity folder are reported as ambiguous. Unrelated files are not serialized; explicit folder imports and moves preserve their contents.

## Workspace file inspector

Open **File inspector** from Home or **Inspect files** from the workspace editor. The inspector reads saved files without changing them or discarding the editor's unsaved changes. It can browse a workspace, a detached module, or a copied project without first loading a valid hierarchy. The folder list loads one directory at a time, with filename filtering, 200-entry pages, refresh, and a splitter between the file list and details. Child-reference links open the referenced definitions and identify missing files.

Workspace, module, project and run definitions display their stored fields, including local overrides and captured inherited defaults. Prepared run parameters display each binding's key, type and value, fixed functions/outputs and local setup references. These views decode saved content; they do not resolve live inheritance or validate the entire workspace.

Stored setup/results data displays an envelope summary: data type/label, project/data/query IDs, database/function/version, query parameter count, dependency references, compression, payload sizes and recorded checksum. The inspector reads at most 1 MiB of the uncompressed envelope header and never decompresses the large data payload. It checks envelope length and identity hashes, but does not claim to validate the payload checksum; **Check outputs** remains the integrity check for execution data. Writer lock and temporary files have explanatory summaries, and other files show filesystem metadata.

Detailed configuration/metadata reading is limited to 4 MiB on disk (16 MiB decompressed for prepared metadata). Larger files receive filesystem summaries. Detail trees show at most 200 elements per collection, 4,000 nodes overall and 4,096 characters per value, with explicit truncation notices. Referenced-file links and dependency summaries are also bounded. Reads run away from the UI thread; changing selection cancels obsolete results. Missing, locked, malformed and unsupported files produce an explanation containing the affected path. The inspector does not follow filesystem links or navigate outside its selected root.

### Configurable query projections

Enter the run spans first, then select the project and open Results outputs or Setup outputs to select query keys separately for each data type. Runs inherit these choices and cannot override them; their output panels and span editors link directly to the corresponding project settings. Choices are restricted to valid explicit spans present in every current run of that project. Each query key must be a required input of its phase function and cannot also have a default. Empty selections are allowed. A key that loses its span remains visible with an error and blocks parameter generation; the incomplete configuration can still be saved.

Query keys control reuse: only selected parameter values, the project/function/output identity, and the declared input data references distinguish an output. Omitting a varying span key intentionally reuses the output across those values. With an empty projection, all parameter combinations share an output for the same input references. The UI states this beside each output. The selections are frozen with the project, included in portable runParameters files, and used for source-project lookup and output-completion checks.
