# Workspaces

Open **Workspace** from the home page and choose a root folder. Enter a workspace name and choose **Save workspace** to create it. Selecting a folder only remembers the location; an existing workspace loads automatically. Names, hierarchy edits, imports, and moves remain in the draft until saved. **Discard changes** restores the last saved state without changing disk contents.

Choose **Export workspace** in the top toolbar to copy the complete saved workspace into an empty folder outside the current workspace. Save or discard pending changes first and wait for execution to finish. The export includes all nested modules, projects, runs, generated parameter files, data, and other workspace files, preserving IDs and references. The current workspace and remembered folder remain unchanged. Export runs in the background and can be cancelled. Open the exported folder with **Browse** to use the copy.

**Remove** schedules deletion when the workspace is saved. Removing a module or project deletes its entire folder, including child definitions, generated data and other files inside it. Removing a run deletes its definition and generated parameter files, then removes project data not used by remaining runs or retained parameter files. Shared setup/results data stays available. Incomplete surviving query spans conservatively retain their output type's data. Cleanup reads data headers rather than decompressing payloads and requires no tracking files. Unlisted folders outside removed components and external import sources remain untouched. Discarding edits before saving cancels deletion. Locked files stop the save; removed contents are staged until definitions commit and restored if the save fails. Any failure during final disposal reports the exact remaining staging path.

Removing a saved item pauses further editing until you choose **Save workspace** or **Discard changes**. You can still select items and copy messages. Saving frees the removed name for reuse, including replacing a project with a module. Removing an item that has never been saved does not need this pause. Workspace error messages can be selected and copied with **Ctrl+C**.

## Persistence boundary

`Sortopia.Workspaces.Persistence` is an F# library that owns workspace filesystem operations and targets plain .NET 10. It references the F# serialization library and uses `Sortopia.FileDb` to identify unshared run data, with no WPF dependency or additional third-party packages. `WorkspaceFileStore` provides the public API for loading definitions and committing saves, removals, copies, and moves. Internally, `WorkspaceDisk` loads and fingerprints the hierarchy, `WorkspaceSavePlan` prepares immutable write plans and remaps IDs, and `WorkspaceCommit` stages and applies transactions with rollback. `WorkspaceDefinitionFiles` locates GUID-named files. The MessagePack schema and folder layout are unchanged by the library extraction and F# conversion.

`WorkspaceImport.PrepareModule` and `PrepareProject` return a `ModuleDocument` or `ProjectDocument` and a deferred `WorkspaceFolderCopy`. Copies receive new entity IDs, with internal source-project references, captured parent IDs, child references, and run parents remapped together. This includes sources in sealed snapshots and retained editing settings; external IDs remain unchanged. Attaching in place keeps the IDs and returns no copy. Preparation validates the document structure without parsing unfinished parameter values and does not write files. Pass the returned copy to `CreateDocument` or `SaveDocument` to commit it. `PrepareChild` and `WithExclusions` support moving a child out of a pending import while preserving its allocated IDs. Saves return a `WorkspaceSaveResult`; its `Workspace` is the explicit saved revision to use for subsequent saves and lifecycle operations.

WPF owns folder dialogs, remembered folder preferences, draft editing, progress, and error presentation. It calls the persistence library for storage operations. `Sortopia.Workspaces.Serialization` continues to own DTOs and MessagePack encoding, and `Sortopia.FileDb` owns execution data and prepared work items. The independent `Sortopia.Workspaces.Persistence.Tests` project exercises workspace storage without the Windows desktop runtime.

Persistence, imports, cloning, comparisons, and the editor use `WorkspaceDocument`, an in-memory hierarchy of editable definitions and child collections. `WorkspaceFileStore.LoadWorkspace`, `CreateDocument`, and `SaveDocument` preserve editable text without parsing it into executable domain values. `LoadModuleDocument` and `LoadProjectDocument` read detached subtrees through the same disk reader. Child membership and order exist only in document collections; shallow file references are derived when saving. Each file still stores only its own settings and child references, with captured inherited defaults for module/project portability; no extra draft files are created. Document copies, comparisons, and concurrency baselines include raw text and the editing settings retained by sealed projects. There is no parallel typed workspace hierarchy or whole-workspace runtime conversion; test fixtures also construct documents directly. `WorkspaceRunDocument.resolve` / `resolveByRunId` validates only the selected run, its parent configuration, and the required source results contracts. This produces a `RunExecutionScope` containing the run and required project locations; its parent snapshot comes directly from the run. Resolution does not parse unrelated draft projects, sibling runs, or source runs. Editing has one save path through `SaveDocument`; generation persists the selected parent snapshot before writing setup data or parameter files.

`LoadWorkspace(folder)` returns a `SavedWorkspace` handle containing the normalized root folder, a protected document baseline, and fingerprints of the referenced definition files. Call `CreateEditDocument()` explicitly to obtain an independent editable copy, then `SaveDocument(edit, saved, token)` and retain `result.Workspace` after success. Focused reads avoid copying the hierarchy: `ResolveRun(runId)` (or `ResolveRun(projectId, runId)`) resolves the selected run; `TryReadProjectState(projectId)` returns a detached lifecycle state; `TryReadRunSnapshotControls(runId)` returns detached controls even when run inputs are unfinished. None of these reads expose mutable baseline values, including SGD/reporting controls in resolved runs. Changes to the original input, an edit copy, or a read result cannot mutate either saved revision. Saving and lifecycle operations obtain their destination from the handle. There are no fallback baselines inferred from an editable document. Failed or cancelled operations leave the existing handle available for retry.

Generation, resume, reset, and removal use the saved handle and return the resulting handle. Generation seals the saved draft before its first generated-file write and retains the original editing settings. Refresh and generation retain the same handle when they do not save a new revision, allowing WPF to apply persisted lifecycle changes while preserving unrelated unsaved edits. Detached import documents remain ordinary documents until committed into a saved workspace.

Resume, parameter-file removal, and reset use one internal `WorkspaceLifecycle` planner. Its result contains the updated document, the project IDs permitted to return to editing, and the removal paths, with nested paths reduced to their containing folders. Planning does not write definitions or delete files; `WorkspaceFileStore` checks the saved revision and applies the complete result through the normal save transaction. Resuming a sealed project clears its data cache. Parameter-file removal retains shared outputs and keeps the parameter folder; when other runs remain, it also keeps reports. Reset additionally removes project reports when resetting one of several runs, and clears the parameter/data trees when resetting the last run or a whole container. Automatic lock refresh uses the same resume path and retains its existing project-by-project behavior.

WPF replaces its editors explicitly after load, save, discard, and reset. Generation, resume, parameter-file removal, and lock refresh share one lifecycle-update path that advances the saved revision, applies sealing/resume transitions, and preserves editor instances, selection, unsaved inheritance choices during sealing, and the dirty flag. Discard then restores this latest saved revision. The selected-run cache includes the saved revision and project/run IDs in its key, so both resolved scopes and validation errors are recomputed when the revision changes without manual invalidation calls.

`WorkspaceDocumentIndex` provides ordered module/project/run entries, parent relationships, module ancestry, and relative paths. Editable-document operations create their own index; it is never cached across document edits. A saved revision can retain an internal index for focused reads because its baseline does not change. `WorkspaceNavigation` replaces projects while preserving identity and sibling order. Run resolution, lifecycle changes, reset/removal planning, and editor refreshes share this navigation.

`InspectGeneratedFiles` returns one inspection result for locked runs, projects, and ancestor modules. Unreadable parameter files keep the affected project and ancestors locked; when run ownership cannot be read, all of that project's runs remain locked. Empty directories do not lock a project. `RefreshProjectStates` uses this inspection to release unused generated snapshots through the normal transactional resume operation. The editor derives its sealed presentation and retained choices from one lifecycle state, with generated-file locks kept separate. Generation preserves unsaved editing choices that do not change effective settings; they remain unsaved until the next workspace save.

Run parameter generation validates only the selected saved run, its resolved project settings, and the results contracts of its required source projects. Unfinished sibling runs, unrelated branches, and later changes to module defaults for an already sealed project do not block it. Draft projects still inherit module changes; save relevant changes before generation. `WorkspaceRunDocument.resolve` builds this scope without converting the whole workspace. Source reads need the producer's saved results contract and existing data, not valid producer run inputs or upstream setup settings. Unsaved inputs on the selected run, pending moves of required project folders, and missing required definitions still block generation with a specific explanation. Other workspace issues remain visible and can be saved as drafts.

## Root and branch hierarchies

A workspace can contain both root and branch modules. Each module and all its descendants use one type:

| Container | Allowed children |
| --- | --- |
| Workspace | Root modules and branch modules |
| Root module | Root modules and root projects |
| Branch module | Branch modules and branch projects |
| Root project | Root runs |
| Branch project | Branch runs |
| Run | None |

Root runs execute without a setup step. Branch runs have separate setup and execution settings. Projects contain runs only; use nested modules to organize projects.

Module and project folders sit directly inside their parent folder. Modules may contain both types together, but their folder names must be unique across both collections, ignoring case. For example, results can live at `C:\GuiSpace\SortableTests\Prefix\SmallCC\data\results\SortableTests`. The `runs`, `runParameters`, and `data` directories inside projects are unchanged. Folder names beginning with `.sortopia-` are reserved for transaction staging.

Select the workspace to choose **New root module** or **New branch module**. Inside a module, creation buttons name the matching type, such as **New branch module** and **New branch project**. Inside a project, **New root run** or **New branch run** creates the correct run type automatically. The tree identifies each item's type with text and color; the hint above it explains the selected item's allowed children. Types are fixed when created.

Module and project folders are derived directly from `ModuleName` and `ProjectName`; these entities have no `FolderName` property or constructor argument. Their names must be valid folder names. Save workspace moves the folder and all contents; Discard changes cancels the rename. Nested renames are committed together, occupied destinations are rejected, and failed saves restore the original folders. Sealed projects can be renamed while their IDs, run parents, and execution settings stay fixed. Location displays the resulting full path, which can be selected and copied, with an Open folder button. There is no separate folder-name editor. Workspace display names do not move the selected root folder, and runs remain GUID-named files.

Runs have no folder name. A run is stored directly as `runs/<run-id>.msgpack`. The **Full path** field shows the selected folder or run file and supports text selection/copy. **Open folder** opens that folder, or the containing `runs` directory for a run.

## Module defaults, project defaults, and run inputs

Setup and Results configuration are independent on modules, projects, and runs. Selecting or inheriting a registered function reveals that phase's outputs and parameter defaults immediately, together with query selections on projects and parameter spans on runs. A missing, unavailable, or incompatible function in the other phase does not hide these editors or discard their values. Compatibility and required-function errors remain visible and must be resolved before generating run parameters. Existing defaults above a function definition remain accessible.

Defaults begin on top-level modules; the workspace itself has no configuration defaults. All modules supply Description, ResultsFunctionName, and ResultsParameterDefaults. Branch modules also have a Setup block containing FunctionName, Sources, and ParameterDefaults. Module output types are derived from their selected functions; modules have no stored output configurations, query fields, or database properties. Module inheritance resolves directly in `ModuleDefaults`, using shared `ConfigurationInheritance` operations for defaults, exclusions, and source choices. A one-way conversion supplies the initial project configuration with empty query projections.

Projects choose query keys separately for each output. Database names belong only to projects: each root project defines ResultsDatabaseName, and each branch project defines both ResultsDatabaseName and SetupDatabaseName. These are direct fields with initial values `Results` and `Setup`, with no inheritance toggle. Runs display their project’s database names as read-only values with a link to that project. Each resolved project setup data-type entry combines its exact type/text pair, SourceProjectId, and its own QueryParameterKeys. Editable overrides contain source assignments (`setupSources`: exact data type and project ID), descriptions, and parameter defaults; projects also own database names and per-output query selections (resultsQueries and setupQueries), while modules own function selections. Output types are fixed by the function. Module/project overrides can exclude inherited defaults by key.

Each property follows the nearest ancestor with a local override. The inspector displays its effective value and the name of the ancestor supplying it. Click an **Inherited from [ancestor name]** link to select the module or project defining that property. Check **Override on this module** or **Override on this project** to edit a local value; uncheck it to restore inheritance. Modules and projects inherit shared properties. Function selectors use **Define on this module**; functions are defined only on modules; project and run inspectors show them read-only. Database names remain project-owned. With no ancestor override, descriptions and lists are empty and function names are unset. Organizational modules can leave functions unset; projects need resolved, nonblank database and function names before sealing or generating run parameters. Incomplete settings can be saved as drafts.

Setup source choices inherit independently by exact data type and text. **Setup outputs and source projects** appears under Setup on branch modules, projects, and runs as soon as a setup function is known, even before a results function is selected. Projects can define or override sources there; runs show their inherited choices. SorterModelSet and SortableTests each have their own checkbox: **Define on this module/project** when no ancestor supplies a source project, or **Override on this module/project** when an inherited source is selected. Empty ancestor selections do not count as definitions for this caption. Each source starts unchecked and follows its parent unless a local choice is explicitly enabled or loaded from saved overrides; opening the editor or changing an ancestor does not enable an override. Checking one copies only that inherited choice into a local draft; unchecking restores inheritance for that source while preserving its local draft for this editing session. A checked source with no project selected explicitly remains unassigned. Modules may leave sources for descendants; generation requires both resolved choices. The Setup function grid links each source to its own defining module or project. It shows the query parameters required by each selected source immediately, even while another source remains unassigned. Parameters are grouped beneath bold SorterModelSet and SortableTests source rows. A shared key appears in both groups, displaying the same value and opening the same default or span; their default, span, and missing-value icons work throughout. Defaults for sources that descendants will select later are retained. Runs inherit the resolved choices, and sealed projects keep their captured selections.

Selecting a catalog function fixes its required parameters and saved data types, including each case's string. The inspector displays these contracts read-only. Follow the value-source link to the module defining the function. Projects choose source projects for source-dependent setup outputs and query-key subsets for each output. They cannot change the function's required inputs or output types/strings. Each phase's default dropdown contains the function's required non-query parameters; its run span rows are defined by the project query keys. Each run must supply exactly the union of that phase's per-output query keys as spans. All other required parameters need fixed defaults on the project or an ancestor module. An explicitly blank description overrides its parent. Turning a local default override off and back on preserves its draft during the current edit session.

Select a run to edit its description and execution parameters. Branch runs have separate setup parameters. Functions and database names always come from the project. Before sealing, functions follow the draft project’s inherited module selections; after sealing, runs use the project’s fixed snapshot. Only the description has an optional per-run override; an explicitly blank description is allowed.

The run's execution settings and output types are inherited. Query selections belong to the project and can be edited there before runs exist, until run parameters are generated. Runs display these selections read-only with a link to the project. **Edit parent defaults** selects the containing project or module, and is available even while a required inherited value is missing. Run type and parent ID come from the containing project. Data types persist as case/text pairs. There is no JSON editor.

Run **Required parameters and spans** editors show a separate coverage checklist for setup and results: supplied by default (with its value and source link), supplied by an explicit span, or still needing a query span or fixed default. Empty, invalid, or undeclared spans and default/span conflicts stay visible as issues. The same editor displays **output query projections** read-only, labeled as inherited from the named project, with a link to edit the matching results or setup projections on that project. Choose query keys on the project from required parameters without fixed defaults. New runs start with an empty span row for every declared key; existing runs keep their entered values and report missing or undeclared spans. Defaults never become query keys. Saving leaves the project editable.

For example, a prefix-tests root run can inherit `SortableDataFormat = Bools` and enter `PrefixLibId` values for 16 and 18 channels in a results span. Select only `PrefixLibId` for the `SortableTests` result projection on its project. The two prefix IDs then identify two result files. With no query keys selected for the entire phase, all required inputs must be fixed defaults and there is one parameter set. An individual output may select an empty subset while another output uses the span keys; that output is shared across those parameter sets when its input data is unchanged. Setup projections follow the same rule independently for each setup output.

For branch results that consume setup data, the results query editor also displays **Query keys inherited from setup**, grouped by the exact setup datatype consumed by that output. These are read-only, with a link to the project's setup projections. They distinguish results through the identities of the consumed setup files; they are not copied into the saved results query projection and do not require duplicate results spans. Additional results query keys distinguish results within each setup combination. Different setup files still produce separate results when no additional results keys are selected.


On a module, open **Results parameter defaults** or **Setup parameter defaults** and choose **Add missing required defaults**. The action adds typed entries for the selected function's required keys that have no inherited or local default. Existing entries and their values stay intact, including incomplete edits, and inherited entries remain inherited. New entries use suggested starting values: 8 channels, 1 stage, 100 sorters, replication 0, self-comparisons excluded, test collection off, `Bools`, `Mssi`, `SplitMix64`, and evaluator `V1`. Channel count follows an existing count or library ID in that phase, then the other phase, before falling back to 8. Library IDs prefer available entries at that width, with a one-stage prefix and a two-way merge where available; if that width has no catalog entry, an available 8-channel entry is used. Review the new values using the usual typed editors and validation. Repeating the action does not duplicate entries; it is disabled when all required keys already have entries or no catalog function is selected.

Use **Add default parameter** on a project or module to supply one typed value per key. Once a catalog function is selected, the key picker contains exactly its required parameters and cannot accept other keys. Each descriptor supplies its value type. Choose the function before editing defaults. The function descriptors determine the available keys and their types; arbitrary custom keys are not offered by these editors. Parameter bindings still support text, integer, unsigned 64-bit integer, floating point, Boolean, GUID, sorter library ID, prefix library ID, and merge library ID at the domain level. Defaults use the same key-specific editors and validation as run spans, including catalog value dropdowns and numeric limits. Boolean values use a True/False selector. Numeric and GUID fields retain invalid drafts and show validation errors. Numbers use invariant formatting, floating values must be finite, and integer bounds are checked. Unconstrained text preserves spaces, commas, Unicode, line breaks, and blank values. Changing a default's key preserves its value and revalidates it. Invalid local or inherited defaults appear in the save explanation and block the affected run preview until corrected; **Override here** uses the same editor for local overrides.

`SorterLibId`, `PrefixLibId`, and `MergeLibId` are distinct typed parameter values backed by the existing catalog ID records. Their shared editor is used for module/project defaults, run spans. Choose a catalog entry to populate its fields, or enter channel count and variant directly. Prefix IDs also require a positive stage length; merge IDs require a positive merge dimension that divides the channel count exactly. Merge catalog suggestions update with the channel count. Invalid field drafts and incompatible values retained after a type change remain visible and can be saved; they block parameter generation. A structurally valid ID may have no catalog entry; lookup availability is checked by the function using it.

Parameter defaults inherit **by key**. A child adding `SorterSuccessFraction = 99%` keeps its parent's `ChannelCount = 16`; a child setting `ChannelCount = 8` replaces only that key. Results and setup defaults merge independently. The inspector shows inherited defaults alongside local defaults, with a clickable source for each inherited value. Choose **Override here** to copy just that key into a local editor. Removing a local row restores its inherited value, if any. An empty local list inherits all parent defaults. Only local bindings are saved as overrides, so other inherited values continue to follow ancestor edits until a project is sealed.

Runs receive the resolved default lists from their parent project. Runs automatically display one row per project query key. The key is read-only; use **Add value** and the value removal buttons to edit its span. Project query changes update existing runs as well as new runs. Every output query key requires an explicitly entered span, including fixed values. A default alone never satisfies a query key. Results and setup each use the union of their project output query keys. Other required inputs need fixed defaults. Spans carry their own declared value type, including when no default exists. Values use that type for editing, validation, serialization, and parameter-set generation. Unsupported keys, missing required inputs, and missing query spans block previews and parameter generation, while draft saving remains available. The shared rule is `default keys ∪ span keys = required keys`, with `default keys ∩ span keys = ∅` and `query keys = explicit span keys`, independently for setup and results.

Each parameter key determines its editor and validation. Booleans use True/False; data formats, RNG types, sorter success fractions and evaluator types offer value dropdowns using their domain parsers. Numeric fields retain invariant numeric validation; ChannelCount and SorterCount must be at least 1, while StageLength and Repl may be 0 unless the selected function imposes a stricter limit. GUIDs and free-form text retain their respective editors. Library IDs use structured editors as described below. Functions can provide cross-parameter validation: the five `sorter-model-set.prefix.*` functions check prefix availability, algorithm compatibility, unfolding-level counts, and numeric limits in module/project defaults, run previews, saving, and execution. All span values are checked, including those beyond the preview limit. Changing a project query or function preserves obsolete and duplicate run inputs in **Retained inputs needing repair**. These values and their types survive draft saving and reopening. Re-select the key on the project to reuse its values, or choose **Discard retained values** to remove the obsolete row. Each span needs at least one value; blank values are valid for unconstrained text or an empty unfolding list at the seed width. Errors identify the key, clear the affected parameter-set preview, and block parameter generation until corrected. Saving the draft remains available. Results and setup span editors use the same rules, with independent inherited defaults. **Discard changes** also clears invalid field edits.

Use **Exclude default here** on a module or project to stop inheriting that key. Exclusions persist separately from local values, so ancestor changes cannot restore an excluded default. The exclusion list offers **Restore fixed default**. On a project, restoring a default also removes that key from its output queries and retains existing run values for repair. Defaults are never copied or moved into spans. On a project output, expand **Fixed parameters** and select **Use as query key** to exclude its default and select that output key in one action. Local defaults are retained in the existing exclusion representation for later restoration, including unfinished draft values. Excluded values are omitted when building typed runtime settings. New span rows start empty; defaults are not copied into run values. Project defaults cannot change after the project is sealed.

Parameter sets contain all combinations of the run's span values, combined with its disjoint fixed defaults. Defaults ChannelCount = 8 and a Repl span of 11, 13 produce {ChannelCount = 8, Repl = 11} and {ChannelCount = 8, Repl = 13}. Putting Repl in both lists is an error. With no spans, one set contains the defaults, provided they satisfy the function's required inputs and there are no selected query keys. Branch setup and results sets are generated independently.

Run editors have one **Run parameter files** section containing the preview, generation controls, and saved-file table. Expand **Preview parameter combinations** for results combinations and, on branch runs, setup combinations. Each preview row is a combination in execution order, using the effective inherited defaults and local spans. Column headers show the key, type, and whether the value comes from a default or a run span. Model-generation previews also show a read-only **Suggested suffix stages** column beside the set number, calculated independently for each setup or results combination using the same helper as execution. It updates with inherited defaults, local spans, the selected function, and success fraction. Fixed prefix stages are additional. This calculated value is display-only: it does not add an editable parameter or query key. Previews update with edits, show the first 50 combinations and total count, and never allocate the full product just to display it. Invalid parameters or missing required query values replace the affected preview with an error. An empty input produces one empty set. Previewing writes no files and executes no functions.

The workspace has three resizable columns: the hierarchy, a compact read-only configuration summary, and the editor for the selected setting. Drag either divider, or focus it and use the arrow keys, to adjust the widths. The summary shows current values, inherited/local/fixed state, validation issues, and run file status. For branch modules, projects, and runs, setup settings form the first group and results settings the second; each function is grouped with its database, outputs, defaults, and applicable run spans. Select a setting’s linked descriptor to open just that setting on the right. Source links select the defining module or project and keep the same setting open. Save-error links open the corresponding setting directly. Each entity remembers its selected setting while navigating the current draft. Parameter lists and setup outputs remain individual items; run previews, generation reports, and saved files share **Run parameter files**. Edits update the summary without discarding drafts. Each column scrolls independently.

Module editing starts with **Setup function** for branch modules or **Results function** for root modules. Each function entry shows only its own function. A module may define neither function, one function, or both. Organizational modules can be saved without functions; empty local function choices mean no definition here and inherit from the parent when available. Each draft project's module path must contain exactly one results definition and, for branch projects, exactly one setup definition before generating a run. Setup and results may be defined on different modules in either order. Repeating a definition, even with the same function name, is an issue on the affected draft project and runs; clear the extra module definition. Sealed projects keep their recorded functions independently of later module edits.

Root modules choose results functions that work without setup data. Branch modules can choose results before setup; once setup is known, the results picker lists functions whose inputs that setup supplies. Both selectors share one editor, with setup above results. A known phase exposes its defaults and outputs even if the other phase will be defined by a child module. Name, location, and description remain available throughout.

When an ancestor or descendant module already defines a function, **Define on this module** stays visible but is disabled for that function. The **Defined on [module name]** link opens an ancestor definition; descendant definitions appear as individual links with relative module paths so repeated names can be distinguished. Each link opens the defining module at the same function setting. Setup and results are handled independently. Only nonblank local module definitions count; inherited values and functions captured by projects do not add definitions. Links and availability update after edits, renames, removals, and moves. Clearing all conflicting definitions re-enables the local choice. Older drafts with duplicate definitions retain their saved values and offer **Use inherited function** or **Remove local definition**, as appropriate, to remove the extra local definition.

Project and run editors show each inherited function in its own **Setup function** or **Results function** entry, starting with setup for branch hierarchies. Function names are read-only, with source links to the defining module or sealed project. Defaults, spans, outputs, and source settings appear only when the inherited functions are available and compatible. Database names, description, and identity remain accessible while functions need attention. Project default pickers list required non-query keys; run span keys are read-only and come from the project. Output cards show each function’s fixed types and the project’s chosen query projections. Projects choose compatible source projects only for source-dependent setup outputs; runs display those choices read-only. Sealed projects and their runs keep their saved function contracts when an ancestor changes.

Setup and results functions have separate catalogs and hierarchical name selectors on modules only. Open the selector and expand the dot-separated parts, for example `sorter-model-set` → `uniform` → `mssi`. Browsing groups does not change the configured function: choose a complete name with **Choose function**, Enter, or a double-click. Escape or Cancel keeps the previous selection. The full name stays visible; reopening expands its path. Highlighting a complete function shows its description, required parameter names and value types, and exact output SortopiaDataTypes (including their text) beside the hierarchy. The preview reads the catalog contract for that phase and updates before choosing; group nodes clear it. Long parameter lists can be scrolled without changing the selection. Check **Define on this module** to choose a function; inherited and sealed values remain read-only and retain their source links. Results choices come from `ResultsFunctionCatalog.functions`, and setup choices come from `SetupFunctionCatalog.functions`. Changing a function refreshes its output contracts and allowed parameter keys. Changing a module function retains only compatible inherited defaults; competing module definitions must be cleared before preparing runs. Module defaults for other functions are retained only in the editing session: they are hidden, excluded from the effective configuration and saved overrides, and restored if you switch back. Compatible local values and inherited sources stay intact. Draft project defaults and run spans follow the same rule: entries outside the inherited function’s required keys are kept only in the editing session, hidden from the active editor, and excluded from previews and saved inputs. Restoring the function restores those entries. Incomplete or invalid values for allowed keys remain visible, are saved as entered, and block parameter generation. Upstream source query keys must also be within the setup function's required parameters. The inspector reports incompatible setup/results selections: evaluator functions need a branch setup that provides their exact input types.

The catalogs are plain immutable maps in `Sortopia.Functions`, keyed by `string<resultsFunctionName>` and `string<setupFunctionName>`. `ResultsFunctionNames` and `SetupFunctionNames` hold the typed name variables. Each `functionDefinition` declares `RequiredParameters: paramKeyDescriptor list` and `Outputs: functionOutputDefinition list` alongside its independent `Execute` implementation. Each output declaration contains its exact `DataType`, contributing `ParameterKeys`, and input `Dependencies`. `DataTypes` and `OutputDependencies` are derived maps, and `SourceDataTypes` is the sorted union of dependencies; these are not separate stored declarations. Parameter descriptors define the types once. Output parameter keys describe contributions, not fixed project query keys. Each project query projection selects a subset of the phase’s required keys; required parameters need not occur in any query projection. Duplicate required keys, duplicate output keys, and output keys outside the required contract are rejected. Both `setupConfig.DataTypes` and `resultsConfig.DataTypes` expose the corresponding exact type-to-key maps. `SetupSortopiaDataTypes` and `ResultsSortopiaDataTypes` are their keys; `ResultsQueryParameterKeys` remains a convenience union, never a shared projection for all result files. Current function labels are empty strings, fixed by their definitions.

Define a function with `FunctionDefinition.results` or `FunctionDefinition.setup`, passing its semantic version, parameter requirements, output declarations, parameter support, and executor. Results takes declared typed descriptors via `ParamKey.describe`. Setup takes `setupParameterRequirements.Declared descriptors` or `FromSources`; the latter resolves requirements from source-query keys and requires source inputs. Copied outputs declare empty parameter-key lists and their source types as dependencies; the selected sources still determine required inputs and permitted project query projections. Both builders use the same field and combination validation from parameter support. Add the name/definition pair to `ResultsFunctionCatalog.fs` or `SetupFunctionCatalog.fs`, respectively, and attach a description with `FunctionDefinition.describe`. Descriptions do not change saved identities or require a version change. Both catalogs remain independent name-to-function maps; dot-separated groups are built by the UI.

### Standard SGD branch runs

`sorter-sgd.standard.msuf4.simple` (version 7) evolves copied **Simple MSUF4** models using GeneSort's fixed-pool Standard SGD pipeline. Use `sorter-eval.source` for setup, selecting separate SortableTests and SorterModelSets source projects. Setup query projections, inherited query columns, parameter-file generation, and portable execution work as for evaluation branches. The source query weights select the starting model file; the results-phase weights configure mutation and may differ from the source weights. Channel count comes from the copied tests; each copied model supplies its own prefix. Evaluation executes only the suffix against prepared tests, treating the fixed prefix as already applied during input filtering. Prefix CEs remain in scalar evaluation metrics, selection, snapshots, and summaries; unused suffix CEs are excluded. Optional detailed reevaluation marks already-applied prefix CEs with usage counts of `-1`. Version 7 adds snapshot controls and checkpoint continuation while preserving the corrected prefix evaluation.

Starting models are taken in stable model-ID order, split into `SorterPoolCount` pools of `SorterCountPerPool` members. Insufficient seeds, incompatible widths, and other model algorithms/families are rejected. Seed model suffixes are evaluated against the complete supplied test set. Each generation mutates every member, retains the best `SelectedSorterCountPerPool` parents, evaluates the children, periodically adjusts raw CE cutoffs, and prunes each pool. Selection uses `SorterEvalMeasure`; `DistinctSorterHashes` removes repeated networks and `PrioritizeNewMutants` controls mutation-cursor tie breaking. As in GeneSort, if strict sorted/length filtering would empty a pool, selection falls back to improving correctness before size. A pool can contain fewer members after duplicate filtering. Each model's prefix remains fixed during mutation and is skipped during evaluation.

`SnapshotInterval` and `SnapshotCount` are special SGD run properties, not defaults, query choices or sweep parameters. The interval is positive and locks after runParameters creation. The count is nonnegative and may only increase after parameter generation. Their product gives the target generation. SnapshotCount excludes generation zero: interval 100 and count 10 produce 11 snapshots at 0, 100, …, 1,000. Count zero saves only the initial population. Mutation uses `RngType`, `MutatorVariantKey` (V1 or V2), `SeedModificationRate`, `ModificationRate`, and normalized relative `OrthoRate` / `ParaRate` / `SelfSymRate` weights. Mutation indices advance for retained parents so later generations do not repeatedly generate the same child. `AdjustCeLengthFrequency` must be positive; `SortedFraction` is the fraction of successful expanded-pool members used to choose GeneSort's raw CE cutoff. These are separate from the model-generation success target.

MSUF4 creation uses `OrthoGenRate`, `ParaGenRate`, and `SelfSymGenRate` for the seed and every unfolding level. Standard SGD instead uses `OrthoRate`, `ParaRate`, and `SelfSymRate` as destination weights for each mutation draw. Let `W = OrthoRate + ParaRate + SelfSymRate`, and let `pO`, `pP`, and `pS` be those weights divided by `W`. Values must be finite and nonnegative, with at least one positive. Scaling all three weights together preserves their relative probabilities. `SelfSymRate` selects the internal `SelfRefl` mode.

For an entry with mutation-attempt probability `m`, a draw chooses Ortho with probability `m*pO`, Para with `m*pP`, SelfRefl with `m*pS`, or no action with `1-m`. The destination weights are the same for every current mode. Choosing the existing mode also leaves the entry unchanged, so its actual probability of changing is `m*(1-pCurrent)`. For example, weights `(OrthoRate, ParaRate, SelfSymRate) = (2, 1, 1)` with `m = 0.10` give draws of 5% Ortho, 2.5% Para, 2.5% SelfRefl, and 90% no action. An existing Ortho entry therefore stays Ortho 95% of the time and changes 5% of the time. A zero destination weight prevents drawing that destination, but existing entries in that mode can survive through no action.

Each generated suffix stage gets a separate draw for its four-channel seed and for every pair-mode entry at each unfolding level. Fixed prefix comparators and the number of suffix stages are preserved by mutation. The seed uses `m = SeedModificationRate` in both variants. With `L = log2(ChannelCount / 4)` unfolding levels numbered `i = 1..L`, V1 uses `m = ModificationRate` at every level. V2 uses `m = SeedModificationRate + (ModificationRate - SeedModificationRate) * i / L`; the last level reaches `ModificationRate`. Four-channel models have no unfolding levels. For example, at 32 channels (`L = 3`), seed rate 0.02 and modification rate 0.08 give V2 rates 0.02 for the seed, then 0.04, 0.06, and 0.08 for the unfolding levels. These probabilities apply per entry, not once to the whole model, stage, or level. Both modification rates default to zero, so the default mutator preserves all modes regardless of the three destination weights.

SGD prepares Boolean inputs with at least 512 tests as `Bitv512` once per invocation on vector-capable machines. The original test ID, duplicates, order, and saved input format are preserved. Independent mutations, network materialization, and evaluation use the invocation's worker budget in separate phases; generations remain ordered. MSUF4 and MSRS materialization expand only enough stages to satisfy the current suffix CE cutoff. These runtime optimizations preserve the generated models, evaluation counts, history, function versions, and output identities.

Scalar batches evaluate independent networks in parallel. SIMD batches choose network ownership when there are at least as many networks as test blocks, or when one worker is requested; otherwise they retain block parallelism. Network owners use ordinary private counters and one reusable work buffer across their test blocks, with no cross-worker counter merge. The block path retains worker-local counts and merges them after processing. Single-file results execution reuses its fully validated setup snapshot instead of deserializing it twice; batch preflight releases payloads to avoid retaining an entire sweep. See [evaluation benchmarks](../benchmarks/README.md) for measurement instructions and results.

Each invocation saves generation-zero and uniformly spaced `SorterPoolSet` checkpoints with both setup inputs as dependencies. Each contains the generation, test identity, models, evaluations, parent IDs, birthdays, mutation cursors and pool CE limits. The checkpoint at the current target is the final result; Summary.csv and Details.csv read only that checkpoint. SGD writes no separate final SorterModelSet or SorterSetEval. The copied source model set remains a required setup input.
Evolution retains and saves compact `sorterEvalV1` evaluations. These contain the scalar statistics used for selection, duplicate filtering, cutoff adjustment, and summaries; they omit per-comparator usage arrays. Existing V2 checkpoints are converted to V1 in memory when loaded and can still be resumed. Existing files are not rewritten automatically. New checkpoint bytes intentionally differ from V2 checkpoints while preserving model/member identities, scalar results, and resumed evolution.

For explicit detail requests, the library operation `StandardSgd.evaluateMemberDetails options tests snapshot poolIndex memberId` reevaluates one selected member against the checkpoint's original test inputs. It reconstructs prefix markers and used comparator counts through the saved last-used index, verifies all scalar metrics, and preserves the original evaluated-sorter identity. It returns V2 detail without inserting it into the population or checkpoint. This may be expensive for large test sets; it is not an automatic step during saving or listing files.

Select **Evolution reporting** in the run's **Reporting** group, after Setup and Results in Configuration. Set SnapshotInterval, SnapshotCount, and **Temp snapshot** here. Full checkpoints are always enabled for version-7 SGD. Pool summaries retain their independent schedule (constant, increasing or custom), which need not land on the final generation. Generation zero is included in both. The retained snapshot interval and summary schedule are frozen in each parameter file.

**Temp snapshot** is a positive generation interval, defaulting to 10 for new and older run definitions. It can change after parameter generation. Each parameter combination has one replaceable file in `data/results/temporarySnapshots`; its identity also includes the summary schedule. A temporary snapshot contains the full population, mutation cursors, evaluations, and pending pool-summary rows. Writes flush a staging file and atomically replace the previous temporary snapshot. At SnapshotInterval boundaries, the ordinary immutable snapshot and due summary batches are published, then the older temporary snapshot is retired. Temporary snapshots are not extra report outputs. Their short-lived staging files are ignored by progress reads and resumption.

Version-4 SGD parameter files freeze SnapshotInterval and the summary schedule. They read SnapshotCount and TempSnapshotInterval from the project-local `runs/<run-id>.msgpack`; copy this definition with the parameter files and setup/results data for portable execution. Changing the saved count or temporary interval leaves parameter bytes and work-item IDs unchanged. Checkpoint identities include algorithm parameters, setup dependencies and GenerationCurrent, never the target. Former final snapshots keep the same identities after extension. Summary batches contain at most 256 sampled generations and split at snapshot boundaries; keys also include the exact sampled generations. Normal checksums, atomic publication, completion checks and shared-data cleanup apply.

To extend a run, increase SnapshotCount, save, update progress and execute its parameter files in a terminal. Execution restores the newest usable temporary or retained checkpoint with complete preceding snapshots and summary batches, then continues using the saved population state and absolute generation numbers. Pending summaries are restored with a temporary snapshot so interrupted reporting intervals produce the same reports as uninterrupted execution. Missing earlier reporting files cause replay from an earlier retained checkpoint; damaged snapshots are reported instead of overwritten. Cancellation preserves published checkpoints. Tests compare snapshot and summary bytes against uninterrupted Random and Best runs. Pool expansion/cycling, SOSS and append/condense remain outside this fixed-pool workflow. Version-6 SGD execution is no longer supported. Older files are not automatically upgraded; create a new run using the current function and snapshot controls.

### Export sorter evaluation reports

On **Results execution**, choose a run filter, **Check all**, then **Export CSV reports** to aggregate an entire sweep. Checking individual rows exports just those combinations; **All runs** can combine multiple saved runs in the project. Completed branch parameter files with `SorterSetEval` or `SorterPoolSet` outputs are supported, including `sorter-eval.evaluate` and the MSUF4/MSRS Standard SGD functions. CSV files are written directly into the project's `data/results/reports` folder with stable names. SGD runs export only **EvolutionSummary.csv**; ordinary sorter evaluations export **Summary.csv** and **Details.csv**. Re-exporting replaces the previous selected export and removes obsolete generated report files, including **Snapshots.csv**, while preserving unrelated files. The export reads saved invocations, exact setup query headers and validated database results. It never generates models, runs setup, evaluates sorters, changes a cache identity, or reads current draft settings. Copied projects work without the original workspace or source projects.

**Summary.csv** has one row per results file. It includes evaluated and successful sorter counts, `ObservedSuccessFraction` (successful / evaluated), and minimum and median CE/stage lengths among successful sorters. Success means zero unsorted inputs in the associated saved test set. A nonempty evaluation with no successes has fraction zero and blank successful-length statistics. An empty evaluation has count zero and blank fraction, channel count, and length statistics. Observed success is separate from a requested model-generation success target. Evaluated stage/CE lengths describe the saved evaluation's used network; `SetupSuffixStages` and `ResultsSuffixStages` retain the separately recorded generation estimates.

**Details.csv** combines selected ordinary evaluation results into one table with one row per network per results file: sorter ID, test subset, actual saved evaluation variant, channel count, success, unsorted count, CE/stage length, sequence hash, last CE index, reflection symmetry, stage crossings, and reflective count. These are the `sorterEval.V1` statistics, also available from saved V2/V3 evaluations; large CE-use arrays and residual test payloads are not expanded into CSV cells. A network appearing in multiple combinations retains one row for each combination.

SGD exports create only **EvolutionSummary.csv**, with one row per sampled generation and pool: member/success counts and fraction, raw CE limit, minimum/mean/population standard deviation of CE and stage length, mean stage crossings, mean reflective fraction, mean unsorted count, mean/minimum selection score, and separate success/failure length histograms. These statistics describe the entire pool, matching GeneSort's summary semantics. Reflective fraction is blank if a member has zero CEs. The report retains saved mutation parameters and inherited setup query values. `ResultsDataId` and `ResultsFile` identify the final saved pools; no per-network CSV is created. The export reads saved summary batches without loading network snapshots. Full checkpoints remain in the database for inspection and continuation. Missing or damaged summary batches must be repaired/rerun before export. All report files are staged before replacing the previous export in the project reports folder.

`sgdPoolStatistics.SuccessfulLengthHistogram` and `UnsuccessfulLengthHistogram` store sparse two-dimensional histograms of `SorterEval.getCeLength` and `SorterEval.getStageLength`. Each `sorterLengthHistogramBin` contains `CeLength`, `StageLength`, and `Count`; exact integer coordinate pairs are sorted by CE length, then stage length, and zero-count bins are omitted. Saved MessagePack summary payloads encode each bin as a three-integer array in `[CeLength,StageLength,Count]` order, for example `[61,11,9]`, with no field names. The reader requires this numeric format; named-field bins are not migrated. Every pool member contributes once, including repeated networks. Success uses `SorterEval.getIsSorted` (zero unsorted inputs), independently of selection-score filtering. The respective counts sum to `SuccessfulCount` and `MemberCount - SuccessfulCount`. CSV columns with the same names contain the same compact triples as JSON, for example `[[45,12,7]]`. A recorded empty group is `Some [||]` and exports as `[]`. Missing histograms export as blank cells. Re-exporting a summary does not rewrite its saved payload.

All reports repeat the project/run/work-item IDs, exact result and setup data/query IDs, source file paths, saved results parameters, and inherited setup query values. Setup columns use `Setup.<datatype>[<label>].Query.<key>` (the bracketed label is omitted when empty), for example `Setup.SorterModelSet.Query.OrthoGenRate`. Results parameters use `Results.<key>`. Nonempty labels and key-name segments are percent-escaped, including periods, to prevent column collisions. Keys from different datatypes remain separate. Only saved query projections are reported as setup query values; unrecorded setup defaults are not reconstructed. Set numbers retain their saved zero-based indexing. Columns start with setup query values and results parameters, followed by metrics, then provenance. Each dynamic group has a stable ordinal order. Missing values are blank rather than zero.

The `Sortopia.Reporting` typed report model keeps integers, unsigned integers, floating-point values, booleans, identifiers, text, and missing values distinct until export. It rejects duplicate names, conflicting column types, unknown row columns, and nonfinite numbers. CSV uses comma delimiters, invariant numbers, UTF-8 with BOM, CRLF records, and quoted/escaped text, including embedded commas, tabs, quotes, and newlines. Formula-like text is prefixed with an apostrophe for spreadsheet opening; numeric negatives remain numbers. Use Excel **Data → From Text/CSV**, selecting comma and UTF-8. Keep identifier columns as text, especially when importing large unsigned integers; CSV cannot encode spreadsheet column types or Excel number precision. Fractions are emitted in the range 0–1 and can be formatted as percentages in Excel.

Export revalidates results against their exact planned keys and checks setup query references. Missing/corrupt files, incompatible invocations, and duplicate result selections fail the whole export. CSVs are fully staged before publication. Replacing existing report files uses a publication lock and rolls back on failure, such as a CSV held open in Excel. Unrelated files remain untouched. Evaluation payloads are processed one file at a time, and detail rows are streamed.

Stored setup/results data allows up to 1 GiB uncompressed per payload, supporting larger model sets such as 10,000 MSUF4 models at 895 suffix stages. The compressed file limit remains 256 MiB. Payload bounds and checksums are validated on read; the storage format and cache identities are unchanged.

### File-based data storage

`ISortopiaDb` provides `TryLoad`, `Load`, `FindResults`, and `GetOrCreate`. Each project stores immutable data at `data/{setup|results}/<sortopiaDataType-case>/<data-id>.msgpack`. Database names are logical identity scopes, not filesystem paths. Payloads use explicit versioned DTOs and MessagePack LZ4 block-array compression; envelopes contain full canonical keys and a SHA-256 integrity checksum. This uses existing dependencies, with no SQL database or separate mutable index.

`storedDataReference` carries `ProjectId`, `Id: Guid<sortopiaDataId>`, `QueryId: Guid<sortopiaQueryId>`, `Phase: runExecutionPhase`, and `DataType`. The distinct ID measures prevent mixing query and data identities in F#. The phase selects the `setup` or `results` folder; storage codecs convert it to and from their boolean `IsSetup` field.

Each setup or results output projects its parameter set onto its own entry in `DataTypes`. IDs also include the project ID, database, phase, exact data type/text, function name/version, and declared source-data dependencies. Canonical keys preserve value types, use ordinal key ordering, and are independent of culture and string formatting. Run IDs, execution IDs, and unselected parameters do not participate. Thus setup can reuse the same file when an unrelated span varies, including across runs and app restarts. Results retries also reuse existing outputs, but a single selected results batch must have distinct output owners. Results include only the setup references their function consumes; independent results generators do not duplicate their files when unrelated setup data changes.

**Query keys are a computation contract:** include every parameter that can vary and change that output. A missing selected key is an error; an empty key list intentionally creates one datum per remaining identity scope. The store cannot infer which parameters an arbitrary function uses. This is projection-based reuse, not global deduplication of identical bytes produced by different projects or different keys.

Source lookup uses the source project's fixed results database, function/version, exact data type/text and that output's **results** query keys, projected from the consumer's setup parameters. Execute source runs first. Missing, corrupt, or ambiguous source results stop execution with an error. If multiple upstream setup inputs yielded the same results query projection, lookup refuses to choose arbitrarily; the producer function's contract must distinguish those cases. The current codecs support `SortableTests`, `SorterModelSet`, `SorterSetEval`, `SorterPoolSet`, and `SorterPoolSummarySet`. Catalog declarations describe the primary outputs; configured sampling adds generation-specific outputs to the invocation plan. Other declarations produce a clear unsupported-type error.

Setup writers coordinate through a project-local file lock and check again after acquiring it, so concurrent setup creators invoke a shared factory once. Results writers generate independent outputs without that lock. The empty `.write.lock` file is coordination infrastructure, not a status marker; the active lock is its open file handle. Files are flushed to a temporary sibling and published without overwriting existing data. Readers ignore incomplete temporary files. Source lookup scans headers within the relevant data-type directory without an additional index. Corruption is reported instead of silently regenerating data. Failure, cancellation or a process crash retains already published outputs, which subsequent output checks and retries discover directly. Existing historical receipt files are ignored and left in place; new work never depends on them.

The initial codecs read whole objects and limit both files and uncompressed payloads to 256 MiB. This store is intended for a local workspace filesystem. Moving an existing project preserves its IDs and data. Importing a copy assigns new project IDs, so copied historical data retains its original identity and is not reused by the new project; executing the copy creates data in its new scope.

Prefixed model functions use the width and depth in `PrefixLibId`; uniform models use zero prefix stages. Defaults and run spans show the suggested suffix length, or a range across their combinations. These are provisional whole-network success targets assuming uniform, enabled entries; custom weights and SimpleR/SimpleS activation can change the actual success rate. See [stage-length methodology](stage-lengths.md). Each parameter set produces `SorterCount` models of the selected family. `Repl` selects the reproducible model-index batch starting at `Repl * SorterCount`. With all other inputs fixed, rerunning the same batch produces the same models, and increasing `Repl` selects the next batch. `RngType` selects the random generator; only the CE function accepts `ExcludeSelfCe`. Model-generation functions use version 2 or later for this changed parameter contract and call their model-specific initializers. MSUF4 version 3 replaces `Seed4Weights` and `UnfoldingWeights` with the three normalized float rates in both required inputs and model-output query projections, across Simple, SimpleR, and SimpleS. Saved sealed MSUF4 version-2 projects require a new project version for the new contract. MSUF4 version 7 renames the generation inputs and model-output query projections to `OrthoGenRate`, `ParaGenRate`, and `SelfSymGenRate`, retaining the version-6 suffix capacity and generation behavior. Each defaults to 1; finite nonnegative values are normalized together and at least one must be positive. `OrthoRate`, `ParaRate`, and `SelfSymRate` remain mutation-only inputs to Standard SGD. Existing saved data keeps its recorded keys; sealed model-generation projects from earlier versions require a new project version and the generation defaults, spans, and query keys must use the new names. The earlier correction from the unused `SelfSym` name to `SelfSymRate` remains the mutation key. Existing sealed version-1 projects retain their saved data and require a new project version to execute with the new parameter; old stage-length values are not reinterpreted as success fractions.

MSUF4 version 6 uses five times the original calculated suffix budget for every success target, keeping the version-3 parameter contract. For 16 channels with one prefix stage, the 50%/90%/99% budgets are now 435/675/895 stages. Other algorithms are unchanged. The new version prevents reuse of shorter cached models; existing generated files retain their lengths until regenerated using the current function version.

MSRS and MSUF6 weights are typed parameter values with named mode fields in the default and span editors. They must be finite and nonnegative, with at least one positive mode per distribution; zero excludes a mode. Each distribution normalizes independently. MSUF6 starts at width 6. For example, UF6 at width 24 needs two unfolding distributions, for 6 → 12 and 12 → 24. The MSUF6 seed and all per-level weights repeat unchanged in every generated stage. Add/remove MSUF6 unfolding levels in the editor; mismatched prefix widths and level counts block parameter generation and execution, but can be saved in a draft. Newly populated defaults use equal mode weights and enough unfolding levels for the selected prefix; fresh UF6 modules start with a 12-channel prefix. Existing inherited and local values are preserved. Values remain typed in parameter sets and round-trip in portable run-parameter files.

The prefix must exist in the catalog and its channel count must suit the function. `Msce` and `Mssi` support every currently cataloged prefix width; `Msrs` requires an even width; `Msuf4` requires a power of two of at least 4; `Msuf6` requires 6 times a power of two (6, 12, 24, 48, ...). For example, Prefix1 at width 16 works with `Msuf4`, while width 24 works with `Msuf6`. Validation covers inherited defaults and every span value. All prefix/weight combinations in a run's Cartesian product must be compatible. MSUF6 needs separate runs for widths requiring different unfolding-level counts; MSUF4 derives each combination's levels automatically and supports mixed-width spans.

Supply fixed inputs as module/project defaults and varying inputs as explicit run spans. Select the desired query keys from those spans for the `SorterModelSet` output, for example `PrefixLibId`, `Repl`, and (for SimpleR) `AInitial` when they vary and should produce separate files. Defaults remain defaults. The root run needs no setup phase or source project; it supports both direct Execute and generating portable run-parameter files. Results are saved under `data/results/SorterModelSet` and reused using the configured query projection.

The inspector scrolls through the full form; the resulting full path is displayed read-only under **Location**. Selecting another tree item returns the inspector to the top. Configuration issues stay visible beside Save and in the affected editors. Save workspace preserves incomplete or invalid configuration, including unfinished parameter text, in the normal GUID-named MessagePack files. Saved drafts reopen with the same issues and do not trigger an unsaved-changes prompt merely because they are invalid. Names, folder locations, hierarchy references, and file access must still be valid for a save to succeed; failures keep the unsaved edits open and explain the cause.

Changing module settings updates descendant modules and draft projects that inherit each property. Saving leaves projects editable. Generating run parameters seals the effective project settings before the first setup or parameter-file write, then locks that project and every ancestor module while generated parameter files exist. Names, functions, defaults, sources, and query choices remain read-only. Sibling runs and projects keep shared ancestors locked until their last files are removed. In **Run parameter files**, **Remove files** deletes the selected run's parameter files and setup/results data no longer used by remaining generated files; shared data is retained. Removing a run performs the same cleanup when **Save workspace** commits the removal. Failed removals restore both files and settings. Removing the last files clears the project's data cache and automatically restores editing, keeping run inputs and the original inheritance/overrides. Refreshing also detects externally removed files. Existing runs retain their parent project ID.

## Types and persistence

`WorkspaceDocument`, `ModuleDocument`, and `ProjectDocument` in `Sortopia.Workspaces.Serialization` are the single workspace hierarchy. A module holds child documents; a project holds raw run inputs. Typed configuration is resolved separately when needed: modules use `moduleConfiguration`, with results settings and `Setup: moduleSetupConfig option`; projects use `projectConfiguration`, with Results and an optional Setup block. Setup absence identifies a root; a present block identifies a branch, including a draft whose setup function is not yet selected. `HasSetup` is derived from this block. Document validation rejects mismatched families between parent modules, child modules, and projects; run construction rejects a setup-phase mismatch with its parent snapshot. The workspace can contain both families, and the UI retains its root/branch labels. Documents are editable; explicit cloning supplies independent copies and save baselines.

Each document has a `WorkspaceDefinition`, `ModuleDefinition`, or `ProjectDefinition` containing only its own values. These definitions contain neither schema versions nor child-reference arrays. `WorkspaceDocument.workspaceFile`, `moduleFile`, and `projectFile` project the current document into the existing shallow file DTOs, deriving ordered references from its children. File loading validates versions, references, filenames, and folders before assembling documents. Renames, additions, removals, and reordering therefore require no separate reference synchronization in memory. The persisted format and folder layout remain unchanged.

Module local settings use one `moduleOverrides` record, with setup-specific function, source, default, and exclusion overrides grouped in `Setup: moduleSetupOverrides option`. This block is present exactly when the inherited module configuration has setup; its fields can all be inherited. `ModuleDefaults.resolve` handles both families directly, and `ModuleDefaults.toProject` supplies project defaults without module-owned query projections. The editor refreshes inherited settings in descendant documents when module values change, while sealed projects keep their captured configuration. Serialization derives the optional setup blocks from the entity family, preserving unfinished branches even when every setup field is empty.

Project settings resolve to a `projectConfiguration` using one `projectLocalSettings` record. Setup settings are grouped in `Setup: projectSetupSettings option`, present exactly when the project has setup. Database names and per-output query selections are ordinary project-owned values, with no inheritance state. `ProjectResolution.initial` starts each project with its own database names and empty query selections for the selected functions. Descriptions, parameter defaults, exclusions, and source selections retain their inheritance behavior, including explicit empty descriptions. `ProjectResolution.resolve` combines local settings with module defaults in one path for both families. `ConfigurationInheritance.mergeParameterDefaults` replaces matching keys, retains other inherited bindings in order, and appends new local keys. Both `None` and `Some []` inherit parameter defaults; duplicate keys within a local list are invalid, and exclusions remove inherited keys. Setup sources merge independently by exact data type through `ConfigurationInheritance.mergeSources`; an explicit empty project ID masks an ancestor choice, while an omitted source inherits. `WorkspaceDefinitionResolution.projectConfiguration` resolves draft settings against supplied or captured parent defaults and reads sealed settings directly from their snapshot. Its module counterpart resolves module configurations and overrides without constructing a typed hierarchy.

The shared editor loads and saves module and project document definitions directly. Shared helpers handle descriptions, defaults, exclusions, and source choices without converting modules through project DTOs. Database-name controls use a project field with no override state; runs display their project’s values. Sealing locks these fields, and resuming restores the retained local settings.

`Run.create snapshot inputs` constructs the unified `run` from an immutable `projectSnapshot` and `runConfig`. The snapshot contains only the project's ID, name, and fixed configuration; it has no editing state or sibling runs. Inputs contain Id, RunName, ParentProjectId, DescriptionOverride, ResultsParameterSpans, optional SetupParameterSpans, and reporting/SGD controls. `SetupParameterSpans = None` means no setup phase; `Some []` means setup with fixed inputs and no query spans. Run construction rejects any mismatch with the project's setup phase. Functions, database names, defaults, and query projections remain in the captured project settings. `WorkspaceDefinitionResolution.projectSnapshot` prepares a candidate snapshot without mutating the draft, and `RunDto.toDomain` decodes run inputs against that snapshot. Attaching run inputs with `WorkspaceDocument.withRuns` leaves the document's lifecycle state unchanged. Generation seals the project in the document before writing generated files, retaining editing settings and every sibling run. A run retains its inputs in `Configuration`, fixed settings in `ProjectConfiguration`, and any resolved source snapshots in `ResolvedSources`, so queries need no further workspace lookup. Existing generation, locking, and resume-editing behavior is unchanged.

The four shared names have distinct UMX tags: `resultsDatabaseName`, `resultsFunctionName`, `setupDatabaseName`, and `setupFunctionName`. Shared configuration is factored into `resultsConfig` and `setupConfig`. A `setupDataTypeConfig` contains `DataType: sortopiaDataType`, `SourceProjectId: Guid<projectId>`, and `QueryParameterKeys: string<paramKeyName> list`. `setupConfig.DataTypes` is the ordered list; its `SortopiaDataTypes`, `SourceProjectIds`, and `QueryParameterKeys` views derive from those entries. Results query keys remain one list.

`WorkspaceDocumentIndex` provides operation-local navigation by entity ID and relative folder. Opening and saving validate the document structure without resolving all runs. For execution, `RunExecutionScope.create run locations` takes its parent from `run.Parent`, checks the location contracts, and uses `RunSources.resolveFor` to resolve only the required source results contracts. Runtime snapshots contain no sealing flags: document resolution requires source projects to be sealed, while the selected parent may still be a candidate snapshot that generation seals before writes. Source locations contain only results snapshots and relative folders. `QueryParams.forSource` uses the source project's ID, results database, and results query keys. `forSetup` uses the parent project's ID, effective setup database, and the selected entry's query keys; `forResults` uses the parent project's results metadata. Query IDs use the stable project ID, exact type/text pair, and selected parameter strings, rather than the display name.

`sortopiaDataType` is a discriminated union with ten cases: `Workspace`, `Run`, `WorkspaceModule`, `RunParameters`, `SorterPoolSet`, `SorterSet`, `SorterModelSet`, `SortableTests`, `SorterSetEval`, and `TextReport`. Every case carries a free-form `string`; empty strings, whitespace, Unicode, and line breaks are preserved. Execution and setup output lists use this type, as do result and setup queries. Each output row has a case selector and a text field. Lists can contain the same case with different text; an identical case/text pair cannot appear twice. Inherited lists show both values and retain their clickable source. Query matching and query IDs include both the case and the exact text.

`parameterBinding` is the general pairing of a `string<paramKeyName>` with a typed `parameterValue`. It can represent a supplied parameter, a default, or an override; the containing property or operation determines its role. `ParameterBinding.create key value` constructs a binding from a typed key, `fromValue name value` accepts an already typed union value, and `fromText name kind text` validates editor or persisted input. All constructors enforce the known key's type and valid values. `ParameterBinding.validateUnique` validates collections with one binding per key. `parameterBindingDto` and `WorkspaceParameterBinding` provide the corresponding storage and editor representations.

`parameterSet` stores a `Map<string<paramKeyName>, parameterBinding>` exposed by `ParamMap`. `parameterSet.fromBindings bindings` creates a set directly; `parameterSet.create map` accepts a typed map and validates that each key matches its binding. `set.WithBinding(binding)` adds or replaces a binding while preserving the original set. `WithValue` accepts a typed key/value or a key name with a `parameterValue`; `None` removes the key. Binding construction, validation, and set updates retain the typed values without formatting or reparsing them.

`set.TryFind(name)` returns a binding. `set.TryFind(typedKey)` reads the underlying CLR value directly, returning `None` for a missing key or mismatched type; numeric-looking text remains text. String conversion is explicit: `TryFindText(name)` formats one value, and `ToStringMap()` projects the whole set to canonical invariant strings. Queries format only their selected keys; DTO serialization formats bindings at the storage boundary. Library IDs remain typed through bindings, parameter sets, and catalog function calls. File-store identity uses their type tags and stable field bytes, so alternate input formatting produces the same data ID.

`ParameterSets.create bindings spans` expands bindings and spans into `parameterSet[]`. It parses span text using the matching binding's type or the known key's type, and stores each candidate as a typed binding. Matching spans replace bindings and other bindings remain fixed. Combinations exceeding the maximum .NET array length are rejected before allocation.

`ParameterSets.preview maxCount bindings spans` shares the same validation and combination generator, materializing only the requested prefix. All candidate values are validated, including values beyond the visible rows. The editor retains typed parameter sets and formats values only for display.

`RunParameterSets.create run` returns a `runParameterSets` record with `Results: parameterSet array` and `Setup: parameterSet array option`. Root runs return `Setup = None`; branch runs return `Some setupSets`. Results and setup combinations are expanded independently from their respective defaults and spans, retaining typed bindings. No spans is valid only when there are no output query keys and the defaults satisfy the required inputs. The function uses the run's resolved settings and does not need a workspace lookup.

`ResultsParameterDefaults` is a `parameterBinding list` on modules, projects, and runs. Projects and runs expose setup defaults through their optional Setup configuration; the run's `SetupParameterDefaults` convenience property is also optional. Defaults merge by key through modules and draft projects. Runs receive the sealed project's resolved defaults, while spans supply the disjoint project query keys. `Run.makeResultsParameterSets` and `Run.makeSetupParameterSets` use the general binding APIs; requesting setup sets for a root run is rejected. `ParamKeys.all` supplies metadata derived from the typed key declarations.

Every entity has a UMX-tagged GUID ID: `workspaceId`, `moduleId`, `projectId`, or `runId`. Its definition filename is `<id>.msgpack`. IDs survive edits, moves, and missing-file restoration. Only the workspace retains a separate root folder name. Modules and projects use their entity names as folder segments. The absolute workspace location stays in application settings, outside the definitions.

Names must be nonblank. Sibling module and project names share one namespace and must be distinct ignoring case; sibling run names must also be distinct. Module, project and run IDs must each be unique within their entity kind throughout the workspace. Rejected edits remain visible for correction while the tree keeps the last accepted value; Save is disabled until corrected. Saved names stay reserved until their removal or rename has been saved.

Workspace, module and project files use schema version **22** through `WorkspaceDefinitionCodec`. Workspace and module child references contain only `{ id, name }`, where `name` is the child entity name and its single relative directory segment directly under the parent. Module/project definitions store their names once, without a separate `folderName`. Separate module/project reference arrays identify the type without extra directories. Project run references are ordered GUID arrays addressing `runs/<id>.msgpack`. When opening or importing modules/projects, their containing folder names must match the entity names. IDs are checked against both the referenced ID and the definition filename; duplicate IDs, duplicate sibling folders, invalid family relationships and escaping paths are rejected. Loading follows references rather than directory enumeration, preserving saved order and keeping removed-but-retained entities out of the loaded tree. Missing children are reported with their ID and location; there is no embedded descendant snapshot to fall back to when reopening.

Modules persist local overrides and **captured parent defaults**, without an additional copy of their own effective configuration. Project definitions have one explicit `Draft` or `Sealed` state. The draft case contains `localSettings`, captured parent defaults, and their origin, including inherited function selections. The sealed case contains the execution snapshot and optional retained editing settings; sealed status is derived from this case rather than stored separately. Local settings contain the project-owned database names and query selections alongside overrides for inherited values. `inheritedFrom` records the immediate parent module's ID and name for captured context. These defaults are captured *before* local overrides, including values currently hidden by a local override. Removing a local override from a detached entity therefore restores the original parent value. Captures refresh when ancestor defaults change even if the child's effective value is unchanged. Attached entities resolve against the actual parent; `LoadModuleDocument` and `LoadProjectDocument` preserve this captured context for detached editing. `WorkspaceDefinitionResolution` parses and validates typed module/project settings at explicit boundaries, without converting descendants or run inputs. Attaching/importing into a workspace resumes normal inheritance from the destination parent. Sealed projects store their complete fixed configuration and run references, without redundant inherited context. Programmatically constructed sealed snapshots can omit retained editing settings; their existing explicit resume action reconstructs local settings and exclusions from the snapshot. When sealing an editable document, its original `localSettings` are retained for resuming editing, including excluded draft values and inheritance choices. Captured context makes configuration portable; it does not copy external source-project data or executor code.

Run files use schema version **18**: IDs, optional description override and spans, with no folder or database overrides. `WorkspaceRunDocument.resolveByRunId document runId` resolves the selected saved run, parent snapshot, and required source snapshots; `RunCodec.decodeRun snapshot bytes` decodes standalone run inputs against an already resolved `projectSnapshot`. Run-parameter payloads use schema version **2**; their stage-length display uses only the recorded values. Unsupported run-parameter versions must be regenerated. There is no separate aggregate DTO or aggregate codec: `WorkspaceDocument` supplies the editable hierarchy, and file DTOs are its shallow persistence projections. Module settings contain functions, defaults, descriptions, and source assignments, with no output/query projections. Only the current entity schemas are supported; older definitions are rejected without modification and must be recreated. No migration layer is retained.

Saving compares definition files against the fingerprints held by `SavedWorkspace`, so edits to any referenced definition—including captured values hidden by live inheritance—cannot be silently overwritten. No tracking file is added. A cloned edit retains the same concurrency protection because the saved handle is passed explicitly. An already-open workspace can explicitly restore missing definitions from its saved revision; surviving files still must match its fingerprints. A run-input-only edit writes its run file without rewriting project, module or workspace files. Transactional rollback and folder moves continue to cover the separate definition files.

### Configurable query projections

Select the project and open Results outputs or Setup outputs to choose query keys before creating runs. Available choices come from the phase's required function inputs; source-dependent setup outputs additionally restrict choices to their source's results query keys. For a fixed parameter, expand **Fixed parameters** and choose **Use as query key**, or exclude its default manually before selecting it. Each output can use a different subset. Runs inherit these selections and must supply exactly their union for each phase, with one span per key and at least one value per span. All other required parameters need fixed project or inherited module defaults. New and existing runs automatically gain empty rows for newly selected keys. Keys and required rows cannot be renamed or removed on the run. Empty query selections are valid when all required inputs have defaults. Incomplete drafts can be saved, but missing values, missing defaults, and undeclared spans block parameter generation. Existing span values are preserved when a project query key is deselected so they can be corrected explicitly.

Query keys control reuse: only an output's selected parameter values, the project/function/output identity, and declared input data references distinguish that output. A run can vary a parameter only when at least one output in that phase declares it as a query key. Each output must include the keys that distinguish its results; other outputs can omit those keys to reuse their data across those values. With an empty projection, an output is shared for the same input references. The selections are frozen with the project, included in portable runParameters files, and used for source-project lookup and output-completion checks.

The derived phase parameter contract contains required keys, per-output projections, their span-key union, and required fixed-default keys. Shared structured diagnostics drive runtime input checks, the coverage checklist, and the function grid. The contract is recomputed from existing settings, so no additional persisted schema is introduced. Editing a run's values refreshes that run's state without rebuilding sibling query choices.
