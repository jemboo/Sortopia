# Workspaces

Open **Workspace** from the home page and choose a root folder. Enter a workspace name and choose **Save workspace** to create it. Selecting a folder only remembers the location; an existing workspace loads automatically. Names, hierarchy edits, imports, and moves remain in the draft until saved. **Discard changes** restores the last saved state without changing disk contents.

## Persistence boundary

`Sortopia.Workspaces.Persistence` is an F# library that owns workspace filesystem operations and targets plain .NET 10. It references the F# serialization library, with no WPF dependency or additional third-party packages. `WorkspaceFileStore` provides the public API for loading definitions and committing saves, copies, and moves. Internally, `WorkspaceDisk` loads and fingerprints the hierarchy, `WorkspaceSavePlan` prepares immutable write plans and remaps IDs, and `WorkspaceCommit` stages and applies transactions with rollback. `WorkspaceDefinitionFiles` locates GUID-named files. The MessagePack schema and folder layout are unchanged by the library extraction and F# conversion.

`WorkspaceImport.PrepareModule` and `PrepareProject` return the loaded definition and a deferred `WorkspaceFolderCopy`. Copies receive new entity IDs, with internal source-project references and run parents remapped together; attaching in place keeps the IDs and returns no copy. Preparation does not write files. Pass the returned copy to `CreateWorkspace` or `SaveWorkspace` to commit it. `PrepareChild` and `WithExclusions` support moving a child out of a pending import while preserving its allocated IDs. Saves return the final definition in `WorkspaceSaveResult`; callers should keep that as the next saved baseline.

WPF owns folder dialogs, remembered folder preferences, draft editing, progress, and error presentation. It calls the persistence library for storage operations. `Sortopia.Workspaces.Serialization` continues to own DTOs and MessagePack encoding, and `Sortopia.FileDb` owns execution data and prepared work items. The independent `Sortopia.Workspaces.Persistence.Tests` project exercises workspace storage without the Windows desktop runtime.

## Root and branch hierarchies

A workspace can contain both root and branch modules. Each module and all its descendants use one type:

| Container | Allowed children |
| --- | --- |
| Workspace | Root modules and branch modules |
| Root module | Root modules and root projects |
| Branch module | Branch modules and branch projects |
| Root project | Root runs |
| Branch project | Branch runs |
| Run | None |

Root runs execute without a setup step. Branch runs have separate setup and execution settings. Projects contain runs only; use nested modules to organize projects.

Module and project folders sit directly inside their parent folder. Modules may contain both types together, but their folder names must be unique across both collections, ignoring case. For example, results can live at `C:\GuiSpace\SortableTests\Prefix\SmallCC\data\results\SortableTests`. The `runs`, `runParameters`, and `data` directories inside projects are unchanged. Folder names beginning with `.sortopia-` are reserved for transaction staging.

Opening a workspace in the previous version-15 layout offers **Convert folder layout**. Opening alone does not change files. Conversion validates the hierarchy and destinations, moves the referenced folders, and updates workspace/module/project definitions to version 16 using the existing save transaction. IDs, sealed configurations, run files, run parameters, setup data, and results are preserved. Name collisions or occupied destinations stop conversion; a failed transaction restores the previous folders and definitions. Obsolete empty containers are removed; unlisted folders and user files are retained. The API is `WorkspaceFileStore.ConvertFolderLayout(root, token)`.

Select the workspace to choose **New root module** or **New branch module**. Inside a module, creation buttons name the matching type, such as **New branch module** and **New branch project**. Inside a project, **New root run** or **New branch run** creates the correct run type automatically. The tree identifies each item's type with text and color; the hint above it explains the selected item's allowed children. Types are fixed when created.

The inspector edits display names and module/project folder names while the entity is editable. A sealed project keeps its name, folder name, and configuration. New folder names follow their display names until saved or manually edited. A module saved with its generated placeholder name (`New module`, `New module 2`, etc.) still uses its first entered name for its folder. After saving a named module, display-name edits keep the folder name fixed. Names may be descriptive, such as `Search: prefixes`, while folder names must be portable directory segments, such as `prefix-search`.

Runs have no folder name. A run is stored directly as `runs/<run-id>.msgpack`. The **Full path** field shows the selected folder or run file and supports text selection/copy. **Open folder** opens that folder, or the containing `runs` directory for a run.

## Module defaults, project defaults, and run inputs

Defaults begin on top-level modules; the workspace itself has no configuration defaults. Root modules supply Description, ResultsFunctionName, ResultsSortopiaDataTypes, and ResultsParameterDefaults. Projects choose query keys separately for each output. Branch modules and projects also share SetupFunctionName, SetupDataTypes, and SetupParameterDefaults. Database names belong only to projects: each root project defines ResultsDatabaseName, and each branch project defines both ResultsDatabaseName and SetupDatabaseName. These are direct fields with initial values `Results` and `Setup`, with no inheritance toggle. Modules have no database properties, and runs display their project’s database names as read-only values with a link to that project. Each resolved setup data-type entry combines its exact type/text pair, SourceProjectId, and its own QueryParameterKeys. Editable overrides contain only source assignments (`setupSources`: exact data type and project ID), descriptions, and parameter defaults; projects also own database names and modules own function selections. Output types are fixed by the function. Projects own editable per-output query selections (resultsQueries and setupQueries), and module/project overrides can exclude inherited defaults by key. The three logical views (setup types, source IDs, and query-key map) are derived from this single list.

Each property follows the nearest ancestor with a local override. The inspector displays its effective value and the name of the ancestor supplying it. Click an **Inherited from [ancestor name]** link to select the module or project defining that property. Check **Override on this module** or **Override on this project** to edit a local value; uncheck it to restore inheritance. Modules and projects inherit shared properties. Function selections are defined only on modules; project and run inspectors show them read-only. Database names remain project-owned. With no ancestor override, descriptions and lists are empty and function names are unset. Organizational modules can leave functions unset; projects need resolved, nonblank database and function names before saving.

Selecting a catalog function fixes its required parameters and saved data types, including each case's string. The inspector displays these contracts read-only. Follow the value-source link to the module defining the function. Projects choose source projects for source-dependent setup outputs and query-key subsets for each output. They cannot change the function's required inputs or output types/strings. Each phase's default and span key dropdowns contain only that function's explicitly declared required parameters. Defaults may supply some of these values at a module or project; runs must supply exactly all required keys through inherited defaults and local spans, with every output query key explicitly present in the spans. An explicitly blank description overrides its parent. Turning a local default override off and back on preserves its draft during the current edit session.

Select a run to edit its description and execution parameters. Branch runs have separate setup parameters. Functions and database names always come from the project. Before the first save, functions follow the draft project’s inherited module selections; after sealing, runs use the project’s fixed snapshot. Only the description has an optional per-run override; an explicitly blank description is allowed.

The run's execution settings and output types are inherited. Query selections belong to the project and can be edited from the project or a draft run until the first run is saved. **Edit parent defaults** selects the containing project or module, and is available even while a required inherited value is missing. Run type and parent ID come from the containing project. Data types persist as case/text pairs. There is no JSON editor.

Run **Required parameters and spans** editors show a separate coverage checklist for setup and results: supplied by default (with its value and source link), supplied by an explicit span, or still needing span input. Empty or invalid spans and default/span conflicts stay visible as issues. The same editor provides **output query projections**, with one checkbox list per produced data type. Only that phase's explicitly entered span keys can be selected; defaults never become query keys. Review these selections before saving the first run, which seals the project.

For example, a prefix-tests root run can inherit `SortableDataFormat = Bools`, enter `PrefixLibId` values for 16 and 18 channels in a results span, and select only `PrefixLibId` for the `SortableTests` result projection. The two prefix IDs then identify two result files. Selecting no query keys intentionally makes both parameter sets share one output (for the same project and input data); the editor highlights this consequence. Setup projections follow the same rule independently for each setup output.


On a module, open **Results parameter defaults** or **Setup parameter defaults** and choose **Add missing required defaults**. The action adds typed entries for the selected function's required keys that have no inherited or local default. Existing entries and their values stay intact, including incomplete edits, and inherited entries remain inherited. New entries use suggested starting values: 8 channels, 1 stage, 100 sorters, replication 0, self-comparisons excluded, test collection off, `Bools`, `Mssi`, `SplitMix64`, and evaluator `V1`. Channel count follows an existing count or library ID in that phase, then the other phase, before falling back to 8. Library IDs prefer available entries at that width, with a one-stage prefix and a two-way merge where available; if that width has no catalog entry, an available 8-channel entry is used. Review the new values using the usual typed editors and validation. Repeating the action does not duplicate entries; it is disabled when all required keys already have entries or no catalog function is selected.

Use **Add default parameter** on a project or module to supply one typed value per key. Once a catalog function is selected, the key picker contains exactly its required parameters and cannot accept other keys. Each descriptor supplies its value type. Choose the function before editing defaults. The function descriptors determine the available keys and their types; arbitrary custom keys are not offered by these editors. Parameter bindings still support text, integer, unsigned 64-bit integer, floating point, Boolean, GUID, sorter library ID, prefix library ID, and merge library ID at the domain level. Defaults use the same key-specific editors and validation as run spans, including catalog value dropdowns and numeric limits. Boolean values use a True/False selector. Numeric and GUID fields retain invalid drafts and show validation errors. Numbers use invariant formatting, floating values must be finite, and integer bounds are checked. Unconstrained text preserves spaces, commas, Unicode, line breaks, and blank values. Changing a default's key preserves its value and revalidates it. Invalid local or inherited defaults appear in the save explanation and block the affected run preview until corrected; **Override here** uses the same editor for local overrides.

`SorterLibId`, `PrefixLibId`, and `MergeLibId` are distinct typed parameter values backed by the existing catalog ID records. Their shared editor is used for module/project defaults, run spans. Choose a catalog entry to populate its fields, or enter channel count and variant directly. Prefix IDs also require a positive stage length; merge IDs require a positive merge dimension that divides the channel count exactly. Merge catalog suggestions update with the channel count. Invalid field drafts and incompatible values retained after a type change remain visible and block saving. A structurally valid ID may have no catalog entry; lookup availability is checked by the function using it.

Parameter defaults inherit **by key**. A child adding `StageLength = 1` keeps its parent's `ChannelCount = 16`; a child setting `ChannelCount = 8` replaces only that key. Results and setup defaults merge independently. The inspector shows inherited defaults alongside local defaults, with a clickable source for each inherited value. Choose **Override here** to copy just that key into a local editor. Removing a local row restores its inherited value, if any. An empty local list inherits all parent defaults. Only local bindings are saved as overrides, so other inherited values continue to follow ancestor edits until a project is sealed.

Runs receive the resolved default lists from their parent project. Use **Add parameter** to add a span of candidate values, or **Add missing span rows** to create empty rows for missing query spans and required inputs that have neither a default nor a span. Every output query key requires an explicitly entered span, including fixed values. A default alone never satisfies a query key. Results and setup span pickers use their respective functions’ required keys, excluding keys already supplied by defaults. Spans carry their own declared value type, including when no default exists. Values use that type for editing, validation, serialization, and parameter-set generation. Unsupported keys, missing required inputs, and missing query spans block saving, previews, and Execute. The shared rule is `default keys ∪ span keys = required keys`, with `default keys ∩ span keys = ∅` and `query keys ⊆ explicit span keys`, independently for setup and results.

Selecting a key chooses its editor and validation. Booleans use True/False; data formats, RNG types, model types and evaluator types offer value dropdowns using their domain parsers. Numeric fields retain invariant numeric validation; ChannelCount and SorterCount must be at least 1, while StageLength and Repl may be 0 unless the selected function imposes a stricter limit. GUIDs and free-form text retain their respective editors. Library IDs use structured editors as described below. Functions can provide cross-parameter validation: the five `sorter-model-set.prefix.*` functions check prefix availability, algorithm compatibility, unfolding-level counts, and numeric limits in module/project defaults, run previews, saving, and execution. All span values are checked, including those beyond the preview limit. Changing the key preserves entered values and immediately flags incompatible ones. Each span needs at least one value; blank values are valid for unconstrained text or an empty unfolding list at the seed width. Errors identify the key, clear the affected parameter-set preview, and block Save and Execute until corrected. Results and setup span editors use the same rules, with independent inherited defaults. **Discard changes** also clears invalid field edits.

Use **Exclude default here** on a module or project to stop inheriting that key. Exclusions persist separately from local values, so ancestor changes cannot restore an excluded default. The exclusion list lets you restore inheritance. Defaults are never copied or moved into spans. Enter span values separately for required parameters without defaults; adding missing span rows leaves their values empty. Project defaults cannot change after the project is sealed.

Parameter sets contain all combinations of the run's span values, combined with its disjoint fixed defaults. Defaults ChannelCount = 8 and a Repl span of 11, 13 produce {ChannelCount = 8, Repl = 11} and {ChannelCount = 8, Repl = 13}. Putting Repl in both lists is an error. With no spans, one set contains the defaults, provided they satisfy the function's required inputs and there are no selected query keys. Branch setup and results sets are generated independently.

Run editors show a **Results parameter sets** table; branch runs also show a separate **Setup parameter sets** table. Each row is a generated combination in execution order, using the effective inherited defaults and local spans. Column headers show the key, type, and whether the value comes from a default or a run span. Previews update with edits, show the first 50 combinations and total count, and never allocate the full product just to display it. Invalid parameters or missing required query values replace the affected preview with an error. An empty input produces one empty set. Previewing does not execute the run.

The workspace has three resizable columns: the hierarchy, a compact read-only configuration summary, and the editor for the selected setting. Drag either divider, or focus it and use the arrow keys, to adjust the widths. The summary shows current values, inherited/local/fixed state, validation issues, and run execution status. Select a setting’s linked descriptor to open just that setting on the right. Source links select the defining module or project and keep the same setting open. Save-error links open the corresponding setting directly. Each entity remembers its selected setting while navigating the current draft. Parameter lists, setup outputs, generated-set previews, and execution reports remain grouped as individual items; edits update the summary without discarding drafts. Each column scrolls independently.

Module editing starts with **Choose functions**, before defaults or outputs appear in the configuration summary. Root modules choose a results function that works without setup data. Branch modules choose a setup function first; the results picker then lists only functions whose input types that setup supplies. Inherited function selections count as chosen. Both selectors share one editor, with setup above results. Defaults, outputs, and source choices appear only once the function selection is complete and compatible. Name, location, and description remain available throughout.

Project and run editors start with **Inherited functions**, showing setup first for branch hierarchies. Function names are read-only, with source links to the defining module or sealed project. Defaults, spans, outputs, and source settings appear only when the inherited functions are available and compatible. Database names, description, and identity remain accessible while functions need attention. Project default pickers and run span pickers list only their phase’s required keys. Output cards show each function’s fixed types and the project’s chosen query projections. Projects choose compatible source projects only for source-dependent setup outputs; runs display those choices read-only. Sealed projects and their runs keep their saved function contracts when an ancestor changes.

Setup and results functions have separate catalogs and hierarchical name selectors on modules only. Open the selector and expand the dot-separated parts, for example `sorter-model-set` → `uniform` → `mssi`. Browsing groups does not change the configured function: choose a complete name with **Choose function**, Enter, or a double-click. Escape or Cancel keeps the previous selection. The full name stays visible; reopening expands its path. Highlighting a complete function shows its description, required parameter names and value types, and exact output SortopiaDataTypes (including their text) beside the hierarchy. The preview reads the catalog contract for that phase and updates before choosing; group nodes clear it. Long parameter lists can be scrolled without changing the selection. Enable a local override to choose a function; inherited and sealed values remain read-only and retain their source links. Results choices come from `ResultsFunctionCatalog.functions`, and setup choices come from `SetupFunctionCatalog.functions`. Changing a function refreshes its output contracts and allowed parameter keys. When a child module selects a different function, it inherits only compatible defaults. Module defaults for other functions are retained only in the editing session: they are hidden, excluded from the effective configuration and saved overrides, and restored if you switch back. Compatible local values and inherited sources stay intact. Draft project defaults and run spans follow the same rule: entries outside the inherited function’s required keys are kept only in the editing session, hidden from the active editor, and excluded from previews and saved inputs. Restoring the function restores those entries. Incomplete or invalid values for allowed keys remain visible and block saving. Upstream source query keys must also be within the setup function's required parameters. The inspector reports incompatible setup/results selections: evaluator functions need a branch setup that provides their exact input types.

The catalogs are plain immutable maps in `Sortopia.Functions`, keyed by `string<resultsFunctionName>` and `string<setupFunctionName>`. `ResultsFunctionNames` and `SetupFunctionNames` hold the typed name variables. Each `functionDefinition` explicitly declares `RequiredParameters: paramKeyDescriptor list` and `DataTypes: Map<sortopiaDataType, string<paramKeyName> list>` alongside its independent `Execute` implementation. Parameter descriptors define the types once. The catalog DataTypes map describes the parameters contributing to each output; it does not fix project query keys. Each project query projection selects a subset of the phase’s required keys; required parameters need not occur in any query projection. Duplicate required keys, duplicate query keys, and query keys outside the required contract are rejected. Both `setupConfig.DataTypes` and `resultsConfig.DataTypes` expose the corresponding exact type-to-key maps. `SetupSortopiaDataTypes` and `ResultsSortopiaDataTypes` are their keys; `ResultsQueryParameterKeys` remains a convenience union, never a shared projection for all result files. Current function labels are empty strings, fixed by their definitions.

Define a function with `FunctionDefinition.results` or `FunctionDefinition.setup`, passing an explicit semantic version such as `"1"`, followed by the required typed descriptors via `ParamKey.describe` separately from each saved type and its query-key names, then add its name/definition pair to `ResultsFunctionCatalog.fs` or `SetupFunctionCatalog.fs`, respectively. Attach a description to each definition with `FunctionDefinition.describe`; it is display metadata and does not change saved data identities or require a function version change. Both catalogs remain simple, independent name-to-function maps; dot-separated groups are built by the UI. Use `setupWithSources` for outputs that consume matching source-project data, and `resultsWithInputs` for results that consume setup data. These constructors take an explicit list of `(output type, input type list)` pairs: every output must appear, including independent outputs with an empty input list. This becomes `OutputDependencies`; its union is `SourceDataTypes`. For example, evaluation depends on both tests and models, while copied setup tests depend on source tests and generated models have no dependencies. Dependencies are resolved before invoking the executor. Preparation, output checks and `SaveIfMissing` share `OutputPlan` and the same stable keys; saving a different dependency list is rejected. Change the function version whenever its computation, query projection or dependency contract changes. The wrappers reject missing, incorrectly typed, and unexpected parameters, and require exactly the declared output kinds. Execute validates both phases' contracts and generated sets before any work or cache reuse. Unknown names may be retained in drafts, but Execute rejects them.

The initial functions adapt GeneSort's standalone computation to Sortopia's current types. Both function signatures return `unit`: `resultsFunction = runHost -> unit` and `setupFunction = runHost -> sourceProjects -> unit`. `sourceProjects` maps each required source `sortopiaDataType` to its project ID. The host holds the invocation's typed `Parameters`, cancellation token, and database views. Setup functions save through `host.SetupDb`; results functions save through `host.ResultsDb`. `functionData` remains the typed database payload, not the return value of a catalog function. Exceptions are caught at the execution boundary and reported with the function and parameter-set number.

Catalog definitions also expose `InputError` for value constraints involving several keys. It accepts partial defaults and spans, permitting module/project edits before all required inputs are supplied. `FunctionValidation` combines this check with the required-key and type checks at run validation and execution boundaries, including output planning before reuse. `FunctionDefinition.resultsValidated` registers a results function with this check; existing definitions without custom constraints retain their usual validation.

`FileRunHost` binds a saved run to its project databases, following GeneSort's separation of `runHost`, `runStorage`, and `workflowSources`. It implements `IRunHostFactory`, creating a separate `runHost` for each invocation. Setup cannot write results. During results execution, `SetupDb` is read-only and exposes the exact batch's declared inputs, addressed by `sortopiaDataType`. The host retains output references between invocations, rather than payload lists.

Call `SaveIfMissing(dataType, dependencyReferences, factory)` once for each declared output. The host selects that output's parameter projection, checks the stable ID, and calls the factory only on a miss. Pure generators pass an empty dependency list. For source-dependent setup, call `host.SourceResults.Find(sourceProjects[dataType], dataType, host.Parameters)` and `host.SourceResults.Load(reference)` to read the source project's results. Lookup resolves the project through `workspace.FindProject` and applies the producer's result query keys. Source access is read-only and restricted to the configured project/type pairs. Include every consumed source reference in the saved output's dependencies. Results functions similarly use `host.SetupDb.Reference(dataType)` for dependencies and `host.SetupDb.Load(dataType)` inside their missing-output factory.

For example, a source-dependent setup saves an output using this pattern (with `dataType` declared in both `DataTypes` and `SourceDataTypes`):

```fsharp
let execute (host: runHost) (sourceProjects: sourceProjects) : unit =
    let source = host.SourceResults.Find(sourceProjects[dataType], dataType, host.Parameters)
    host.SetupDb.SaveIfMissing(dataType, [source], fun () ->
        let input = host.SourceResults.Load source
        makeData host.Parameters input)
```

The wrappers verify that the function saved exactly its declared types and labels. There is no registration lifecycle. Each independent definition owns its version; bump it when its output semantics change. Catalogs remain simple name-to-definition maps. Sealed projects capture the function name, version, and resolved output contract. Source lookups use this saved version, even after the installed definition changes. A run whose saved version differs from the installed version cannot execute; create a new project version to use the changed function. Saved data and project snapshots remain readable. Unknown function names are rejected during configuration validation; organizational modules may leave functions unset.

### Generate parameter files and execute results

The setup catalog includes **`sorter-eval.source`**, which copies saved `SorterModelSet ""` and `SortableTests ""` outputs from source projects' results into the current project's `data/setup/SorterModelSet` and `data/setup/SortableTests` folders. It supplies the complete setup for **`sorter-eval.evaluate`**. Select it on a branch module, then choose the source project's ID separately for each output using the **SorterModelSet source project** and **SortableTests source project** selectors. These can reference different projects, or the same project if it produces both types. Supply **ChannelCount** as a setup default or span. To index the local copies by channel count, enter it as a span and select it as each setup output's query key; defaults and spans remain mutually exclusive.

Each source project must expose compatible results query keys (normally `ChannelCount` alone); additional source query keys are not accepted by this function. Lookup resolves each project through `workspace.FindProject` and requires one matching saved result for each type. Both inputs are validated before either local copy is saved: all models and the tests must have the requested positive channel count. Model identities, test identities, format, and the tests' generating prefix are preserved. Each local output records only its own source dependency and is reused on subsequent setup attempts. Missing, ambiguous, or incompatible source data fails with an explanation. **Generate run parameters** copies both inputs locally; the project folder can then be moved elsewhere for results execution without either source project.

Save the workspace, select a run, and choose **Generate run parameters**. It uses the saved run's fixed project defaults and local spans, expanding every parameter set. Root runs produce one file per results set. Branch runs first run all setup sets locally, resolve source projects through `workspace.FindProject`, and materialize their inputs into the project's setup store. Each setup output set is paired with every results set. Generation does not execute results. Unsaved edits or invalid configuration must be corrected and saved before generating files.

Each atomically published `runParameters/<work-item-id>.msgpack` is independently executable. It contains typed values, fixed function name/version and output contracts, project/run IDs, set numbers, and exact local setup references. Work-item IDs hash the complete invocation, including typed values and input references. Identical generation reuses parameter files and setup data; changed inputs add files. No preparation manifest, batch membership file, execution receipt or mutable status index is written. Cancellation can leave a subset of published parameter files; these files are usable and retrying generation fills in the rest. Setup failure occurs before parameter publication for that attempt.

The workspace run editor offers **Generate run parameters** and **Execute page**. The latter opens **Results execution** at the saved run's project `runParameters` folder, automatically reads file statuses, and initially filters to that run (including a zero-file view when it has not been generated). **Back to workspace** preserves the selection and any unsaved editor changes. You can also open **Home → Results execution** and browse to a folder independently. The **Run filter** chooses all files or one run ID; **Refresh** reloads files and their output statuses. Generating new files does not remove previous inputs, so older files still in the folder remain available for selection.

The read-only grid shows each file's name, Pending/Partial/Complete/Invalid status, available/expected outputs, executor, and a column for every required parameter binding. Values include both saved defaults and spans and retain their types in the underlying parameter files. Status comes from exact expected output files, validating identity, schema, checksum and payload without running an executor or writing tracking files. Unreadable files appear as Invalid under **All runs** and do not prevent other files from loading.

Select rows with Ctrl/Shift, **Select all**, or **Select pending**, then choose **Execute selected**. Execution snapshots only those selected files, validates all selected work and existing outputs, and verifies setup inputs needed by incomplete work before writing results. Invalid selected files must be deselected or corrected; unselected files are not executed. Complete work skips the executor, even if its original setup payloads have since been removed. Partial work reuses valid outputs and generates only missing ones. Invalid outputs stop execution and are not overwritten. Selected files must declare distinct results output paths, including already-complete work. Preflight rejects conflicting owners and identifies both parameter filenames and their shared destination before any job starts. Outputs are rechecked before each invocation. Statuses refresh after execution. Results execution never runs setup or consults source projects. It uses immutable saved files independently of unsaved editor changes.

During execution, individual rows change to **Running**, then **Complete** or **Failed**. A validation failure is also attributed to its parameter file before any execution starts. Jobs fail independently: other selected jobs continue, and the final report includes all errors. Unstarted rows keep their previous status after cancellation. Select a failed row and expand **Error details** to read or copy its full error. Failed attempts survive refreshes in the current folder session, including a parameter file deleted after selection; retrying clears the old failure when that file runs again. Cancellation marks an interrupted row **Cancelled**, retains completed work, and leaves unreached rows alone. These attempt statuses are held in memory only. Reopening a folder derives completion from its output files as before. The **Elapsed** column measures each attempt from Running to its terminal event, updates every quarter second while running, and remains visible with the filename and status when scrolling horizontally. Timings survive refreshes in the current folder session and reset when that row is retried; validation failures and completed files with no recorded attempt show a dash. No timings are inferred from file dates or persisted to tracking files. The batch progress bar and summary report finished/total, percentage, running jobs, and jobs not started; finished includes complete, failed, and cancelled attempts. Cancellation does not count unstarted jobs as finished. The batch summary remains available after execution and resets on a new batch or folder.

The UI uses `RunParameterExecution.generate`, `inspectFile` and `executeFilesWithStatus`. The latter emits typed per-file events identified by work-item ID; `executeFiles` remains available without those events. The CLI retains `inspectFolder`, `executeFolder` and `executeFile` for folder-wide or individual work. Operations run away from the UI thread; cancellation is cooperative at storage and function boundaries. The local generation host resolves workspace sources; `FileResultsHost` uses only the copied project, fixed parameter files and local setup references. `FileRunExecution.execute` remains available for immediate execution by other callers.

### Copy a project and execute from the command line

Copy the **entire project folder**, preserving IDs and relative layout:

```text
<Project>/
  <project-id>.msgpack
  runs/<run-id>.msgpack
  runParameters/<work-item-id>.msgpack
  data/setup/SortableTests/<data-id>.msgpack
  data/setup/SorterModelSet/<data-id>.msgpack
  data/results/SorterSetEval/<data-id>.msgpack
  data/.write.lock
```

Type directories use only the `sortopiaDataType` union case name. Free-form labels stay in metadata and stable IDs; labels such as `a b` and `ab` remain distinct. Query IDs stay in file envelopes and identities, rather than folder names. Source lookup scans headers within the relevant type directory and only decodes matching payloads. No persistent index or additional dependency is needed. Older GUID query folders and obsolete manifest files are not migrated or consulted.

Parameter files use versioned, checksummed MessagePack with LZ4 block-array compression and a 64 MiB bound. Published parameter file bytes and IDs are unchanged by removing manifests. Upstream source IDs in provenance are not runtime dependencies: generation copies/materializes the necessary setup data locally. Copying preserves IDs; workspace **import** intentionally assigns new IDs and should not be used to deploy work for execution.

The `Sortopia.Cli` project targets .NET 10 without WPF. Deploy its complete build/publish output and matching runtime/catalog versions. The executable is `sortopia`; `dotnet sortopia.dll` also works.

```text
sortopia generate-parameters --workspace <workspace-folder> --run <run-id>
sortopia list-parameters --parameters-folder <copied-project>/runParameters
sortopia check-results --parameters-folder <copied-project>/runParameters
sortopia execute-results --parameters-folder <copied-project>/runParameters --jobs 4
sortopia execute-results --parameters-folder <copied-project>/runParameters --run <run-id>
sortopia execute-results --parameters <copied-project>/runParameters/<work-item-id>.msgpack
```

Folder operations accept an optional `--run` filter. Single-file execution requires no manifest. Temporary and non-MessagePack files are ignored; malformed parameter files, wrong IDs and mixed-project inputs are rejected with an explanation. An empty selection is reported rather than silently executing other work. The folder is enumerated once per operation, so files added during execution are considered on the next invocation. Use `--jobs <positive-count>` for bounded parallel results execution (default 1), for either folder or single-file commands. The UI exposes **Parallel jobs**, remembers it on this machine, and disables execution for invalid values. A fixed worker pool creates a separate host per invocation and retains report results in selection order. The evaluator CPU allowance is divided between active worker slots; scalar and SIMD evaluation receive cancellation. Results computation and compression do not hold the setup writer lock; independent files publish atomically without overwriting existing destinations. Setup generation remains sequential with its original reuse lock. Execution options do not change serialized parameters or IDs. Distributed scheduling/merging separate copies remains outside this workflow. Exit codes are 0 for success, 1 for failure, 2 for invalid command syntax, and 130 for cancellation. A successful output check returns 0 even when work is pending or partial.

### File-based data storage

`ISortopiaDb` provides `TryLoad`, `Load`, `FindResults`, and `GetOrCreate`. Each project stores immutable data at `data/{setup|results}/<sortopiaDataType-case>/<data-id>.msgpack`. Database names are logical identity scopes, not filesystem paths. Payloads use explicit versioned DTOs and MessagePack LZ4 block-array compression; envelopes contain full canonical keys and a SHA-256 integrity checksum. This uses existing dependencies, with no SQL database or separate mutable index.

Each setup or results output projects its parameter set onto its own entry in `DataTypes`. IDs also include the project ID, database, phase, exact data type/text, function name/version, and declared source-data dependencies. Canonical keys preserve value types, use ordinal key ordering, and are independent of culture and string formatting. Run IDs, execution IDs, and unselected parameters do not participate. Thus setup can reuse the same file when an unrelated span varies, including across runs and app restarts. Results retries also reuse existing outputs, but a single selected results batch must have distinct output owners. Results include only the setup references their function consumes; independent results generators do not duplicate their files when unrelated setup data changes.

**Query keys are a computation contract:** include every parameter that can vary and change that output. A missing selected key is an error; an empty key list intentionally creates one datum per remaining identity scope. The store cannot infer which parameters an arbitrary function uses. This is projection-based reuse, not global deduplication of identical bytes produced by different projects or different keys.

Source lookup uses the source project's fixed results database, function/version, exact data type/text and that output's **results** query keys, projected from the consumer's setup parameters. Execute source runs first. Missing, corrupt, or ambiguous source results stop execution with an error. If multiple upstream setup inputs yielded the same results query projection, lookup refuses to choose arbitrarily; the producer function's contract must distinguish those cases. The current codecs support `SortableTests` (including prefix CEs), `SorterModelSet`, and `SorterSetEval`, with one output per kind for current catalog functions. Other declarations produce a clear unsupported-type error.

Setup writers coordinate through a project-local file lock and check again after acquiring it, so concurrent setup creators invoke a shared factory once. Results writers generate independent outputs without that lock. The empty `.write.lock` file is coordination infrastructure, not a status marker; the active lock is its open file handle. Files are flushed to a temporary sibling and published without overwriting existing data. Readers ignore incomplete temporary files. Source lookup scans headers within the relevant data-type directory without an additional index. Corruption is reported instead of silently regenerating data. Failure, cancellation or a process crash retains already published outputs, which subsequent output checks and retries discover directly. Existing historical receipt files are ignored and left in place; new work never depends on them.

The initial codecs read whole objects and limit both files and uncompressed payloads to 256 MiB. This store is intended for a local workspace filesystem. Moving an existing project preserves its IDs and data. Importing a copy assigns new project IDs, so copied historical data retains its original identity and is not reused by the new project; executing the copy creates data in its new scope.

## Types and persistence

`Sortopia.Workspaces` defines concrete `rootProject`, `branchProject`, `rootModule`, and `branchModule` types. Their child arrays are strongly typed: for example, `rootProject.Runs` is `rootRun[]`, and `branchModule.Projects` is `branchProject[]`. The `project` and `workspaceModule` discriminated unions provide common views for storage and the editor. Their boundary factories validate type consistency. `workspace.Modules` accepts either `workspaceModule.Root` or `workspaceModule.Branch`. Array properties return copies.

Modules and projects expose their effective shared properties directly and through `Configuration` (`rootProjectConfig` or `branchProjectConfig`). `LocalOverrides` uses `rootDefaultOverrides` or `branchDefaultOverrides`: each property is optional, with `None` meaning inherit and `Some` meaning local, including `Some []` and `Some ""`. `Defaults.resolveRoot` / `resolveBranch` apply local values over the inherited configuration. For parameter defaults, `Defaults.mergeParameterDefaults` replaces matching keys, retains other inherited bindings in order, and appends new local keys. Both `None` and `Some []` inherit all parameter defaults; duplicate keys within a local list are invalid. Other list properties use whole-list replacement. `createInherited` constructs an entity with its parent configuration and local overrides; `rebind` resolves it and its descendants against a new parent. The existing project `create` factory makes every supplied configuration property local; the module `create` factory starts with all properties inherited.

`RootRun.create parent inputs` and `BranchRun.create parent inputs` accept their concrete parent projects through `IRootProject` / `IBranchProject`; the contracts avoid a dependency from runs back to workspaces. Run input records contain Id, RunName, ParentProjectId, DescriptionOverride, and ResultsParameterSpans. Branch inputs also contain SetupParameterSpans. Function overrides are absent from project local overrides and run inputs. Both database names come from the project. The parent must be sealed when constructing a runtime run; `project.seal` creates that immutable parent snapshot and `project.withRuns` attaches the validated runs. `RunDto.toDomain` prepares a sealed snapshot without mutating the draft parent. A run retains its inputs in `Configuration` and fixed settings in `ProjectConfiguration`. Branch runs also retain resolved source project snapshots, so queries need no further workspace lookup.

The four shared names have distinct UMX tags: `resultsDatabaseName`, `resultsFunctionName`, `setupDatabaseName`, and `setupFunctionName`. Shared configuration is factored into `resultsConfig` and `setupConfig`. A `setupDataTypeConfig` contains `DataType: sortopiaDataType`, `SourceProjectId: Guid<projectId>`, and `QueryParameterKeys: string<paramKeyName> list`. `setupConfig.DataTypes` is the ordered list; its `SortopiaDataTypes`, `SourceProjectIds`, and `QueryParameterKeys` views derive from those entries. Results query keys remain one list.

`workspace.ProjectIndex` indexes projects globally by ID, and `FindProject` returns an optional project. Workspace creation/loading validates references and resolves branch source snapshots through `BranchRunSources.resolve`. `QueryParams.forSource` uses the source project's ID, results database, and results query keys. `forSetup` uses the parent project's ID, effective setup database, and the selected entry's query keys; `forResults` uses the parent project's results metadata. Query IDs use the stable project ID, exact type/text pair, and selected parameter strings, rather than the display name.

`sortopiaDataType` is a discriminated union with ten cases: `Workspace`, `Run`, `WorkspaceModule`, `RunParameters`, `SorterPoolSet`, `SorterSet`, `SorterModelSet`, `SortableTests`, `SorterSetEval`, and `TextReport`. Every case carries a free-form `string`; empty strings, whitespace, Unicode, and line breaks are preserved. Execution and setup output lists use this type, as do result and setup queries. Each output row has a case selector and a text field. Lists can contain the same case with different text; an identical case/text pair cannot appear twice. Inherited lists show both values and retain their clickable source. Query matching and query IDs include both the case and the exact text.

`parameterBinding` is the general pairing of a `string<paramKeyName>` with a typed `parameterValue`. It can represent a supplied parameter, a default, or an override; the containing property or operation determines its role. `ParameterBinding.create key value` constructs a binding from a typed key, `fromValue name value` accepts an already typed union value, and `fromText name kind text` validates editor or persisted input. All constructors enforce the known key's type and valid values. `ParameterBinding.validateUnique` validates collections with one binding per key. `parameterBindingDto` and `WorkspaceParameterBinding` provide the corresponding storage and editor representations.

`parameterSet` stores a `Map<string<paramKeyName>, parameterBinding>` exposed by `ParamMap`. `parameterSet.fromBindings bindings` creates a set directly; `parameterSet.create map` accepts a typed map and validates that each key matches its binding. `set.WithBinding(binding)` adds or replaces a binding while preserving the original set. `WithValue` accepts a typed key/value or a key name with a `parameterValue`; `None` removes the key. Binding construction, validation, and set updates retain the typed values without formatting or reparsing them.

`set.TryFind(name)` returns a binding. `set.TryFind(typedKey)` reads the underlying CLR value directly, returning `None` for a missing key or mismatched type; numeric-looking text remains text. String conversion is explicit: `TryFindText(name)` formats one value, and `ToStringMap()` projects the whole set to canonical invariant strings. Queries format only their selected keys; DTO serialization formats bindings at the storage boundary. Library IDs remain typed through bindings, parameter sets, and catalog function calls. File-store identity uses their type tags and stable field bytes, so alternate input formatting produces the same data ID.

`ParameterSets.create bindings spans` expands bindings and spans into `parameterSet[]`. It parses span text using the matching binding's type or the known key's type, and stores each candidate as a typed binding. Matching spans replace bindings and other bindings remain fixed. Combinations exceeding the maximum .NET array length are rejected before allocation.

`ParameterSets.preview maxCount bindings spans` shares the same validation and combination generator, materializing only the requested prefix. All candidate values are validated, including values beyond the visible rows. The editor retains typed parameter sets and formats values only for display.

`RunParameterSets.create run` returns a `runParameterSets` record with `Results: parameterSet array` and `Setup: parameterSet array option`. Root runs return `Setup = None`; branch runs return `Some setupSets`. Results and setup combinations are expanded independently from their respective defaults and spans, retaining typed bindings. No spans is valid only when there are no output query keys and the defaults satisfy the required inputs. The function uses the run's resolved settings and does not need a workspace lookup.

`ResultsParameterDefaults` is a `parameterBinding list` on root/branch modules, projects, and runs. Branch types additionally expose `SetupParameterDefaults`. These properties use bindings as defaults, merging by key through modules and draft projects. Runs receive the sealed project's resolved defaults; their spans replace matching keys. `RootRun.makeResultsParameterSets`, `BranchRun.makeResultsParameterSets`, and `BranchRun.makeSetupParameterSets` use the general binding APIs. `ParamKeys.all` supplies metadata derived from the typed key declarations.

Every entity has a UMX-tagged GUID ID: `workspaceId`, `moduleId`, `projectId`, or `runId`. Its definition filename is `<id>.msgpack`. IDs survive edits, moves, and missing-file restoration. Folder names exist only on workspaces, modules, and projects. The absolute workspace location stays in application settings, outside the definitions.

Names must be nonblank, and sibling display names of the same entity type must be distinct ignoring case. Sibling module/project folder names must be distinct across both types, ignoring case. Module, project and run IDs must each be unique within their entity kind throughout the workspace. Rejected edits remain visible for correction while the tree keeps the last accepted value; Save is disabled until corrected. Saved names and folder names stay reserved until their removal or rename has been saved.

Workspace, module and project files use schema version **16** through `WorkspaceDefinitionCodec`. Workspace and module child references contain only `{ id, folderName }`, where the folder is a single relative directory segment directly under the parent. Separate module/project reference arrays identify the type without extra directories. Project run references are ordered GUID arrays addressing `runs/<id>.msgpack`. IDs are checked against both the referenced ID and the definition filename; duplicate IDs, duplicate sibling folders, invalid family relationships and escaping paths are rejected. Loading follows references rather than directory enumeration, preserving saved order and keeping removed-but-retained entities out of the loaded tree. Missing children are reported with their ID and location; there is no embedded descendant snapshot to fall back to when reopening.

Modules persist local overrides and **captured parent defaults**, without an additional copy of their own effective configuration. Draft projects likewise persist local overrides and captured parent defaults, including inherited function selections; database names remain project-owned overrides. `inheritedFrom` records the immediate parent module's ID and name for captured context. These defaults are captured *before* local overrides, including values currently hidden by a local override. Removing a local override from a detached entity therefore restores the original parent value. Captures refresh when ancestor defaults change even if the child's effective value is unchanged. Attached entities resolve against the actual parent; `LoadModuleFolder` and `LoadProjectFolder` use the captured context at the detached root and then resolve its descendants normally. Attaching/importing into a workspace resumes normal inheritance from the destination parent. Sealed projects store only their complete fixed configuration and run references, without a redundant inherited-context or local-overrides copy. Captured context makes configuration portable; it does not copy external source-project data or executor code.

Run files retain schema version **14**: IDs, optional description override and spans, with no folder or database overrides. `WorkspaceCodec.decodeRunById workspace bytes` resolves a sealed parent and source snapshots; `decodeRun parent bytes` supports an already loaded parent. Prepared execution formats and data IDs are unchanged. `WorkspaceDto`, `ModuleDto`, `ProjectDto` and the aggregate methods on `WorkspaceCodec` remain in-memory editing/cloning/comparison representations; persistence does not write them as container files. Older container formats are rejected, with no migration.

Saving compares the loaded files' content hashes in memory, so edits to any referenced definition—including captured values hidden by live inheritance—cannot be silently overwritten. No tracking file is added. An already-open workspace can explicitly restore missing definitions from its loaded tree; surviving files still must match the loaded baseline. A run-input-only edit writes its run file without rewriting project, module or workspace files. Transactional rollback and folder moves continue to cover the separate definition files.

  Branch research/
    <branch-module-id>.msgpack

      <branch-project-id>.msgpack

Definition limits are 64 nesting levels, 50,000 entities, and 16 MB per definition file. Multiple container definitions in one entity folder are reported as ambiguous. Unrelated files are not serialized; explicit folder imports and moves preserve their contents.

## Workspace file inspector

Open **File inspector** from Home or **Inspect files** from the workspace editor. The inspector reads saved files without changing them or discarding the editor's unsaved changes. It can browse a workspace, a detached module, or a copied project without first loading a valid hierarchy. The folder list loads one directory at a time, with filename filtering, 200-entry pages, refresh, and a splitter between the file list and details. Child-reference links open the referenced definitions and identify missing files.

Workspace, module, project and run definitions display their stored fields, including local overrides and captured inherited defaults. Prepared run parameters display each binding's key, type and value, fixed functions/outputs and local setup references. These views decode saved content; they do not resolve live inheritance or validate the entire workspace.

Stored setup/results data displays an envelope summary: data type/label, project/data/query IDs, database/function/version, query parameter count, dependency references, compression, payload sizes and recorded checksum. The inspector reads at most 1 MiB of the uncompressed envelope header and never decompresses the large data payload. It checks envelope length and identity hashes, but does not claim to validate the payload checksum; **Check outputs** remains the integrity check for execution data. Writer lock and temporary files have explanatory summaries, and other files show filesystem metadata.

Detailed configuration/metadata reading is limited to 4 MiB on disk (16 MiB decompressed for prepared metadata). Larger files receive filesystem summaries. Detail trees show at most 200 elements per collection, 4,000 nodes overall and 4,096 characters per value, with explicit truncation notices. Referenced-file links and dependency summaries are also bounded. Reads run away from the UI thread; changing selection cancels obsolete results. Missing, locked, malformed and unsupported files produce an explanation containing the affected path. The inspector does not follow filesystem links or navigate outside its selected root.

### Configurable query projections

Enter the run spans first, then open Results outputs or Setup outputs and select query keys separately for each data type. Choices are restricted to valid explicit spans present in every current run of that project. Each query key must be a required input of its phase function and cannot also have a default. Empty selections are allowed. A key that loses its span remains visible with an error and blocks saving or execution.

Query keys control reuse: only selected parameter values, the project/function/output identity, and the declared input data references distinguish an output. Omitting a varying span key intentionally reuses the output across those values. With an empty projection, all parameter combinations share an output for the same input references. The UI states this beside each output. The selections are frozen with the project, included in portable runParameters files, and used for source-project lookup and output-completion checks.
