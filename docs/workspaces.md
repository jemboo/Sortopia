# Workspaces

Open **Workspace** from the home page and choose a root folder. Enter a workspace name and choose **Save workspace** to create it. Selecting a folder only remembers the location; an existing workspace loads automatically. Names, hierarchy edits, imports, and moves remain in the draft until saved. **Discard changes** restores the last saved state without changing disk contents.

## Root and branch hierarchies

A workspace can contain both root and branch modules. Each module and all its descendants use one type:

| Container | Allowed children |
| --- | --- |
| Workspace | Root modules and branch modules |
| Root module | Root modules and root projects |
| Branch module | Branch modules and branch projects |
| Root project | Root runs |
| Branch project | Branch runs |
| Run | None |

Root runs execute without a setup step. Branch runs have separate setup and execution settings. Projects contain runs only; use nested modules to organize projects.

Select the workspace to choose **New root module** or **New branch module**. Inside a module, creation buttons name the matching type, such as **New branch module** and **New branch project**. Inside a project, **New root run** or **New branch run** creates the correct run type automatically. The tree identifies each item's type with text and color; the hint above it explains the selected item's allowed children. Types are fixed when created.

The inspector edits display names and module/project folder names while the entity is editable. A sealed project keeps its name, folder name, and configuration. New folder names follow their display names until saved or manually edited. Saved display-name edits keep folder names fixed. Names may be descriptive, such as `Search: prefixes`, while folder names must be portable directory segments, such as `prefix-search`.

Runs have no folder name. A run is stored directly as `runs/<run-id>.msgpack`. The **Full path** field shows the selected folder or run file and supports text selection/copy. **Open folder** opens that folder, or the containing `runs` directory for a run.

## Module defaults, project defaults, and run inputs

Defaults begin on top-level modules; the workspace itself has no configuration defaults. Root modules and projects share Description, ResultsFunctionName, ResultsSortopiaDataTypes, ResultsQueryParameterKeys, and ResultsParameterDefaults. Branch modules and projects also share SetupFunctionName, SetupDataTypes, and SetupParameterDefaults. Database names belong only to projects: each root project defines ResultsDatabaseName, and each branch project defines both ResultsDatabaseName and SetupDatabaseName. These are direct fields with initial values `Results` and `Setup`, with no inheritance toggle. Modules have no database properties, and runs display their project’s database names as read-only values with a link to that project. Each setup data-type entry combines its exact type/text pair, SourceProjectId, and its own QueryParameterKeys. The three logical views (setup types, source IDs, and query-key map) are derived from this single list.

Each property follows the nearest ancestor with a local override. The inspector displays its effective value and the name of the ancestor supplying it. Click an **Inherited from [ancestor name]** link to select the module or project defining that property. Check **Override on this module** or **Override on this project** to edit a local value; uncheck it to restore inheritance. Modules and projects inherit shared properties. Function selections are defined only on modules; project and run inspectors show them read-only. Database names remain project-owned. With no ancestor override, descriptions and lists are empty and function names are unset. Organizational modules can leave functions unset; projects need resolved, nonblank database and function names before saving.

Selecting a catalog function fixes its saved data types, including each case's string, and the parameter keys for each output. The inspector displays these contracts read-only. Follow the value-source link to the module defining the function. Projects can choose source projects for source-dependent setup outputs, but cannot change the function's types, strings, or keys. Each phase's default and span key dropdowns contain only that function's explicitly declared required parameters. Defaults may supply some of these values at a module or project; runs must supply exactly all required keys through inherited defaults and local spans, with every output query key explicitly present in the spans. An explicitly blank description overrides its parent. Turning a local default override off and back on preserves its draft during the current edit session.

Select a run to edit its description and execution parameters. Branch runs have separate setup parameters. Functions and database names always come from the project. Before the first save, functions follow the draft project’s inherited module selections; after sealing, runs use the project’s fixed snapshot. Only the description has an optional per-run override; an explicitly blank description is allowed.

The run's execution settings, output types, and query keys are shown as inherited. **Edit parent defaults** selects the containing project or module, and is available even while a required inherited value is missing. Run type and parent ID come from the containing project. Data types persist as case/text pairs. There is no JSON editor.

On a module, open **Results parameter defaults** or **Setup parameter defaults** and choose **Add missing required defaults**. The action adds typed entries for the selected function's required keys that have no inherited or local default. Existing entries and their values stay intact, including incomplete edits, and inherited entries remain inherited. New entries use suggested starting values: 8 channels, 1 stage, 100 sorters, replication 0, self-comparisons excluded, test collection off, `Bools`, `Mssi`, `SplitMix64`, and evaluator `V1`. Channel count follows an existing count or library ID in that phase, then the other phase, before falling back to 8. Library IDs prefer available entries at that width, with a one-stage prefix and a two-way merge where available; if that width has no catalog entry, an available 8-channel entry is used. Review the new values using the usual typed editors and validation. Repeating the action does not duplicate entries; it is disabled when all required keys already have entries or no catalog function is selected.

Use **Add default parameter** on a project or module to supply one typed value per key. Once a catalog function is selected, the key picker contains exactly its required parameters and cannot accept other keys. Each descriptor supplies its value type. Before a module has a registered function, shared defaults can be prepared using known or custom keys. Selecting an inherited custom key initially uses its inherited type; you may still change a custom key’s type. Known keys use their existing `ParamKeys` type; custom keys support text, integer, unsigned 64-bit integer, floating point, Boolean, GUID, sorter library ID, prefix library ID, and merge library ID. Defaults use the same key-specific editors and validation as run spans, including catalog value dropdowns and numeric limits. Boolean values use a True/False selector. Numeric and GUID fields retain invalid drafts and show validation errors. Numbers use invariant formatting, floating values must be finite, and integer bounds are checked. Unconstrained text preserves spaces, commas, Unicode, line breaks, and blank values. Changing a default's key preserves its value and revalidates it. Invalid local or inherited defaults appear in the save explanation and block the affected run preview until corrected; **Override here** uses the same editor for local overrides.

`SorterLibId`, `PrefixLibId`, and `MergeLibId` are distinct typed parameter values backed by the existing catalog ID records. Their shared editor is used for module/project defaults, run spans, and custom keys assigned one of these types. Choose a catalog entry to populate its fields, or enter channel count and variant directly. Prefix IDs also require a positive stage length; merge IDs require a positive merge dimension that divides the channel count exactly. Merge catalog suggestions update with the channel count. Invalid field drafts and incompatible values retained after a type change remain visible and block saving. A structurally valid ID may have no catalog entry; lookup availability is checked by the function using it.

Parameter defaults inherit **by key**. A child adding `StageLength = 1` keeps its parent's `ChannelCount = 16`; a child setting `ChannelCount = 8` replaces only that key. Results and setup defaults merge independently. The inspector shows inherited defaults alongside local defaults, with a clickable source for each inherited value. Choose **Override here** to copy just that key into a local editor. Removing a local row restores its inherited value, if any. An empty local list inherits all parent defaults. Only local bindings are saved as overrides, so other inherited values continue to follow ancestor edits until a project is sealed.

Runs receive the resolved default lists from their parent project. Use **Add parameter** to add a span of candidate values, or **Add missing span rows** to create empty rows for missing query spans and required inputs that have neither a default nor a span. Every output query key requires an explicitly entered span, including fixed values. A default alone never satisfies a query key. Results and setup pickers use their respective functions’ exact required-key lists. Values use the declared parameter type. Unsupported keys, missing required inputs, and missing query spans block saving, previews, and Execute. The shared rule is `default keys ∪ span keys = required keys`, with `query keys ⊆ explicit span keys`, independently for setup and results.

Selecting a key chooses its editor and validation. Booleans use True/False; data formats, RNG types, model types and evaluator types offer value dropdowns using their domain parsers. Numeric fields retain invariant numeric validation; ChannelCount and SorterCount must be at least 1, while StageLength and Repl may be 0. GUIDs and free-form text retain their respective editors. Library IDs use structured editors as described below; catalog availability and constraints involving several parameters are checked by execution. Changing the key preserves entered values and immediately flags incompatible ones. Each span needs at least one value; blank values are valid only for unconstrained text. Errors identify the key, clear the affected parameter-set preview, and block Save and Execute until corrected. Results and setup span editors use the same rules, with independent inherited defaults. **Discard changes** also clears invalid field edits.

Use **Use default as single-value span** on an inherited default to copy its current value into the run. **Use query defaults as single-value spans** copies all missing query defaults for that phase. These are explicit user actions: preview, Save, loading, and Execute never insert spans. Copying preserves typed values, leaves inherited defaults unchanged, and never replaces an existing span (including an incomplete draft). Changing a default later does not change the copied span.

Parameter sets contain all combinations of the run's span values. A span replaces the default for the same key; all other defaults stay fixed. For example, defaults `ChannelCount = 8, Seed = 7` with a `Seed` span of `11, 13` produce two sets: `{ChannelCount = 8, Seed = 11}` and `{ChannelCount = 8, Seed = 13}`. When the function has no query keys, no spans produces one set containing the defaults, provided those defaults satisfy its required-input contract. Branch setup and execution sets are generated independently. Runs display the inherited values, identify defaults overridden by spans, and show the number of parameter combinations.

Run editors show a **Results parameter sets** table; branch runs also show a separate **Setup parameter sets** table. Each row is a generated combination in execution order, using the effective inherited defaults and local spans. Column headers show the key, type, and whether the value comes from a default or a run span. Previews update with edits, show the first 50 combinations and total count, and never allocate the full product just to display it. Invalid parameters or missing required query values replace the affected preview with an error. An empty input produces one empty set. Previewing does not execute the run.

The workspace has three resizable columns: the hierarchy, a compact read-only configuration summary, and the editor for the selected setting. Drag either divider, or focus it and use the arrow keys, to adjust the widths. The summary shows current values, inherited/local/fixed state, validation issues, and run execution status. Select a setting’s linked descriptor to open just that setting on the right. Source links select the defining module or project and keep the same setting open. Save-error links open the corresponding setting directly. Each entity remembers its selected setting while navigating the current draft. Parameter lists, setup outputs, generated-set previews, and execution reports remain grouped as individual items; edits update the summary without discarding drafts. Each column scrolls independently.

Module editing starts with **Choose functions**, before defaults or outputs appear in the configuration summary. Root modules choose a results function that works without setup data. Branch modules choose a setup function first; the results picker then lists only functions whose input types that setup supplies. Inherited function selections count as chosen. Both selectors share one editor, with setup above results. Defaults, outputs, and source choices appear only once the function selection is complete and compatible. Name, location, and description remain available throughout.

Project and run editors start with **Inherited functions**, showing setup first for branch hierarchies. Function names are read-only, with source links to the defining module or sealed project. Defaults, spans, outputs, and source settings appear only when the inherited functions are available and compatible. Database names, description, and identity remain accessible while functions need attention. Project default pickers and run span pickers list only their phase’s required keys. Output cards show each function’s fixed types and query projections. Projects choose compatible source projects only for source-dependent setup outputs; runs display those choices read-only. Sealed projects and their runs keep their saved function contracts when an ancestor changes.

Results and setup functions use catalog-name comboboxes on modules only. Enable a local override to choose a function; inherited and sealed values remain read-only and retain their source links. Results choices come from `FunctionCatalogs.resultsFunctionCatalog`, and setup choices come from `FunctionCatalogs.setupFunctionCatalog`. Changing a function refreshes its output contracts and allowed parameter keys. When a child module selects a different function, it inherits only compatible defaults. Module defaults for other functions are retained only in the editing session: they are hidden, excluded from the effective configuration and saved overrides, and restored if you switch back. Compatible local values and inherited sources stay intact. Draft project defaults and run spans follow the same rule: entries outside the inherited function’s required keys are kept only in the editing session, hidden from the active editor, and excluded from previews and saved inputs. Restoring the function restores those entries. Incomplete or invalid values for allowed keys remain visible and block saving. Upstream source query keys must also be within the setup function's required parameters. The inspector reports incompatible setup/results selections: evaluator functions need a branch setup that provides their exact input types.

The catalogs are plain immutable maps in `Sortopia.Functions`, keyed by `string<resultsFunctionName>` and `string<setupFunctionName>`. `ResultsFunctionNames` and `SetupFunctionNames` hold the typed name variables. Each `functionDefinition` explicitly declares `RequiredParameters: paramKeyDescriptor list` and `DataTypes: Map<sortopiaDataType, string<paramKeyName> list>` alongside its independent `Execute` implementation. Parameter descriptors define the types once. Each output projection refers to a subset of those keys; required parameters need not occur in any query projection. Duplicate required keys, duplicate query keys, and query keys outside the required contract are rejected. Both `setupConfig.DataTypes` and `resultsConfig.DataTypes` expose the corresponding exact type-to-key maps. `SetupSortopiaDataTypes` and `ResultsSortopiaDataTypes` are their keys; `ResultsQueryParameterKeys` remains a convenience union, never a shared projection for all result files. Current function labels are empty strings, fixed by their definitions.

Define a function with `FunctionDefinition.results` or `FunctionDefinition.setup`, passing the required typed descriptors via `ParamKey.describe` separately from each saved type and its query-key names, then add its name/definition pair to `FunctionCatalogs.fs`. Use `setupWithSources` for outputs that consume matching source-project data, and `resultsWithInputs` for results that consume setup data. `SourceDataTypes` declares these dependencies. The wrappers reject missing, incorrectly typed, and unexpected parameters, and require exactly the declared output kinds. Execute validates both phases' contracts and generated sets before any work or cache reuse. Unknown names may be retained in drafts, but Execute rejects them.

The initial functions adapt GeneSort's standalone computation to Sortopia's current types. Both function signatures return `unit`: `resultsFunction = runHost -> unit` and `setupFunction = runHost -> sourceProjects -> unit`. `sourceProjects` maps each required source `sortopiaDataType` to its project ID. The host holds the invocation's typed `Parameters`, cancellation token, and database views. Setup functions save through `host.SetupDb`; results functions save through `host.ResultsDb`. `functionData` remains the typed database payload, not the return value of a catalog function. Exceptions are caught at the execution boundary and reported with the function and parameter-set number.

`FileRunHost` binds a saved run to its project databases, following GeneSort's separation of `runHost`, `runStorage`, and `workflowSources`. It implements `IRunHostFactory`, creating a separate `runHost` for each invocation. Setup cannot write results. During results execution, `SetupDb` is read-only and exposes the exact batch's declared inputs, addressed by `sortopiaDataType`. The host retains output references between invocations, rather than payload lists.

Call `SaveIfMissing(dataType, dependencyReferences, factory)` once for each declared output. The host selects that output's parameter projection, checks the stable ID, and calls the factory only on a miss. Pure generators pass an empty dependency list. For source-dependent setup, call `host.SourceResults.Find(sourceProjects[dataType], dataType, host.Parameters)` and `host.SourceResults.Load(reference)` to read the source project's results. Lookup resolves the project through `workspace.FindProject` and applies the producer's result query keys. Source access is read-only and restricted to the configured project/type pairs. Include every consumed source reference in the saved output's dependencies. Results functions similarly use `host.SetupDb.Reference(dataType)` for dependencies and `host.SetupDb.Load(dataType)` inside their missing-output factory.

For example, a source-dependent setup saves an output using this pattern (with `dataType` declared in both `DataTypes` and `SourceDataTypes`):

```fsharp
let execute (host: runHost) (sourceProjects: sourceProjects) : unit =
    let source = host.SourceResults.Find(sourceProjects[dataType], dataType, host.Parameters)
    host.SetupDb.SaveIfMissing(dataType, [source], fun () ->
        let input = host.SourceResults.Load source
        makeData host.Parameters input)
```

The wrappers verify that the function saved exactly its declared types and labels. There is no registration lifecycle. Each catalog has a simple name-to-version map; bump an entry's version when its computation changes.

### Execute a run

Save the workspace, select a run, and choose **Execute** in its Execution section. Execution uses the saved run's fixed project defaults and local spans, expanding all parameter sets (not just the first 50 shown in the preview). Unsaved changes, input errors, missing saved components, and unknown catalog names disable Execute with an explanation.

Root runs process each results parameter set. Branch runs first prepare every setup parameter set. Source-dependent outputs resolve projects with `workspace.FindProject` and load their saved results; pure generators need no source project. After all setup sets succeed, each setup output batch is paired with every results parameter set: 2 setup sets × 3 results sets means 2 setup sets followed by 6 results sets. Both phases reuse each saved output independently, including partial cache hits, without invoking that output's generator. A setup failure prevents all results processing; any other failure stops remaining work and identifies the function and parameter set.

Execution runs off the UI thread and disables editing and duplicate execution. **Cancel operation** is checked between function calls, during database operations, and between mutant-evaluation chunks. Other synchronous computation finishes before the next cancellation check. Progress counts processed parameter sets. The Execution section retains the last attempt for each run while the workspace is open, including completed setup/results sets and their stored output references, even after a failure or cancellation. The expandable output summary shows the first 100 sets, with data types, saved/reused indicators and data IDs. Executing again replaces that run's displayed report.

Execute uses `FileRunExecution.execute` in `Sortopia.FileDb`, which creates the `FileRunHost` and calls `RunExecution.execute`. Published data remains available after closing the app, for subsequent runs and downstream projects. Run definitions are unchanged. Callers of the shared execution loop supply an `IRunHostFactory`; the catalogs and execution loop have no filesystem dependency.

### File-based data storage

`ISortopiaDb` provides `TryLoad`, `Load`, `FindResults`, and `GetOrCreate`. Each project stores immutable data at `data/{setup|results}/<query-id>/<data-id>.msgpack`. Database names are logical identity scopes, not filesystem paths. Payloads use explicit versioned DTOs and MessagePack LZ4 block-array compression; envelopes contain full canonical keys and a SHA-256 integrity checksum. This uses existing dependencies, with no SQL database or separate mutable index.

Each setup or results output projects its parameter set onto its own entry in `DataTypes`. IDs also include the project ID, database, phase, exact data type/text, function name/version, and declared source-data dependencies. Canonical keys preserve value types, use ordinal key ordering, and are independent of culture and string formatting. Run IDs, execution IDs, and unselected parameters do not participate. Thus varying an unrelated span reuses the same file, including across runs and app restarts. Results include only the setup references their function consumes; independent results generators do not duplicate their files when unrelated setup data changes.

**Query keys are a computation contract:** include every parameter that can vary and change that output. A missing selected key is an error; an empty key list intentionally creates one datum per remaining identity scope. The store cannot infer which parameters an arbitrary function uses. This is projection-based reuse, not global deduplication of identical bytes produced by different projects or different keys.

Source lookup uses the source project's fixed results database, function/version, exact data type/text and that output's **results** query keys, projected from the consumer's setup parameters. Execute source runs first. Missing, corrupt, or ambiguous source results stop execution with an error. If multiple upstream setup inputs yielded the same results query projection, lookup refuses to choose arbitrarily; the producer function's contract must distinguish those cases. The current codecs support `SortableTests` (including prefix CEs), `SorterModelSet`, and `SorterSetEval`, with one output per kind for current catalog functions. Other declarations produce a clear unsupported-type error.

Writers coordinate through a project-local file lock and check again after acquiring it, so concurrent creators invoke a shared factory once. Files are flushed to a temporary sibling and published without overwriting existing data. Readers ignore incomplete temporary files. Corruption is reported instead of silently regenerating data. Failure or cancellation retains already published outputs. Each finished attempt also saves a small `executions/<execution-id>.msgpack` receipt containing parameters, output references, reuse flags and status; it does not duplicate payloads. Receipts are not yet loaded into the UI's history. A process crash may leave published data without a receipt, which later executions can still reuse.

The initial codecs read whole objects and limit both files and uncompressed payloads to 256 MiB. This store is intended for a local workspace filesystem. Moving an existing project preserves its IDs and data. Importing a copy assigns new project IDs, so copied historical data retains its original identity and is not reused by the new project; executing the copy creates data in its new scope.

The inspector scrolls through the full form; folder names and paths are available under **Location**. Selecting another tree item returns the inspector to the top. Configuration is validated before saving as MessagePack.

Changing module settings updates descendant modules and draft projects that inherit each property. A project is sealed when its first valid run is saved: all effective settings are captured as fixed values in the same transaction as the run. Failed saves leave the draft editable. Removing the last run does not unseal the project. Sealed projects keep their settings across ancestor edits, moves, and imports. **Create new version** creates an editable copy with a new project ID and no runs. Existing runs keep their parent project ID; create a new run to use another project.

## Setup outputs and source projects

Each setup row describes data **saved by the setup function**. Types, strings, and per-output keys come from its catalog definition. Pure outputs display “Generated from parameters” and have no source dependency (`SourceProjectId = Guid.Empty`). An output that consumes source data has a picker listing projects providing exactly the same `sortopiaDataType`, including its string, whose result query keys are all accepted by the setup function. Modules may leave a source unassigned for descendant projects to choose. A project can provide several types, and several entries may select that project. Sources may be root or branch projects anywhere in the workspace. A draft consumer can refer to a draft source; its source must be sealed before the consumer saves runs. Missing required sources, mismatched types, duplicate entries, and cyclic project dependencies are rejected.

Setup executors receive a `Map<sortopiaDataType, Guid<projectId>>` containing exactly their declared source types. Different types can select different projects and results databases; source project and database names are not execution parameters. Names are displayed in the UI, while IDs identify the selected projects.

The row's query keys identify the saved setup data. Fetching source data uses that output's keys in the source project's **results** contract and its results database instead. Those source keys must fit within the setup function's required parameters; setup sets supply the values through defaults or spans. The inspector shows source query requirements and links to the source project. Source choices inherit or override together; fixed output contracts are always reapplied from the selected function. For `sorter-eval.standard`, varying only `Repl` or `StageLength` creates new models while reusing the same tests file.

## Reorganizing and importing

Use **Cut** and **Paste**, the tree's context menu, or **Ctrl+X / Ctrl+V** while the tree has focus. Text fields retain normal text-editing shortcuts. **Cancel cut** or **Escape** clears the cut selection. Cut alone does not change the draft. Paste is disabled for incompatible types, including a project selected as the parent of another project. Its tooltip explains a type mismatch. Cycles, sibling collisions, and occupied destinations are rejected.

A successful paste changes the draft. Saving moves folders and their contents while preserving entity IDs and sealed project settings. Runs can be reordered within their project but cannot be moved to a different project. Discard cancels pending moves. Moving an item within its current parent reorders its typed collection.

**Add module…** and **Add project…** import existing saved entities. Modules can be added to workspaces or matching modules; projects can be added only to matching modules. Imports require valid definition files identifying their root/branch type. All descendants must match. Plain folders without definitions cannot establish an entity's type.

The picker starts in the selected parent's matching container or its nearest existing ancestor. An external import is copied only on save, including output files and empty folders. Copying assigns fresh IDs and filenames to the copied entities and descendants. Internal source references and run parent IDs are remapped together; external source IDs are preserved and validated in the destination workspace. Source files stay unchanged. An entity already at the exact destination is attached in place and keeps its IDs. Existing destinations are not merged or overwritten.

Imports read the actual disk hierarchy, ignoring stale child lists in parent snapshots. Wrong types, malformed settings, forbidden child containers, and name/folder collisions leave the draft unchanged. Changes to an import source require removing the pending import and adding it again. Linked paths and overlapping source/destination trees are rejected. A child moved out of an unsaved import is copied once to its new destination, excluding it from the parent copy.

## Saving and disk status

When an edit cannot be saved, a summary beside **Save workspace** lists the affected item’s full hierarchy path, the editor section, and specific instructions. Select an issue to select its workspace/module/project/run, open the relevant section, and scroll to it. Missing functions explain which override checkbox to enable and which catalog to choose from. Missing database names direct you to the project. Parameter errors name the key. Invalid names and folders remain editable while the tree retains the last valid value. The disabled Save button also explains its state in a tooltip, including an unavailable folder or no unsaved changes.

Save creates the required folders and writes all definitions transactionally, with the workspace snapshot written last. Failed or canceled operations restore previous definitions and locations. External changes detected since loading or during a save prevent overwriting those changes. Recovery failures are reported explicitly.

The workspace definition is authoritative. Removing an entity keeps its existing files on disk and reports retained items. Changing an editable entity's folder name creates the new folder and retains the old folder and output data; use Cut/Paste to move an existing entity with its contents. Changes made directly on disk are not automatically adopted; import an existing entity to add its actual hierarchy.

The tree distinguishes unsaved items, pending copies/moves, and missing saved definitions. Status refreshes while the page is open and after loading, saving, or discarding. Save can restore missing definitions with the same IDs. A missing workspace root directory must be restored or another location selected first.

Before changing the root folder, returning Home, or closing, unsaved changes prompt for **Save / Discard / Cancel**. Save continues only after success; Discard abandons the draft; Cancel keeps editing. Selecting the same folder or canceling the picker keeps the current draft. Choosing an empty root without editing it does not count as an edit.

## Types and persistence

`Sortopia.Workspaces` defines concrete `rootProject`, `branchProject`, `rootModule`, and `branchModule` types. Their child arrays are strongly typed: for example, `rootProject.Runs` is `rootRun[]`, and `branchModule.Projects` is `branchProject[]`. The `project` and `workspaceModule` discriminated unions provide common views for storage and the editor. Their boundary factories validate type consistency. `workspace.Modules` accepts either `workspaceModule.Root` or `workspaceModule.Branch`. Array properties return copies.

Modules and projects expose their effective shared properties directly and through `Configuration` (`rootProjectConfig` or `branchProjectConfig`). `LocalOverrides` uses `rootDefaultOverrides` or `branchDefaultOverrides`: each property is optional, with `None` meaning inherit and `Some` meaning local, including `Some []` and `Some ""`. `Defaults.resolveRoot` / `resolveBranch` apply local values over the inherited configuration. For parameter defaults, `Defaults.mergeParameterDefaults` replaces matching keys, retains other inherited bindings in order, and appends new local keys. Both `None` and `Some []` inherit all parameter defaults; duplicate keys within a local list are invalid. Other list properties use whole-list replacement. `createInherited` constructs an entity with its parent configuration and local overrides; `rebind` resolves it and its descendants against a new parent. The existing project `create` factory makes every supplied configuration property local; the module `create` factory starts with all properties inherited.

`RootRun.create parent inputs` and `BranchRun.create parent inputs` accept their concrete parent projects through `IRootProject` / `IBranchProject`; the contracts avoid a dependency from runs back to workspaces. Run input records contain Id, RunName, ParentProjectId, DescriptionOverride, and ResultsParameterSpans. Branch inputs also contain SetupParameterSpans. Function overrides are absent from project local overrides and run inputs. Both database names come from the project. The parent must be sealed when constructing a runtime run; `project.seal` creates that immutable parent snapshot and `project.withRuns` attaches the validated runs. `RunDto.toDomain` prepares a sealed snapshot without mutating the draft parent. A run retains its inputs in `Configuration` and fixed settings in `ProjectConfiguration`. Branch runs also retain resolved source project snapshots, so queries need no further workspace lookup.

The four shared names have distinct UMX tags: `resultsDatabaseName`, `resultsFunctionName`, `setupDatabaseName`, and `setupFunctionName`. Shared configuration is factored into `resultsConfig` and `setupConfig`. A `setupDataTypeConfig` contains `DataType: sortopiaDataType`, `SourceProjectId: Guid<projectId>`, and `QueryParameterKeys: string<paramKeyName> list`. `setupConfig.DataTypes` is the ordered list; its `SortopiaDataTypes`, `SourceProjectIds`, and `QueryParameterKeys` views derive from those entries. Results query keys remain one list.

`workspace.ProjectIndex` indexes projects globally by ID, and `FindProject` returns an optional project. Workspace creation/loading validates references and resolves branch source snapshots through `BranchRunSources.resolve`. `QueryParams.forSource` uses the source project's ID, results database, and results query keys. `forSetup` uses the parent project's ID, effective setup database, and the selected entry's query keys; `forResults` uses the parent project's results metadata. Query IDs use the stable project ID, exact type/text pair, and selected parameter strings, rather than the display name.

`sortopiaDataType` is a discriminated union with ten cases: `Workspace`, `Run`, `WorkspaceModule`, `RunParameters`, `SorterPoolSet`, `SorterSet`, `SorterModelSet`, `SortableTests`, `SorterSetEval`, and `TextReport`. Every case carries a free-form `string`; empty strings, whitespace, Unicode, and line breaks are preserved. Execution and setup output lists use this type, as do result and setup queries. Each output row has a case selector and a text field. Lists can contain the same case with different text; an identical case/text pair cannot appear twice. Inherited lists show both values and retain their clickable source. Query matching and query IDs include both the case and the exact text.

`parameterBinding` is the general pairing of a `string<paramKeyName>` with a typed `parameterValue`. It can represent a supplied parameter, a default, or an override; the containing property or operation determines its role. `ParameterBinding.create key value` constructs a binding from a typed key, `fromValue name value` accepts an already typed union value, and `fromText name kind text` validates editor or persisted input. All constructors enforce the known key's type and valid values. `ParameterBinding.validateUnique` validates collections with one binding per key. `parameterBindingDto` and `WorkspaceParameterBinding` provide the corresponding storage and editor representations.

`parameterSet` stores a `Map<string<paramKeyName>, parameterBinding>` exposed by `ParamMap`. `parameterSet.fromBindings bindings` creates a set directly; `parameterSet.create map` accepts a typed map and validates that each key matches its binding. `set.WithBinding(binding)` adds or replaces a binding while preserving the original set. `WithValue` accepts a typed key/value or a key name with a `parameterValue`; `None` removes the key. Binding construction, validation, and set updates retain the typed values without formatting or reparsing them.

`set.TryFind(name)` returns a binding. `set.TryFind(typedKey)` reads the underlying CLR value directly, returning `None` for a missing key or mismatched type; numeric-looking text remains text. String conversion is explicit: `TryFindText(name)` formats one value, and `ToStringMap()` projects the whole set to canonical invariant strings. Queries format only their selected keys; DTO serialization formats bindings at the storage boundary. Library IDs remain typed through bindings, parameter sets, and catalog function calls. File-store identity uses their type tags and stable field bytes, so alternate input formatting produces the same data ID.

`ParameterSets.create bindings spans` expands bindings and spans into `parameterSet[]`. It parses span text using the matching binding's type or the known key's type, and stores each candidate as a typed binding. Matching spans replace bindings and other bindings remain fixed. Combinations exceeding the maximum .NET array length are rejected before allocation.

`ParameterSets.preview maxCount bindings spans` shares the same validation and combination generator, materializing only the requested prefix. All candidate values are validated, including values beyond the visible rows. The editor retains typed parameter sets and formats values only for display.

`RunParameterSets.create run` returns a `runParameterSets` record with `Results: parameterSet array` and `Setup: parameterSet array option`. Root runs return `Setup = None`; branch runs return `Some setupSets`. Results and setup combinations are expanded independently from their respective defaults and spans, retaining typed bindings. No spans is valid only when there are no output query keys and the defaults satisfy the required inputs. The function uses the run's resolved settings and does not need a workspace lookup.

`ResultsParameterDefaults` is a `parameterBinding list` on root/branch modules, projects, and runs. Branch types additionally expose `SetupParameterDefaults`. These properties use bindings as defaults, merging by key through modules and draft projects. Runs receive the sealed project's resolved defaults; their spans replace matching keys. `RootRun.makeResultsParameterSets`, `BranchRun.makeResultsParameterSets`, and `BranchRun.makeSetupParameterSets` use the general binding APIs. `ParamKeys.all` supplies metadata derived from the typed key declarations.

Every entity has a UMX-tagged GUID ID: `workspaceId`, `moduleId`, `projectId`, or `runId`. Its definition filename is `<id>.msgpack`. IDs survive edits, moves, and missing-file restoration. Folder names exist only on workspaces, modules, and projects. The absolute workspace location stays in application settings, outside the definitions.

Names must be nonblank, and sibling display names must be distinct ignoring case. Sibling module/project folder names must also be distinct ignoring case. Runs in a project require distinct IDs because their files share one directory. Rejected edits remain visible for correction while the tree keeps the last accepted value; Save is disabled until corrected. Saved names and folder names stay reserved until their removal or rename has been saved.

`Sortopia.Workspaces.Serialization` writes schema version 13 MessagePack DTOs. Library parameter values use distinct type tags and canonical identifier text at this storage boundary; they are parsed back into typed records on load. Data types are `{ kind, value }` pairs. Setup entries are `{ dataType, sourceProjectId, queryParameterKeys }`; results entries are `{ dataType, queryParameterKeys }`. Sealed snapshots preserve these per-output contracts and are checked against their catalog definitions on load. Projects persist `isSealed`, effective configuration, local overrides, and their runs. Modules retain database-free local overrides and effective snapshots in their own module settings DTO. Project database names are stored locally and remain fixed after sealing. For shared settings, null override fields inherit and empty arrays are explicit empty lists. Draft projects resolve against the actual hierarchy; sealed projects load their fixed configuration snapshots. Run files contain IDs, an optional description override, and spans; they contain no database override. `WorkspaceCodec.decodeRunById workspace bytes` finds the stored ParentProjectId, verifies a sealed parent of the correct family, and resolves source snapshots; `decodeRun parent bytes` supports callers already holding a sealed parent. Cross-project validation occurs after the hierarchy loads. Unknown or older schema versions are rejected, with no legacy migration. Saved runs lacking explicit query spans are also rejected rather than automatically converting their defaults. Each container definition includes its descendants.

workspace-folder/

  modules/

        Nested root module/

Definition limits are 64 nesting levels, 50,000 entities, and 16 MB per definition file. Multiple container definitions in one entity folder are reported as ambiguous. Unrelated files are not serialized; explicit folder imports and moves preserve their contents.
